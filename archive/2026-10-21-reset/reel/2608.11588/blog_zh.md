# CoAdapt-GUI：在新应用上同时调整工作流笔记和 LoRA 权重的移动端智能体

*CUA Radar 对 arXiv 2608.11588v1（Guo、Gu、Jiang、Chi、Reid、Wang、Yu、Liu、Wang、Chen）的解读。本文是第三方对论文所报告内容的整理，并非作者背书。海报见 `poster.png`。论文：https://arxiv.org/abs/2608.11588v1 · 看板上未列出代码仓库。*

## 问题：新应用带来的不只是新任务

移动端 GUI 智能体在训练中见过应用和工作流的基准上表现不错。论文的出发点是：在熟悉界面里完成新任务，并不意味着在陌生应用里也能有效行动。它引用了此前的 AndroidWorld-Generalization 研究：源端在线 RL 使 7B 策略在未见任务实例上提升 26.1 个百分点，但在未见应用上只提升 8.3 个点。

陌生应用可能暴露两类缺口。智能体也许理解目标，却无法把动作落到不熟悉的界面元素上；或者单步动作都对，却缺少完成任务所需的工作流和完成条件。只更新策略或只更新上下文，都可能留下其中一种失败没有解决。论文的设定是测试时自适应（TTA）：在目标应用上只有有限的交互预算，没有目标示范，并且在留出评测之前冻结结果。

## CoAdapt-GUI 是什么

**智能体。** 这是一个移动端 GUI 智能体：视觉语言策略接收任务、当前观测、交互历史，以及一段渲染后的工作流文本（附录的提示模板里列出截图和 UI 元素列表作为输入），输出由 Android 模拟器执行的动作。设定一使用已发布的 step-500 UI-TARS-7B 检查点，设定二使用 Qwen3-VL-8B-Instruct。平台是 Android。在 CUA Radar 看板上的架构模式是 C19（experience memory and retrieval，经验记忆与检索）。

**两个自适应状态。** 一个显式的工作流状态 M，和一个参数化状态 theta（冻结 VLM 上的 LoRA 适配器）。每个可迁移的工作流条目有四个带类型的字段：适用条件、抽象流程、失败或恢复条件、完成检查。

**迁移边界。** 对每个源应用，系统构建一个屏幕转移有限状态机（具体屏幕、转移、可见线索）。这部分与应用绑定，不会离开源应用。只有抽象后的条目才有资格迁移到别的应用，并且由 schema 校验器和 linter 拒绝含有应用名、包名或资源标识、具体控件文字、坐标或任务实例取值的条目。合格条目按 Google Play 类别分组，合并成冻结的源库。目标应用只能检索自己所属的类别；如果其类别不在源池中，检索返回空先验。

**奖励引导的上下文更新。** 适应期间，控制器维护一个用 TrueSkill 评级的上下文变体种群。每轮最多采样两个变体，对每个任务-上下文组合跑四条匹配的 rollout，并根据可执行的任务奖励更新评级。一个冻结的 reflector（AndroidWorld Plus 配置中为 Claude Opus 4.7）对比成功与失败轨迹，向高评级的父节点提出带类型的 diff。子节点只有在通过 schema、来源和 lint 检查后才进入种群，并且不继承任何奖励：它要在之后的轮次被采样时才获得评级。最后保留评级最高的合格状态。

**任务-上下文匹配的策略更新。** 同一批 rollout 还用于在线的 group-relative 目标（Shao et al. 2024）。由于上下文会改变策略的输入，优势只在同时共享任务和上下文变体的 rollout 之间计算。只有单个成员或奖励恒定的分组没有梯度；缓冲区是 on-policy 的，每次尝试更新后清空。

**训练信号。** 来自基准程序化评估器的可执行任务奖励，取自智能体自己在目标应用上的 rollout。预算用完后，上下文和适配器被冻结，再跑留出任务。两个通道通过交互而非梯度耦合：上下文塑造策略学习所用的轨迹，策略产生 reflector 读取的成功与失败。

## 论文报告的结果

以下均为在线模拟器回合的成功率（SR），由基准的程序化评估器判定。论文没有报告离线的单步准确率。

**设定一：AndroidWorld-Generalization，UI-TARS-7B，五个目标应用，48 个留出实例。** 适应和评测使用同样的 16 个任务模板，但种子不重叠，因此测的是对适应阶段见过的任务类型的新实例。Base Policy 和 Policy-Only TTA 取自此前的 AndroidWorld-Generalization 论文；其余三行是作者五次运行的均值 ± 标准差。

| 方法                    | 适应实例数 | SR (%)       | 来源             |
|-------------------------|------------|--------------|------------------|
| Base Policy             | 0          | 27.10        | 引用             |
| Static Context Transfer | 0          | 28.75 ± 2.28 | 作者（5 次运行） |
| Policy-Only TTA         | 40         | 37.50        | 引用             |
| Context-Only TTA        | 40         | 35.00 ± 1.74 | 作者（5 次运行） |
| CoAdapt-GUI             | 40         | 45.00 ± 1.86 | 作者（5 次运行） |

论文写明，CoAdapt-GUI 比引用的 Policy-Only TTA 高 7.5 个点，在相同的适应实例和 rollout 预算下比 Context-Only TTA 高 10.00 个点。

**设定二：AndroidWorld Plus，Qwen3-VL-8B-Instruct，105 个留出回合，模板与适应阶段不相交。** 作者在 AndroidWorld 基础上加入了来自 B-MoCA 的三个应用和来自 AndroidLab 的三个应用（共 25 个应用、191 个模板）。12 个应用作源，13 个作目标。每个目标应用内，适应和评测使用不相交的模板。每个自适应配置每个应用运行 20 轮。

| 方法                    | Category-Shared | Category-Novel | 总体 SR (%) |
|-------------------------|-----------------|----------------|-------------|
| Base Policy             | 47.2            | 29.4           | 38.6        |
| Static Context Transfer | 56.5            | 29.4           | 43.3        |
| Policy-Only TTA         | 53.7            | 25.5           | 40.0        |
| Context-Only TTA        | 63.9            | 31.4           | 48.1        |
| CoAdapt-GUI             | 70.4            | 34.3           | 52.9        |

论文报告相对 Base Policy 提升 14.3 个点。一次 20 轮的适应运行在 NVIDIA H200 上平均约需 9–10 GPU 小时。

## 论文自带的对照实验

- **组件路径（表 2，附录 E）。** 累积的上下文路径（Static Context Transfer，再到 Context-Only TTA）达到 48.1，论文写明比 Base Policy 高 9.5 个点；Policy-Only TTA 只提升 1.4。CoAdapt-GUI 比 Context-Only TTA 再高 4.8 个点。增量表还显示，Policy-Only TTA 使 Category-Novel 的成绩下降（变化为 -3.9），而目标端上下文构建对两组都有提升。
- **内置的源迁移对照。** 在 Category-Novel 应用上，源检索为空，所以 Static Context Transfer 与 Base Policy 完全相同（29.4）。Context-Only TTA 和 CoAdapt-GUI 在这里仍然有提升（31.4 和 34.3），论文据此认为，没有类别匹配的源经验时，目标端适应依然有效。
- **留出设计。** 源应用池和目标应用池不相交，所有更新和检查点选择只使用适应划分，且在打开留出清单之前冻结两个状态。留出面板覆盖 13 个目标应用中的 12 个（有一个应用只有一个模板，只用于适应）。

## 证据偏薄之处，用论文自己的话

- Context-Only TTA 与 CoAdapt-GUI “独立运行，因此可能收集到不同的、依赖策略的轨迹；它们的差异反映的是完整的联合流程，而不是对 LoRA 更新本身的受控估计”。
- 设定一中名义上的 50 次更新计划“不应被解读为各方法之间相同的梯度或计算预算”，因为上下文修订和策略优化使用不同的更新算子。
- 设定一的 Base Policy 和 Policy-Only TTA 数值“未在我们的环境中复现”。
- 表 2 没有给出标准差，附录中的五次运行说明只针对设定一。评测集很小：五个应用上的 48 个实例，以及 105 个回合。
- 设定一中评测模板与适应模板相同（只是新实例），设定二中目标应用被用于适应；这里的“留出”指实例或模板，而不是应用本身。

## CUA Radar 的判断

CUA Radar 给这篇论文打 **80 分（三星）**，证据等级 **transfer**。判定记录认可：使用程序化评估器的在线评测、留出应用与模板、五次运行的方差（设定一）、使用相同适应任务和 rollout 预算的基线、成本报告（每次适应运行 9–10 GPU 小时），以及组件消融。判定记录没有标出风险项，论文也没有给出代码链接。CUA Radar 没有复现任何实验，本文所有数字均来自论文（版本 v1）。
