# StepWise：默认用小模型操作电脑，只在卡死或漂移时升级到大模型

*CUA Radar 对 arXiv 2604.27151v1（Wei、Ni、Zhao、Gan、Cohan，Yale NLP Lab 与 UNC Chapel Hill）的解读。本文是第三方对论文所报告内容的整理，并非作者背书。海报见 `poster.png`。论文：https://arxiv.org/abs/2604.27151v1 · 代码：https://github.com/yale-nlp/StepWise*

## 问题：每一步都调用前沿模型

Computer-use agent 直接操作图形界面，而最强的那些系统几乎在每一个交互步都调用大型多模态模型。论文从部署视角切入：现实的多步任务要跑 20–35 步、消耗数十万 token、耗时以十分钟计，全程用前沿模型时单任务推理成本可能超过一美元。论文的反命题是：这种均匀的算力分配本身就是低效的，因为 GUI 轨迹是异质的——大多数步骤是常规操作，失败集中在少数高风险时刻。

论文把这些失败归为两类。**Progress stall（进度停滞）**：循环、重复等价动作、界面状态不变。**Silent semantic drift（静默语义漂移）**更隐蔽：agent 偏离用户意图之后仍在”合理地”继续操作，后半段轨迹局部自洽但注定失败。对小型策略的测量（Figure 2）支持这一划分：EvoCUA-8B 的失败轨迹平均比成功轨迹长 2.8×，Qwen3-VL-8B 是 2.5×；失败轨迹的动作重复率显著更高；还有一部分失败最终仍由模型主动发出 done——这正是漂移的信号。

## StepWise 是什么

这是一个标准 GUI agent：观察截图（可选附加 accessibility tree/DOM 信号），输出一段简短文字 rationale 和一个可执行动作（click、type、scroll、hotkey）；桌面任务跑在 OSWorld 的 Ubuntu 虚拟机上，网页任务跑在 WebArena-Verified 上。它在 CUA Radar 板上的架构模式是 C18：“对比动作前后的观察、验证动作结果并把结论反馈回环路”（隶属 agent loop 的上下文控制主模式）。

StepWise 本身是一个包在两个策略外面的部署时控制器：便宜的 π_small 默认执行，强大的 π_large 按需介入。每一步 t，控制器从 agent 自己的生成日志里取最近 K 个（rationale, action）对构成滚动窗口 w_t——刻意只用文本、不用截图或 DOM 差分——然后用两个 ModernBERT-base 编码器（各 149M 参数）打分：

- **Stuck monitor** S_φ(w_t) → p_stuck。分数超过阈值 θ_s 时，下一步升级到大模型；小模型的近期历史会被重新序列化进大模型的回复格式，使其能就地接手。
- **Milestone monitor** M_ψ(u, w_t) → p_mile，额外以任务描述 u 为条件，因为里程碑依赖目标。触发时系统组装一个里程碑包——任务指令、自上一个已验证里程碑 τ_t 以来的轨迹、前后两张截图——交给更强的验证模型回答两个问题：这段轨迹是否在向目标推进（progress validity）？当前 UI 状态是否符合预期结果（intent consistency）？任一不过就升级；都通过则提交里程碑并保存截图，作为下一个检查点。

训练信号完全来自合成数据：跑小模型收集 300 条 GUI agent 轨迹，用 GPT-5.2 给每个步窗口打标签（stuck 判定只看 w_t；milestone 判定看 u 和 w_t）。每条轨迹独立标注 5 次，至少 3 次命中记正例、0 次记负例、1–2 次的丢弃以降噪。两个编码器用类平衡交叉熵微调（5 个 epoch，AdamW，80/20 划分）。部署时通过阈值 (θ_s, θ_m) 在成功率与成本之间取操作点。

## 论文报告的结果

以下全部是在线、按执行结果判定的成功率；成本为 OpenRouter 参考价，延迟在 2× H100 本地部署上测得。论文没有报告随机种子、方差或置信区间。OSWorld 上小模型为 EvoCUA-8B 和 Qwen3-VL-8B，大模型为 Claude Sonnet 4.5 和 Kimi K2.5；WebArena-Verified 上小模型为 gpt-oss-20b 和 AgentTrek-32B，大模型为 GPT-5 mini 和 GPT-5.2。

| 设置（OSWorld）          | 成功率 | 成本/任务 | 延迟/请求 |
|--------------------------|--------|-----------|-----------|
| EvoCUA-8B 单独           | 43.3%  | \$0.022   | 2.6s      |
| Qwen3-VL-8B 单独         | 30.8%  | \$0.018   | 3.9s      |
| Claude Sonnet 4.5 单独   | 58.1%  | \$0.881   | 6.4s      |
| Kimi K2.5 单独           | 60.1%  | \$0.132   | 8.3s      |
| EvoCUA-8B + Sonnet 4.5   | 55.4%  | \$0.224   | 4.1s      |
| EvoCUA-8B + Kimi K2.5    | 58.2%  | \$0.051   | 4.5s      |
| Qwen3-VL-8B + Sonnet 4.5 | 54.3%  | \$0.423   | 5.2s      |
| Qwen3-VL-8B + Kimi K2.5  | 59.3%  | \$0.078   | 6.5s      |

| 设置（WebArena-Verified）  | 成功率 | 成本/任务 | 延迟/请求 |
|----------------------------|--------|-----------|-----------|
| gpt-oss-20b 单独           | 37.6%  | \$0.001   | 6.9s      |
| AgentTrek-32B 单独         | 30.3%  | \$0.005   | 3.9s      |
| GPT-5 mini 单独            | 55.0%  | \$0.053   | 11.1s     |
| GPT-5.2 单独               | 60.1%  | \$0.335   | 19.6s     |
| gpt-oss-20b + GPT-5 mini   | 51.3%  | \$0.027   | 8.5s      |
| gpt-oss-20b + GPT-5.2      | 57.8%  | \$0.211   | 12.2s     |
| AgentTrek-32B + GPT-5 mini | 52.3%  | \$0.028   | 9.4s      |
| AgentTrek-32B + GPT-5.2    | 58.8%  | \$0.208   | 13.4s     |

用论文原话概括节省幅度：Qwen3-VL-8B + Kimi K2.5 在 OSWorld 上达到 59.3%，“非常接近独立 Kimi K2.5 的 60.1%”；EvoCUA-8B + Kimi K2.5 以每任务 \$0.051 达到 58.2%，“成本降低 61.4%”；贡献部分声称相对全程大模型最多降低 74.6% 的成本和 45.8% 的延迟。八个级联配置中大模型承担 37.4–69.4% 的执行步，46.8–73.0% 的任务至少调用过一次大模型。另一个横贯观察：最终成功率更多由大模型的选择决定，而不是小模型——“小模型主要决定成本，大模型主要决定最终准确率”。

## 论文自带的对照实验

**组件消融（Figure 3）。** OSWorld 上以 Kimi K2.5 为大模型：EvoCUA-8B 从 43.3%（无检测器）→ 49.7%（仅 stuck）→ 53.2%（仅 milestone）→ 58.2%（两者都开）；Qwen3-VL-8B 从 30.8 → 52.1 → 47.6 → 59.3。WebArena 上以 GPT-5.2 为大模型：gpt-oss-20b 从 37.6 → 44.9 → 54.7 → 57.8，AgentTrek-32B 从 30.3 → 49.6 → 48.9 → 58.8。任一单独检测器都优于无检测器，两者同开在所有配对上最好；且分工与失败签名吻合——循环严重的 Qwen3-VL-8B 从 stuck 检测获益最大，重复较少、漂移较多的 gpt-oss-20b 从 milestone 验证获益最大。

**事件驱动 vs 固定间隔（Table 3）。** 每 k 步调用同一大模型检查的周期基线（k ∈ {3, 5, 7} 取最优）：OSWorld 上 55.1%、\$0.07/任务，对比事件驱动的 58.2%、\$0.05；WebArena 上 52.5%、\$0.24，对比 58.8%、\$0.21。周期检查从不更便宜，在轨迹更短的 WebArena 上还明显更不准。

**检测器质量（Table 4）。** 在 EvoCUA-8B 数据留出的 20% 上，学到的 stuck 检测器达到 93.9% 准确率、91.5 F1；milestone 检测器 94.1% 准确率、62.0 F1（论文强调 F1，因为里程碑稀疏且有些含糊）。作为参照，独立 GPT-5.2 标注在同数据上的一致性为 96.5% 准确率 / 92.7 F1（stuck）和 94.3% / 77.1 F1（milestone）。

## 论文自己承认的薄弱处

- 监控器和验证器只对照其教师验证：检测器评估测的是与 GPT-5.2 标签的一致性，而非人类真值；论文也没有测试策略是否会钻判定器的空子。CUA Radar 将此标记为反模式 AP4（判定器使用缺乏双侧面可靠性验证）。
- 所有基准数字均未报告种子、方差或置信区间。
- 判定记录中 held-out 环境一项为 unclear。论文确实写到”我们评测所用的任务始终与用于生成 gold 轨迹的任务不相交”，但监控器训练与评测的任务分布来自同一批基准套件。
- 成本是基于 OpenRouter 定价的参考估算，不是实际计费。

## CUA Radar 的判断

CUA Radar 给这篇论文打 **63 分（★★）**，证据等级 **transfer**。分数反映论文所报告的证据：OSWorld 与 WebArena-Verified 上的完全在线评测、包括预算可比的周期检查基线在内的强基线、成本与延迟报告、组件消融，以及对照 GPT-5.2 参照的检测器级测量。判定记录同时标出了缺失项：方差报告、held-out 环境、代码核查，以及学到判定器的人类侧验证（AP4）。CUA Radar 没有复现任何实验，本文所有数字均来自论文（版本 v1）。
