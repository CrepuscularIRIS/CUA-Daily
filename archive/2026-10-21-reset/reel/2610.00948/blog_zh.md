# GUI-HARVEST：让优化器改写冻结 GUI 模型外面的 harness

*CUA Radar 对 arXiv 2610.00948v1（Yang、Qu、Li、Wang、Zhang、Zeng、Dai）的解读。本文是第三方对论文所报告内容的整理，并非作者背书。海报见 `poster.png`。论文：https://arxiv.org/abs/2610.00948v1 · 代码：https://github.com/GaryYang12345/GUI-HARVEST*

## 问题：harness 是代码，却没有针对每个模型调过

桌面 GUI 智能体不只是一个模型。模型外面还有一层可执行的 harness：如何构造观察和上下文、如何分发动作，以及如何控制验证、恢复和终止。Meta-Harness、Self-Harness 等自动 harness 优化器已经能根据轨迹修改提示词和代码，但它们面向非 GUI 领域，读到的主要是文本、源码和分数。

作者指出这些通用优化器没有解决三个问题。第一，文本轨迹可能声称成功，而屏幕上仍是未完成的状态，例如点了保存但对话框还开着。第二，即便解码是确定性的，同一个智能体在同一任务上也可能时成时败：在基线运行中，依骨干模型不同，11.8% 到 20.4% 的任务在三次执行中既出现零分又出现正分。第三，针对一个任务写的补丁不一定对别的任务有用。

## GUI-HARVEST 是什么

被改进的智能体是一个冻结的模型加一套 harness，在桌面上根据截图和文本行动。对 Qwen3-VL 和闭源骨干，起点 harness 是 Agent S3：worker 每步输出一个 `agent.*` 原语，grounding 模型（UI-TARS-1.5-7B）把描述的目标映射为坐标，再编译成 PyAutoGUI 代码。OpenCUA 模型则从其官方运行时出发，直接输出带坐标的 PyAutoGUI 动作。在 CUA Radar 板上，它的架构模式是 C19：从智能体自身运行中积累可复用知识，这里积累的形式是可执行代码。

优化器从不改动权重、任务、评测器或资源限制，只能编辑 capability manifest 中列出的文件。任务被划分为 Search（80）、Validation（80）和封存的 Test（201）。每一轮包含五步：

1.  **Repeated rollouts（重复采样）。** 每个 Search 和 Validation 任务从干净快照运行 K = 3 次。Search 的运行提供详细证据，Validation 只提供汇总分数。
2.  **Evidence Analyst（证据分析员）。** 对至少有一次零分运行的任务，分析员对比各次运行，写出指向决定性步骤的 finding；若有成功运行则作为对照。工具包 GAFT 把文本、动作和前后截图按步骤对齐。确定性校验器检查所引用的运行和步骤是否存在；论文指出，行为层面的解读仍是分析员的判断。
3.  **Cross-task Clusterer（跨任务聚类器）。** 把 finding 归并为开放词汇的行为模式（behavior mode），每个模式至少需要两个独立任务支持。
4.  **Harness Engineer（harness 工程师）。** 做一次有界的源码修改，运行本地测试，并在任何 GUI 评估之前记录对可观察行为的预测。
5.  **Validator（验证器）。** 通过代码检查后，效用门要求 Search 和 Validation 都不下降且至少一个提升；行为门由另一个验证器判断编辑后的运行是否支持事先冻结的预测。两道门都通过才晋升，否则回滚。

每轮最多尝试 P = 5 个候选修改，最多 B = 10 轮；当同一状态下五次尝试全部被拒绝时优化停止。四个角色都使用 Claude Sonnet 5，搜索采用 15 步预算。因此训练信号是 OSWorld 评测器的分数加上行为判定，不更新任何权重。

附录给出一个完整例子。在一个 Chrome 任务中，三次运行里有两次输入了新的用户名，却在输入框仍处于编辑状态时调用 done()，因而失败。该模式 EDIT_NOT_COMMITTED_AT_DONE 在 Impress 和 Calc 任务中也出现，催生了一个扣留首次过早 done() 的门；验证器在三次编辑后的运行中都判定预测成立（supported）。

## 论文报告的结果

以下均为 OSWorld-Verified（排除 8 个 Google Drive 任务后共 361 个任务）上的在线分数：K = 3 次运行的原始评测分数均值，15 步预算，优化后冻结的 harness H\*。论文没有报告离线基准。

| 骨干模型       | Test 初始 | Test GUI-HARVEST | Full 初始 | Full GUI-HARVEST |
|----------------|-----------|------------------|-----------|------------------|
| Qwen3-VL-8B    | 28.79     | 34.84            | 29.49     | 36.83            |
| Qwen3-VL-32B   | 43.02     | 53.18            | 38.61     | 50.94            |
| OpenCUA-32B    | 32.82     | 34.31            | 30.71     | 34.24            |
| OpenCUA-72B    | 41.25     | 44.18            | 37.65     | 42.33            |
| Gemini 3.1 Pro | 66.42     | 72.63            | 66.46     | 73.37            |
| GPT-5          | 56.35     | 61.86            | 55.20     | 62.42            |

Test 上的提升从 +1.49 到 +10.16 个点；Qwen3-VL-32B 在 Full 上提升 +12.33。以 15 步优化后冻结的 harness 还在 50 步和 100 步下评测，Gemini 3.1 Pro 在 100 步达到 79.14%。论文称在其展示的所有与已发表系统的比较中得分均为最高，这些已发表行保留各自的运行时和预算。

## 论文自带的对照实验怎么说

**同模型优化器对比（Table 2）。** 在同一个 Qwen3-VL-32B 与 Agent S3 harness、同一个优化器模型和十轮上限下，Test 分数为 GUI-HARVEST 53.18、Self-Harness 45.02、Meta-Harness 47.40；Full 上分别为 50.94、42.08、45.10。这两个基线都是作者自己做的 GUI 适配版本。对于优化器未公开的 LFF，作者套用其发布的 OpenCUA 补丁：在 OpenCUA-72B 上为 44.18 和 42.33，对比 41.29 和 39.50。

**消融（Qwen3-VL-32B，Test / Full）。** 去掉视觉证据 44.54 / 40.69；去掉聚类器 45.66 / 42.13；单次运行证据（K = 1）47.44 / 43.12；仅用硬门 49.36 / 48.08；完整方法 53.18 / 50.94。仅用硬门的变体跑了九轮，却选出了分数更低的 harness。K = 3 得到 50.9%，K = 1 为 43.1%，K = 5 的 rollout 成本更高而结果为 49.7%。

**成本。** 成本只包含目标模型的调用，不含优化过程。GPT-5 从 55.2%（\$78.6）变为 62.4%（\$72.3）；Gemini 3.1 Pro 从 66.5%（\$140.0）变为 73.4%（\$92.4）。论文与 Agent S3 在 GPT-5 上的比较（62.4% 对 62.6%，\$72 对 \$260）明确不是同预算实验：前者 15 步，后者 100 步。

## 证据偏薄之处（用论文自己的话）

- 提升依赖骨干模型：OpenCUA 的 Full 提升为 3.53 到 4.68 个点，其他模型为 6.91 到 12.33；作者认为这与其“对新增工具和控制机制适应性较低”相符（consistent with），而非已被证明。
- 预算从 15 步提高到 100 步，Qwen3-VL-8B 和 32B 只多得 2.54 和 0.85 个点。
- 剩余失败是“执行成功但选错了对象、路径或与评测相关的状态”的动作，harness 很难察觉。
- Search、Validation、Test 是同一基准的随机划分；Test 任务虽未被优化器见过，但与 Search 共享领域，Full 的数字也包含优化所用的任务。WAA 迁移只覆盖两个骨干。
- 论文给出 K = 3 时 Full 均值的标准误为 0.93 个点，但没有报告重复的优化运行，也没有用人工标注检验行为验证器。

## CUA Radar 的判断

CUA Radar 给这篇论文打 **76 分（★★★）**，证据等级 **transfer**。判定记录肯定了在线评测、留出的 Test 划分、同骨干的优化器基线、主要比较中对齐的骨干与步数预算、成本报告、组件消融和已发布的代码；把方差标为 unclear，行为验证器的检验标为 untested；并标出反模式 AP5（优化与评测来源重叠），因为 Search 与 Test 来自同一基准。CUA Radar 没有复现任何实验，本文所有数字均来自论文（版本 v1）。
