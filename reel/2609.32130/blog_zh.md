# REBASE：在应用更新之后，让手机上的 GUI agent 缓存的经验保持正确

*CUA Radar 对 arXiv 2609.32130v1（Wu、Huang、Zhao）的解读。这是第三方对论文所报告内容的总结，并非作者背书。海报：`poster.png`。论文：https://arxiv.org/abs/2609.32130v1*

## 问题：过期的路径看起来并没有坏

部署在手机上的 GUI agent 运行一个小模型并复用经验：这些是此前运行时记录下来的动作路径，由厂商在云端整合，再缓存到设备上。应用更新后，其中一部分路径会变得部分错误，却不会变得不可用。在九对真实的版本上，论文报告：携带旧版本经验的 agent 成功率比不带经验的低 10.1 个百分点。失败是静默的：在 62.2% 的执行中，被更新破坏的步骤仍然能找到一个元素去操作，所以 agent 要在 3 步之后才发现不匹配。有两个信号没有被利用：厂商的云端往往能比设备更早拿到新版本，而设备在失败之前就已经知道自己更新了。

## REBASE 是什么

REBASE（Replay-Backed Attestation with Staged Evidence）是一个设备与云端之间的协议，不是训练出来的模型。设备端在 Jetson AGX Orin 上运行 INT4 的 Qwen3-VL-8B-Instruct；云端 agent 是 Gemini 3.1 Pro；一块 Jetson AGX Thor 充当网关并托管一个虚拟的 Android 设备。agent 观察 accessibility tree，回放记录下来的路径，路径中的每一步通过指纹（role、label、归一化的框，以及两层祖先的哈希）绑定到元素上，通过执行这些步骤来行动。在 CUA Radar 板上它属于 C19 模式，即复用 agent 自身的经验。

协议由两个“时钟”驱动：

- **更新时钟**（版本变化时）。云端在新版本上回放自己那份路径副本，不调用任何模型，找出每条路径上第一个失败的步骤，重新推导出补丁，并为每条路径推送一个比特外加一个步骤索引。在设备端，每个记录下来的步骤在执行前后都要验证：元素必须在屏幕上，后继屏幕必须与记录的一致。
- **失败时钟**（验证出现不匹配时）。设备按从小到大的顺序发送证据，在第一个能让云端产出经过测试的补丁的层级停下：L0 指纹和失败的步骤，L1 accessibility-subtree diff，L2 低分辨率裁剪，L3 截图。云端提出候选元素，在虚拟设备上测试，并把补丁以版本键（应用、版本、元素）提交，所以一次修复可以服务整个设备群。

信号就是验证和虚拟设备测试给出的结果；没有任何微调。论文中支撑这个阶梯设计的测量是：accessibility-subtree diff 能修复 79.1% 的失败步骤，单独的指纹为 27.4%，而裁剪、298 KB 的截图和完整轨迹各自只多带来约 9.4 个百分点，其中截图的字节数中位数是 diff 的 36.6 倍。

## 论文报告的结果

所有结果都是 AndroidWorld 上的 online 评测：九个应用，每个有两个版本（AndroidWorld 固定的版本，以及下一个会在记录路径上改变 accessibility tree 的 F-Droid 发行版），每对五个任务，共 45 个评测单元。其中六对云端能拿到新版本，三对是盲的（云端拿不到新版本）。每个对照臂在三个随机种子下运行 K = 5 个更新后的 episode，每个 episode 最多 30 步或六分钟。成功由评估器直接读取应用状态，所以没有模型参与判断。Succ@K 是 K 个 episode 上的成功率。

| 方法                        | Succ@K (%)     | 上行 KB | 云端调用 | 设备 J |
|-----------------------------|----------------|---------|----------|--------|
| 无经验                      | 47.7 ± 2.0     | 0.0     | 0.00     | 1730   |
| 过期经验                    | 37.6 ± 2.5     | 0.0     | 0.00     | 940    |
| 失败后重新探索              | 69.3 ± 4.5     | 0.0     | 0.00     | 1612   |
| 截图上传云端（MAI-UI 形式） | 92.9 ± 0.8     | 2912.0  | 9.60     | 539    |
| 轨迹上传（CoMIC 形式）      | 92.1 ± 1.1     | 883.9   | 0.30     | 1042   |
| **REBASE**                  | **93.8 ± 1.3** | 2.5     | 0.20     | 702    |
| 纯云端 agent（能力上界）    | 97.5 ± 1.1     | 3825.7  | 12.57    | 152    |

相对过期经验，REBASE 把 Succ@K 提高了 56.1 个百分点（95% 区间 \[51.6, 60.6\]），与在新版本上重新记录的新鲜经验只差 0.4 个百分点（区间 \[-2.1, 3.0\]）。在云端可见的单元中，91.1% 在第一个 episode 就恢复，盲对为 68.9%，重新探索为 28.1%。论文给出的数字是：比截图上传少 708 倍字节、少 47.3 倍云端调用，比轨迹上传少 215 倍字节。截图上传在 Succ@K 上与 REBASE 持平，是因为云端会完成每一个出问题的 episode；设备从未回到自主成功。

## 论文自带的对照说明了什么

**消融（九对，Succ@K）。** 去掉更新时钟为 90.5；去掉失败时钟为 80.6（盲对为 56.4 对 88.0，云端可见的对为 92.7 对 96.7）；云端盲为 90.5；去掉设备端验证为 90.4；证据固定在截图层为 93.0，但上行字节是 REBASE 的 14.4 倍；固定在 diff 层为 84.0；用文字指导代替可执行补丁为 80.4。论文认为小模型回放一个记录下来的动作，比理解修复建议更可靠。

**链路档位。** 带宽从 50 降到 2 Mbps、往返时间从 20 升到 250 ms，REBASE 的 Succ@K 与最快档位的差距分别在 2.7 和 4.0 个百分点以内，episode 延迟在 32.5 到 33.2 秒之间；截图上传的延迟则从 48 秒升到 61 秒。

**设备群与能耗。** 有了版本键，在由轨迹驱动的 100 台设备的模拟中，云端重新推导的次数比没有版本键时少 80.0 倍。每个 episode 中设备的能耗比无经验少 2.5 倍，比重新探索少 2.3 倍，但比截图上传更多（539 J 对 702 J），因为那里有更多推理在云端完成。

## 证据偏薄之处

- 只有一个测试台：两台 Jetson 设备加一个网关，九个 Android 应用，每个一对版本。盲对只有三对，100 台设备的设备群是由轨迹驱动的，不是真实设备。
- 两个基线是“以 MAI-UI 和 CoMIC 的形式”重新实现的，并不是这两个系统的端到端版本。
- 方法依赖 accessibility tree：“我们九个应用中每一次测得的失败都暴露了子树”，没有它的屏幕（canvas、不透明的 web view）要从裁剪层开始。论文把桌面 agent 列为下一步工作。
- 标准差是对三个随机种子计算的。
- 论文没有单独的局限性章节，也没有代码链接；CUA Radar 的记录把代码标为 unclear。

## CUA Radar 的解读

CUA Radar 给这篇论文打 **68 分（★★）**，证据等级 **online**。记录认可：用应用状态评估器做的 online 评测、三个种子上的标准差、在相同 K 和步数上限下的接管式与轨迹上传式基线、成本报告以及组件消融；held-out 评测标为 partial（三个盲对），没有标注 flag。CUA Radar 没有重跑任何实验；本文所有数字都来自论文（版本 v1）。
