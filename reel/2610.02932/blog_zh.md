# PACE：判断把 GUI 流程编译成程序到底什么时候真的省 token

*CUA Radar 对 arXiv 2610.02932v1（Ming、Xu、Wu、Jia）的解读。这是第三方对论文所报告内容的总结，并非作者背书。海报：`poster.png`。论文：https://arxiv.org/abs/2610.02932v1 · 代码：https://github.com/myl7/computer-use*

## 问题：单次运行便宜，不等于整体便宜

computer-use agent 反复执行同一个 GUI 流程（添加日历事件、删除笔记）时，可以把成功的 trace 编译成带参数的程序：一次模型调用抽取任务输入，之后程序不再调用模型就能跑完整个流程。以往的审计给出的 payback count（收回编译成本所需的使用次数）从 4 到 17 不等，但它们衡量的是系统的不同部分，数字之间无法比较。论文指出两个难点。其一，编译成本不确定：一次尝试可能需要修复，最后仍然得不到可用的程序。其二，未来复用次数未知：任务可能不再出现，或者 GUI drift 会让程序失效。太早编译，任务不重复就白花 token；等得太久，任务频繁出现时又损失了本可节省的部分。

## PACE 是什么

PACE（Payback-Aware Compilation from Experience）包含两部分：一套测量协议和一个在线算法。agent 每一步读取截图加 accessibility tree 或 DOM tree，运行 ReAct 风格的循环；编译后的程序在一次输入抽取调用之后取代这个循环。整个过程没有训练：信号是 token 开销和验证结果。在 CUA Radar 板上，这篇论文属于 C19 模式，即从 agent 自身运行中积累可复用知识。

**测量。** 用 k = 3 条已完成的 agent trace 编译（沿用 AutoRPA 的翻译与构造阶段），允许有限次修复，并要求程序通过全部三个源任务的验证。记录成功和失败尝试的成本，并在匹配的输入上比较程序和 agent 的成本，单位是加权 token。任务族包括：四个 AndroidWorld 任务、两个在基于 OSWorld 的容器里自建的 LibreOffice 任务、一个 WebArena Reddit 评论任务；模型为 GLM 5.3 Flash、DeepSeek Flash 和 Qwen 3.8 Flash。

**在线算法。** PACE 先为到达的任务提供服务，再考虑是否编译。savings test 把预计的未来节省与预计的编译成本比较，后者包含预期的失败尝试。另有独立的预算检查，在任何服务或编译动作之前先预留最坏情况的开销。在论文声明的成本模型假设下，每次任务到达之后，累计成本都不超过“全部任务都交给 agent 执行”的成本的 1 + ε 倍；主要评测中 ε = 0.25。论文明确说这约束的是成本，不是任务成功率，也不声称 PACE 能最小化期望成本。

## 论文报告的结果

**实测的编译成本。** 在有编译阶段记录的二十个格子里，十一个产出了通过验证的程序。这些程序的抽取成本为 331 到 724 个 token，估计的节省比例为 0.936 到 0.999。在六个已验证的 Android 程序上做了 180 次匹配的 agent 重放，节省比例为 0.952 到 0.999；其中 agent 成功 157 次，程序成功 178 次。在记录完整的 DeepSeek 尝试中，失败尝试的成本中位数为 1701K token，成功的为 259K。不含源任务运行的 payback count 为 1.389 到 15.488 次。

**模拟的决策规则（offline）。** 各策略在相同的编译器和相同的成本记账下比较；基线是 AutoRPA（只尝试一次、不重试）和 ToolPro（只计当前任务的节省）的决策规则改写版，不是原系统。在这些条件下 ToolPro 的成本与 ReAct 相同。在两个各含 300 个条件的网格上，ReAct 的成本平均是 PACE 的 1.107 倍和 1.130 倍。在四条记录下来的到达序列（两个流程日志、两个 Wikipedia 编辑流）上，PACE 比 ReAct 便宜 17.34%（条件 95% 区间 \[14.96, 19.61\]%），在十二个模型与日志的组合中有九个更便宜；摘要还给出相对 AutoRPA 改写版的 24.9%。

| 成本，GLM 5.3 Flash（× PACE） | Sepsis | BPI 2019 | Wiki tools | Wiki humans |
|-------------------------------|--------|----------|------------|-------------|
| ReAct（= ToolPro）            | 0.971  | 1.531    | 1.730      | 1.056       |
| AutoRPA 改写版                | 1.145  | 1.582    | 1.754      | 1.164       |
| PACE                          | 1.000  | 1.000    | 1.000      | 1.000       |

## 论文自带的对照说明了什么

**消融（日志，对各模型取平均）。** 去掉 savings test，成本上升 52.68%（\[48.25, 58.36\]%）；成功与失败尝试使用同一个成本，上升 23.34%（\[19.18, 28.06\]%）；eager retry 的成本是完整 PACE 的 3.303 到 4.922 倍。去掉预算后，日志上的平均成本只变化 0.0013%，但相对 ReAct 的最大测试比值从 1.2468 升到 1.7563，所以预算的作用是防止大幅亏损。在 4800 次网格运行和 120 次日志运行中，每个记录下来的成本比值都在 1.25 的界限以内。

**成本假设。** 把失败与成功编译成本之比取 0.5、1、2、5，日志上 PACE 相对 ReAct 的平均比值为 0.833 到 0.866。当高编译成本落在频繁出现、验证概率低的任务族上，平均值是 1.015，即比 ReAct 高约 1.5%，说明单看任务频率并不能决定什么时候编译。

**实时检查。** 另有一项在 OpenApps Calendar 应用上的研究，测试的是一个预先编译好的固定程序，不是在线算法：四个种子、三种界面条件，共十二对 agent/程序运行。agent 成功 7 次（4 次调用中断）；程序加 agent 回退成功 11 次。平均服务成本的区间：agent 为 8.142 到 21.590 milli-USD，程序路径为 1.202 到 4.564。

## 证据偏薄之处（用论文自己的话）

- “我们在开发 PACE 时使用了这些网格，因此这些比较不是独立的确认。”
- 日志只给出任务频率和到达顺序，不是真实的 GUI 任务；成本和结果是分配给各任务族的，策略还会拿到任务族标签和失败参数。
- 历史平均成本“不能提供成本保证所需的动作上界”。
- 实时研究只有四个种子簇和一个任务族；配对成本差的 95% 包络 \[-33.017, 4.621\] milli-USD 包含零。
- 延迟、设备占用和程序维护的工作量不在测量范围内；静默的程序失败和部分变化的界面还需要进一步评估。
