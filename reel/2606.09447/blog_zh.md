# AliyunConsoleAgent：用蒸馏加真实账号上的强化学习训练 32B 云控制台智能体

*CUA Radar 对 arXiv 2606.09447v1（Rong、Shen 等）的解读。本文是第三方对论文所报告内容的整理，并非作者背书。海报见 `poster.png`。论文：https://arxiv.org/abs/2606.09447v1 · 代码：https://github.com/AlibabaResearch/aliyun-console-agent*

## 问题：文档与控制台不断脱节

云控制台迭代很快，而描述它的文档由人工撰写。论文的场景叫 Execution-as-Verification：让智能体在真实控制台上端到端执行文档里的每个步骤，执行失败就提示文档存在缺陷。作者估计，保持文档更新每年需要约 400 万次重复巡检，每次约 1.6 小时人工，因此人工覆盖率低于 1%。他们已经用前沿闭源模型上线了一套生产系统，但单任务 API 成本（Gemini 3 Pro Preview 约 7 元）以及把控制台元数据发给外部服务的隐私风险，促使他们转向私有部署的 32B 模型。按作者的说法，RL 的难点在于云任务有很强的资源依赖：缺少前置资源（例如特定规格的 ECS 实例）会产生与智能体失误无法区分的失败，污染奖励信号。

## AliyunConsoleAgent 是什么

**智能体。** 这是面向阿里云控制台的 web agent。每一步的观察由 Set-of-Mark（SoM）标注截图、提取的 DOM 文本和动作历史组成。模型先写出显式的 Thought（ReAct 风格），再选择一个动作：通过 Playwright 在 headless Chromium 上执行的 GUI 操作（用 SoM id 定位元素而非像素坐标，因为控制台页面有数百个小元素）、`task_complete`、`task_unachievable`，或者按需供给动作——暂停 GUI 操作，调用 LLM 编码智能体 ResourceCoder，用 Terraform 或 Aliyun CLI 创建缺失的资源。一个流程按有序列表拆成子步骤，每个子步骤的交互预算为 40。在 CUA Radar 板上，其架构模式是 K12（可验证执行奖励）。

**Rollout 环境。** 四层：账号池（每个并发 rollout 一个独立账号）、基于阿里云 Kubernetes 服务的容器沙箱、离线的 Resource META 记录层（包含依赖描述、关键属性，以及创建、验证、销毁代码，已为 4,000+ 篇文档生成），以及运行时层——由 ResourceCoder 补足文档未写明的依赖。每个任务结束后，清理步骤把账号恢复到初始状态。

**训练。** 第一阶段对 Qwen3-VL-32B-Instruct 做全参数 SFT，约 160K 条单步样本、1 个 epoch，数据来自经过任务级和步骤级过滤的前沿模型蒸馏轨迹，以及自主探索。第二阶段是 GRPO，组大小 16，KL 惩罚用逐 token 的 MSE 形式，并做两层优势归一化。

**训练信号。** 双通道结果奖励。通道 1 查询阿里云的 API 审计日志 ActionTrail，用经领域专家核验的任务专属规则给出二值奖励。通道 2 用于没有决定性审计事件的任务：两个 LLM 评审必须一致，否则标记为 -1 并从训练中剔除。在 308 条专家标注轨迹上，双评审集成与人工判断的一致率为 96.7%，单模型为 91.9%。评测只使用规则通道。

## 论文报告的结果

以下均为在线端到端结果：12 个阿里云产品上的 278 个文档验证任务（76 个标准、202 个困难），由 ActionTrail 规则判定，评测中不使用 LLM 评审。每个任务运行 3 次。pass@1 为各次运行的均值（± 标准差）；pass@3 表示 3 次中任一次通过即算成功。所有模型使用同一套 rollout 环境。成本单位为元/任务。

| 模型 | 部署 | 成本 | pass@1 | pass@3 |
|----|----|----|----|----|
| Qwen3-VL-32B-Instruct（基座） | 私有 | 0.56 | 43.28 ± 0.50% | 60.79% |
| AliyunConsoleAgent-32B (SFT) | 私有 | 0.56 | 56.89 ± 0.83% | 72.66% |
| **AliyunConsoleAgent-32B (SFT+GRPO)** | 私有 | 0.56 | **63.52 ± 1.86%** | **75.18%** |
| Qwen3.6-Plus | 仅 API | 0.97 | 57.69 ± 1.50% | 72.66% |
| Kimi K2.6 | 仅 API | 2.70 | 60.79 ± 0.72% | 73.38% |
| Gemini 3 Pro Preview | 仅 API | 7.00 | 65.34 ± 2.15% | 79.86% |
| GPT-5.5 | 仅 API | 15.50 | 62.08 ± 2.00% | 76.09% |

论文写明：SFT+GRPO 模型的 pass@1 比基座高 20.24 个百分点，比 Gemini 3 Pro Preview 低 1.82 个百分点，成本低 92%。0.56 元对应 4 张 L20 GPU、0.4 QPS 的部署。按难度看（pass@3），该模型在标准任务上为 84.21%，困难任务上为 71.78%，Gemini 3 Pro Preview 分别为 88.16% 和 76.73%。

离线结果与上表分开：在 400 条单步样本的基准上（每个模型评测 3 次），SFT 后的 AliyunConsoleAgent-32B 为 92.75%，基座为 83.00%，Gemini 3 Pro Preview 为 95.25%。

## 论文自带的对照实验

**训练阶段。** 在 pass@1 上，SFT 比基座提升 13.61 个百分点，GRPO 在此基础上再提升 6.63 个百分点，GRPO 相对 SFT 的增益在配对 bootstrap 下 95% CI 为 \[2.97, 9.64\]。论文的训练消融（Table 5）只有这三行，不包含仅用 RL 的实验或加长 SFT 的对照。

**与前沿模型比较。** Gemini 与 GRPO 模型 pass@1 差距的配对 bootstrap 给出 95% CI \[-1.27, 7.39\]（p \> 0.05），作者据此称其“接近” Gemini 3 Pro Preview。在 pass@3 上，该模型为 75.18%，Gemini 3 Pro Preview 为 79.86%，GPT-5.5 为 76.09%。

**逐任务行为。** GRPO 之后没有任务从 3/3 退化到 0/3，有 9 个任务从 SFT 的持续失败变为 GRPO 成功（至少 2/3 通过）。作者描述了两种新获得的行为：构造前置条件（先开启自动续费，才能验证“关闭”操作），以及在文档中的按钮不存在时调整计划。

**环境本身。** 在 ECS 上，与在空账号上并行执行相比，加入资源供给后成功率从 33.81% 提升到 84.39%；10 个产品的交叉验证平均成功率为 80%。

**评审模型。** 双评审奖励集成在 308 条轨迹上与专家标注的一致率为 96.7%。

## 论文自己承认的薄弱处

- 留出只在文档层面：“no document URL appearing in SFT or RL rollouts is included in the benchmark”。训练中的自主探索从产品入口开始，论文没有说明产品层面的隔离。
- 预算是每个子步骤 40 次交互，即“effectively a dynamic max-turn limit”；论文没有给出前沿模型逐方法的步数对比。
- checkpoint 按每 5 步一次的验证选择，最佳为第 25 步，训练“exhibits non-monotonic oscillations”。
- 论文自己的错误分析把资源供给缺口列为最大的失败类别，且多为确定性失败，“reflecting Rollout Environment coverage gaps rather than agent errors”。局限包括静态 Terraform 模板会过时、SoM 依赖脆弱的 DOM 解析，以及基础设施开销。
- 生产审计（54,000+ 个流程，4,399 个确认缺陷）使用的是前沿模型；32B 模型仍在灰度测试。
