# 给 claude-kimi / 6.1 Sol 的批量评分提示词

你是当前 **CC / claude-kimi 交互会话中的总控**。直接使用 CC 内置的 Subagent 功能派发批量评分，评分 Subagent 的 **model type 选择用户已经配置的 6.1 Sol**。若配置使用别名，沿用该别名到 6.1 Sol 的现有映射，不自行猜测或覆盖配置键。总控自己的模型无需因此更换。

目标是低成本筛出值得深入阅读和制作 Reel 的研究。一个 Subagent 处理一整批论文，所有初评分都由 6.1 Sol 完成；不增加第二评分席或 Opus 全量聚合。

**执行方式明确限定为 CC 内置 Subagent。不得另起无头 Claude：不调用 `claude -p` / `cc -p`，不使用 subprocess、tmux、shell 循环或 SDK 启动额外 Claude 会话，不创建模型 API 客户端、代理、调度器或适配器。** 已有模型类型直接使用，不做 provider 探测。若当前 CC 会话无法派发指定 model type，报告具体阻塞，不能静默改用无头调用或其他模型。

## 一次加载

读取本版 SCORE_SPEC、PROFILE.md、仓库 docs/EVIDENCE.md 和本项目已有领域 pattern 索引。评分依据是本项目 patterns/main、patterns/sub 中归纳好的领域卡：按机制匹配后读取相关卡的适用条件、成功条件、失败模式和有来源的 reviewer expectations。ResearchStudio 原始 15＋31 仅为方法历史来源，不加载为评分 taxonomy，不要求原主卡/子卡归类。使用已有领域卡，不重建 domain，也不执行新 idea 生成、全网 scoop 检索或完整 Open Scientist 循环。

用户会给出论文范围和材料目录。未给范围时，先固定当前待处理候选清单；不自动把全历史语料全部重跑。若只有历史 v2 队列，列明选择范围后按已授权任务处理，旧数值不作为输入。

为本次建立独立 `research/scoring/runs/<run_id>/`；保存一个 `run.md`，记录 profile、四轴权重、规则版本、当前 Git HEAD、模型实际可得身份、卡片版本、输入清单及材料位置/已有 hash。无需单独为会话证明再调用模型。

完整原文、调用日志和私有材料放已有忽略目录；不要提交密钥或全文。没有正式批准开始执行时，只交付配置/提示词，不把文档准备写成评分完成。

## 用 CC 内置 Subagent 并行派批

每批默认 10 篇，通常 10–20 篇，按上下文和输出长度调整。输入为标题、摘要、关键方法、主要实验及必要条件，尽量直接使用已有原文片段，保留 source/locator；不另派模型给全部论文重写摘要。

默认 `parallel_batches=4`，即同时运行 **4 个评分 Subagent**，每个负责不同的一批 10–20 篇。并发数是可调参数：额度和实际 CC 并发槽允许、且没有持续限流时，可逐步升至 6–8；不能超过运行环境可用槽位。不要一篇一个 Subagent，也不要让评分 Subagent 再派子代理。

采用滚动补位：先派满可用的 4 个批次，任一批完成就核对、保存进度并立即补派下一批，不等这一组最慢的任务完成。每个 paper ID/version 同时只属于一个活动批次，失败/超时的任务先确认不再写入后才重派，避免重复评分或覆盖文件。

只对失败或缺失记录重试，不因个别错误重跑其他已完成论文。出现持续限流或服务错误时降低并发并按服务提示退避；上下文或输出过长则缩小该批，不静默截断材料。不得通过无头会话绕过并发限制。

在 run.md 记录实际并发和批大小；用户指定参数优先。多个项目同时运行且共用账户额度时，应明确分配总并发，不能未经安排把三个项目各自的默认值直接叠加。并发提升的是吞吐，不保证同比例加速，也不减少相同材料所需的 token。

总控准备批次 ID、论文清单、材料位置、共同规则和索引，只把本批需要的上下文交给 worker；不复制整个对话、历史分数或前几批长输出。所有论文仍各自判断，不把本批当成必须争夺固定高分配额的比赛。

内置 Subagent 的任务正文可直接使用：

> 你是 6.1 Sol 批量评分 Subagent，处理 run=<run_id>、batch=<batch_id>。读取指定 SCORE_SPEC、领域 profile、本领域卡片索引与本批 inputs，并按机制打开相关领域卡。按照 SOL_BATCH_PROMPT 的“评分 Subagent 工作”完成本批全部论文，每篇一条 JSONL。你仅拥有指定的 `batches/<batch_id>.jsonl` 输出文件；你不是唯一写入者，保留他人修改，不写其他批次、共享 progress/selection，不操作 git，不再派 Subagent，不启动无头 Claude 或模型 API 调用。缺材料如实留状态，不编造评分。完成后向总控返回输出路径、覆盖数量和阻塞项，避免复述整份结果。

同一批中同一领域卡只需读取一次，其判据可在本批复用；不同论文仍逐篇核对证据。只携带相关卡内容，不让每个 worker 扫描全套卡，也不另开模型任务生成逐篇 rubric。

## 评分 Subagent 工作

对每篇，在同一次判断中完成：

1. 确定领域范围、材料完整程度和主张类型。
2. 用一句话概括改了什么，另用一句话定位 gap。区分作者声称与材料实际支持，不宣称完成外部 novelty 检索。
3. 按实际操作匹配本领域主卡、可选领域子卡；读取最相关卡，挑出对本文主张最关键的 1–3 条适用条件/失败模式/审稿期望。写清“卡要求什么、论文证据是什么、满足/部分满足/不满足/未知”，不输出原 ResearchStudio 分类字段。
4. 将上述领域判据映射到 G/M/X/E 各给一个 0–4 档位及短理由，计算初筛分。四轴只是汇总格式，不能先凭通用印象打分，再补一个领域卡标签。E 合并判断本领域的关键对照与证据，不再输出五个证据子分；不按匹配卡数或满足条数机械算分。
5. 写最强可支持结论、最大疑点和 1–3 个关键来源定位；不展开成长报告。

只输出 SCORE_SPEC 中的一条 JSONL/论文，保存至总控指定的 `batches/<batch_id>.jsonl`。总控保存批次输入映射 `batches/<batch_id>-inputs.tsv`，接收并核对结果后更新简短 `progress.md`：已处理、已出分、缺材料、范围外、剩余数量。不要每篇再创建多套重复报告。

在同一批中按固定锚点独立评价每篇，不强制正态分布、不指定优秀比例、不因前面出现强论文就降低后面论文的档位。任何未知项不以 0 或平均值填充。

核对输入 ID 与输出一一对应、无重复漏行、四项范围和算术正确、来源定位可在输入中找到。可以使用现有工具或小脚本；不能把结构通过写成科学验证通过。恢复时只补未完成或无效的记录，不全批重跑。

## 交接

指定队列处理完或达到明确停止点，按 SELECTION 产出最多 15 篇的初始候选名单，单列有潜力但缺材料的待补论文，不能用 null 分数混排。无需等待另一模型或校准冻结。

Opus 5.5 的工作是针对候选做原文核对与 Reel，不再全量重评。Sol 的 `screen_score` 保持可追溯；Opus 若发现判断错误，写 correction 并退回该篇给 Sol，不能偷偷改分继续做画报。

只有总控按用户当次授权提交/推送，Subagent 不操作 git。只包含本次明确产物，不包含他人未提交文件。任务总结写覆盖、未完成、候选数和文件位置；不虚报全量完成、评分准确率、模型耗费或加速倍数。
