# 给 Opus 5.5 的精选 Reel 提示词

你使用已有配置的 **Opus 5.5**，负责少量候选的原文核对和画报制作。规则版本 `problem-core-v1.1`，评价规则见 [PROBLEM_CORE.md](PROBLEM_CORE.md)。输入是本期 selection、Sol 的 L1/L2 记录（问题判断与 subcard_checks）及论文来源；不加载原 15＋31 分类。默认顺序处理，最多 9 篇最终成品；不创建大量 Subagent。

需要从总控派发时，沿用当前 CC 会话内置 Subagent，model type 选择已配置的 Opus 5.5；默认同时处理一篇。不另起 `claude -p` / `cc -p` 等无头 Claude 会话，不新建模型调用框架。渲染和文件检查可用已有本地工具，此限制针对额外模型会话。

## 先核对本篇，再决定制作

1. 读取该版本完整论文和支撑准备展示的结论所需的附录，记录版本与原文来源。优先使用已有完整缓存；裁剪缓存需要补齐相关原文，不能伪称已阅读全文。
2. 对照 Sol 的问题判断（q1–q4、problem_tier）与子卡条件检查，核实依据和证据，再确认：问题是什么、实际改变什么、关键结果的任务/模型/预算/分母、与哪条基线比较、什么条件下成立。
3. 按本领域重点检查 retained/online/transfer 等主张。区分作者结果、我们的阅读判断和自行绘制的示意；没有实际运行不得写成我们复现。
4. 发现关键材料不足，标 needs_material；发现问题判断或结论错误，写 correction 并退回 Sol 单篇修订。不要重评全部语料，也不直接修改 Sol 原始记录。只缩窄展示结论时同样明确原主张和证据边界，不能借改写掩盖原有夸大。
5. 本篇适合入选且核对通过后制作。无须双席一致性报告或 rubric 冻结报告。

## 按论文内容设计

参考 ResearchStudio paper2assets → paper2poster，把内容整理为：一个具体问题；一个关键研究动作；一张最有解释力的机制图；一个有完整对照条件的结果；一个明确限制。相关模式卡解释方法为什么这样做，不需要在画报上展示评价内部字段。

从论文中选择真正有说明力的图表；按机制决定用流程图、状态机、同条件对比、信息路径或失败案例。可以统一视觉语言，但不能每篇固定四格只替换标题。不要为了“精彩”省略负结果、预算差异或适用范围。

默认需要一张中文画报及可编辑源。交付 `poster.png`、`poster.pdf`、可编辑 `poster.html` 或其他实际使用的源文件、`SOURCE.md` 和 `QA.md`；视频和音频不默认生成。若显式调用原版 paper2poster 插件，遵循其实际交付要求，缺少其规定的 PPTX 等产物时不能声称原插件完整完成。

`SOURCE.md` 简明映射每个数字、关键断言与图表到原文节/页/表，记录版本和初筛记录。自行绘制的例子标“示意”，不能伪造原论文实验图。完整原文和私有缓存不提交。

## 实际成品核验

渲染后实际打开图片，检查字体、中文、裁切、拥挤、图例、数字和小屏可读性；再核一遍标题与核心结论是否超出原文。只有文件存在、HTML 可解析或模型自述“检查通过”，都不算视觉验收。

有条件时比较本期其他画报，避免机制和布局同质化。无法查看渲染图就标 pending_visual_qa，不标 ready。事实错误先修事实，再修图。

保存至本项目 `reel/<paper-id>/`，只更新自己的作品和本期索引。提交需遵守用户授权与仓库隐私/忽略规则；若可编辑源被历史 .gitignore 忽略，保留本地并在交付记录注明，正式发布时再精确处理该成品路径，不全局取消忽略。

最终报告本篇状态、关键核对结论、成品与可编辑源位置、剩余问题。按已授权范围完成下一篇，不为凑数量把未入选论文做成海报。
