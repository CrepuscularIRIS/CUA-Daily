title: A Decade in a Day: Synthesizing Agent-Native Interfaces from Human-Oriented Software Evolution
source: https://arxiv.org/abs/2610.15765

§Abstract
Large language model agents are emerging as an important new class of users of desktop applications. However, existing desktop interfaces were designed for human end users or application developers, leaving agents to interpret visual controls or discover and compose low-level software operations. This mismatch can hinder even capable agents, yet it remains unclear what interface properties make desktop software easier for agents to use. To study this question, we treat software evolution as a natural source of interface variation and introduce DeskIF-Bench, a benchmark of 255 artifact-verified tasks across six desktop applications. By holding the task, agent, and verifier fixed while varying the software release, we measure how interface changes affect agent performance. Across two models and six applications, the newest release consistently outperforms the oldest. Trajectory analysis identifies three relevant interface properties: discoverability, granularity, and observability. Guided by these properties, we develop ANIS, a framework that synthesizes agent-native interfaces from the capabilities of installed applications. On an expanded evaluation of 368 tasks across eight applications, atomic interfaces improve success over native SDK use by 3.8 and 3.5 percentage points with DeepSeek V4 Flash and Claude Haiku 4.5, respectively, while reducing online token usage by approximately 73%. Goal-level commands further raise success to 74.5% and 67.4%, respectively.

§Introduction (from cached fulltext; cut at ~9000 chars)
Large language model (LLM) agents are emerging as a new class of users of desktop applications, performing tasks from document editing to image manipulation [ Bonatti et al., 2025 , Nayak et al., 2025 , Zhao et al., 2025 , Li et al., 2026 ] . This creates a new interface-design challenge for desktop applications. Desktop applications expose functionality through interfaces built for human end users and developers, not for LLM agents. Graphical user interfaces (GUIs) assume that users can visually locate controls and interpret continuous visual feedback. Software development kits (SDKs) assume that developers can search documentation, understand an object model, write code, and debug low-level calls [ Lu et al., 2025 , Song et al., 2025 ] . Agents therefore need to perform the work these interfaces expect of humans: repeatedly interpreting and grounding GUI controls or discovering and composing low-level SDK operations. Command-line interfaces (CLIs) offer a higher-level alternative through concise, structured, task-oriented commands [ De Masi, 2026 , Yang et al., 2026 ] , but most desktop applications expose no general-purpose CLI, and available CLIs often cover only a narrow subset of application functionality, such as import and export [ Wang et al., 2026 , Zhou et al., 2026 ] . Together, these limitations leave agents without a broadly applicable interface aligned with their capabilities. An interface mediates every action an agent takes on an application. If it neither exposes the capabilities required for a task nor allows them to be composed from available operations, even a capable agent cannot complete the task. A poorly aligned interface therefore becomes the Achilles’ heel of agents operating desktop software. This raises a fundamental question: What constitutes a good interface for agents interacting with desktop applications? Answering this question requires interface variations that are both realistic and controlled, yet hand-crafted variants would merely encode our own assumptions about what agents need. Our key observation is that software evolution has already produced such variations: across releases, an application’s core functionality remains largely stable while its interface is continually reshaped by developers responding to real usability pressure. Version history thus offers a ready-made natural experiment: by fixing the agent and tasks and varying only the historical interface, we can attribute performance shifts to documented interface changes. As a concrete illustration, Figure 1 compares two historical releases of QGIS, a geographic information system [ QGIS Development Team, 2026 ] , on the same task: creating a graduated map of country GDP with fixed-width intervals. In QGIS 3.10, the agent must derive eleven classes and assemble the renderer through a long chain of poorly documented low-level calls. The long chain invites parameter errors that the sparse SDK descriptions make hard to avoid or repair, and the agent fails after 33 turns and 662k input tokens. QGIS 3.44 instead offers clear SDK descriptions and a task-level QgsClassificationFixedInterval operation that generates the complete classification from a single interval width. The same agent succeeds in 11 turns with 36k input tokens. Clearer operation descriptions and a task-level abstraction make the interface more agent-friendly. To systematically understand what makes interfaces more agent-friendly, we build DeskIF-Bench ( Desktop Interface Benchmark ), a benchmark comprising 255 artifact-verified tasks across six applications and five domains. Holding the agent scaffold, backbone model, task setup, and artifact verifier fixed, we vary only the interface exposed to the agent across software releases. The results reveal that the newest release outperforms the oldest in all 12 model–application series, but by uneven margins. From QGIS 3.10 to 3.44, the success rate rises from 33% to 65% while mean SDK operations per task fall from 30.4 to 21.2. Impress gains 19 points, from 33% to 52%. Across applications, versions, and trajectories, our analysis identifies three recurring interface properties that help explain these performance differences (Section 4.3 ): • Discoverability : The interface makes supported operations discoverable at runtime and describes their semantics and arguments clearly enough for agents to understand how to invoke them. Poor discoverability forces agents to search documentation and probe live objects before they can act. • Granularity : The interface provides operations aligned with recurring user goals, reducing low-level calls. For example, QGIS 3.44 introduces task-level operations that reduce such overhead. • Observability : The interface exposes the resulting artifact state at the same level at which it is modified, so agents can verify whether the requested outcome has been achieved.
