title: How GUI Agents Fail: GraceBench for Execution Stability Diagnosis
source: https://arxiv.org/abs/2610.19900

§Abstract
As GUI agents are increasingly deployed for mobile task automation, their reliability depends not only on final task outcomes, but also on whether they reach these outcomes through stable interaction trajectories. In automation workflows, unnecessary actions, detours, and execution errors can add noise to collected data, introduce irreversible side effects, or undermine trust, even when the agent eventually completes the task. It is therefore important to systematically diagnose the execution stability, including whether an agent deviates from a feasible path, enters a loop, becomes stagnant, or recovers from unstable actions. Existing benchmarks, however, primarily assess final task success or a small set of intermediate milestones, leaving step-level execution behavior unclear. To bridge this gap, we introduce GraceBench, an online evaluation framework that represents the reachable interaction space of mobile applications as UI Transition Graphs (UTGs), providing a structural reference for step-level execution diagnosis. To support reliable alignment between dynamic UI observations and graph states, GraceBench uses video-grounded trajectory evaluation over this graph-aligned representation, assessing process stability beyond final success with metrics such as deviation rate, loop burden rate, and recovery ability. GraceBench contains 169 tasks spanning 10 applications and constructs 10 UTGs with 2,909 canonical GUI states and 3,116 observed transitions. Across 3,718 trajectories, GraceBench shows that outcome scores hide execution instability: GPT-5.6 Sol achieves the highest success rate (SR) but the lowest recovery ability, 51.24% of successful runs still contain a deviation or loop, and trajectories with the same success rate (SR) and completion rate (CR) can differ substantially in recovery behavior. Code and data will be released on https://iaie-physicalai.github.io/GraceBench.

§Introduction (from cached fulltext; cut at ~9000 chars)
Graphical user interface (GUI) agents are increasingly expected to operate real software environments on behalf of users ( Zhang et al., 2025 ) , from completing routine mobile tasks ( Rawles et al., 2025 ) to supporting software-testing data collection workflows. In such settings, an agent’s capability is not determined solely by whether it eventually reaches a target state; the execution process itself is equally important. This is especially true in GUI-based automated testing, where system performance, logs, resource usage, and behavioral signals are often collected along the execution trajectory. If an agent gets off track, repeats actions, or fails to recover, these path-dependent measurements become noisy and difficult to interpret, reproduce, and trust ( Dong et al., 2021 ) . Execution stability is therefore a key requirement for reliable GUI-agent deployment in real interactive environments. Existing GUI-agent benchmarks primarily evaluate task completion, usually by checking whether the final state satisfies a goal condition ( Rawles et al., 2025 ) . Although terminal success is useful, it offers little visibility into the stability of the execution process. Some recent work introduces intermediate milestones, such as essential states or subtasks, to measure staged progress ( Chai et al., 2026a ; Chen et al., 2025 ) , but such evaluation remains coarse-grained: it implicitly treats tasks as mostly linear and overlooks the effect of each action in a complex interactive environment. By checking only predefined semantic milestones, milestone-based evaluation cannot assess execution stability between them. As shown in Figure 1 , existing evaluation methods cannot distinguish whether a successful agent follows a stable path, deviates and recovers, or falls into a repeated loop before completion. Without step-level diagnostic signals, it is difficult to systematically understand execution instability in real GUI interactions. To address this gap, we introduce GraceBench , a benchmark for diagnosing the execution stability of GUI agents in real mobile applications. GraceBench uses UTGs to represent the finite reachable interaction space of an application as a graph. In a UTG, nodes correspond to GUI states and edges correspond to executable action transitions between states ( Yang et al., 2015 ; Wen et al., 2024 ) . This graph serves as a coordinate system for evaluating execution: nodes indicate where the agent is, edges indicate where the agent is moving, and the surrounding graph reveals what alternative interactions are available. GraceBench defines each task on a task-specific UTG subgraph and maps the recorded execution trajectory back onto this graph for step-level diagnosis. Because dynamic mobile UIs can change during and after an action, GraceBench uses synchronized video evidence to align observations with graph states and diagnose what happened between consecutive decisions. Based on this UTG representation, GraceBench evaluates GUI agents beyond final success. It contains 169 tasks across 10 applications and multiple domains, built on 10 UTGs with 2,909 canonical GUI states; each task’s matched states and their one-hop neighborhood cover 41.09 canonical GUI states on average, providing a local structural reference for step-level diagnosis. Each task is paired with concise and detailed instruction variants, allowing us to evaluate stability under both autonomous path planning and step-level execution guidance. Beyond success and completion rates, GraceBench reports deviation rate, loop burden rate, and recovery ability to evaluate the execution stability of GUI agents. We evaluate eleven models, including two GUI-specific models and nine general-purpose models, on all 169 tasks under two instruction conditions, yielding 3,718 trajectories. Instability drives GUI-agent failures and persists even behind successful outcomes. Across these trajectories, agents often fail through path deviation and looping, while 51.24% of successful trajectories still contain a deviation or loop. Even GPT-5.6 Sol, which achieves the highest success rate, has the lowest recovery ability on its observed recovery opportunities. Outcome-controlled comparisons further show that trajectories with the same success and completion outcomes can differ substantially in recovery behavior, indicating that final success alone can overestimate GUI-agent reliability.
