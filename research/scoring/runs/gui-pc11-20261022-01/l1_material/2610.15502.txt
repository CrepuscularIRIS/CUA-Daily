arxiv: 2610.15502 (2610.15502v1)
title: From Observations to Authorized Actions: Measuring Source Information in Android Agents
source: https://arxiv.org/abs/2610.15502

§Abstract
Android agents read content from applications and web pages and act on it with the user's authority, yet they cannot reliably tell where that content came from -- its source, the application or document that supplied it. The WebView accessibility fields we inspected expose the host application but omit the document origins available inside the browser, so an agent reading through this interface cannot check which document supplied an object; a limited reproduction on an unmodified WebView yields the same finding. We build and separately evaluate two prototypes to examine how source information supports authorization. Our application-source monitor withholds side-effecting calls whose signed source record contains an untrusted application. With the source set derived from the OS accessibility log, it blocked every selected attack write in the tested runs, but it also withheld benign sends issued after reading untrusted content, flagged benign tasks that use external content, and carried source records into a later clean task. Our WebView source-reference gate uses records from a modified browser to check object origins and reference lifetime through direct calls; in a separate 24-trial evaluation, the live agent selected no disallowed object. Supporting benchmark and planner measurements characterize textual argument matches and attacker-target selection, without establishing causal dataflow or a controlled model ranking. The prototypes are not an integrated defense: the WebView gate still lacks authenticated browser delivery and atomic capture of selected bytes and origin. Together, the results show which source information the tested policies need and why it must stay linked to the object used in execution.

§Introduction (from cached fulltext; cut at ~9000 chars)
An Android agent reads web pages, notifications, and application screens, then invokes functions with the user’s authority. A message recipient or body may come from this observed content rather than from the user’s request. In our prototypes, the agent invokes functions in another application through Android AppFunctions ( 4 ) . Caller authentication identifies the requesting application but does not establish the source of the content in the request. A message copied from an embedded advertisement and one supplied directly by the user can reach the same execution boundary under the same caller identity. System model. The agent observes application content through Android accessibility, including web content rendered in WebView; Android GUI agents commonly read the accessibility tree, often together with screenshots ( 25 , 26 , 27 ) . It acts through AppFunctions: the agent is the caller , the platform’s broker mediates the request, and the provider is the application that executes the function. Our experimental provider, ChatApp, stores messages in memory. We add source recording and execution checks to this path; Figure 1 shows where the two prototypes obtain their source information. Indirect prompt injection shows why observed content cannot automatically be treated as instructions ( 1 ) . Consider the policy “share only content selected from an approved source.” Enforcing it requires evidence beyond the planner’s claim: which source supplied the selected object, and whether the action uses that same object. Because a trusted host application can display untrusted content, trust in the host does not determine eligibility. We therefore distinguish whether a source is eligible from whether the user authorized the action, since an approved source does not authorize every recipient or operation. We organize the study around two questions. What can recent application history tell an execution check? What additional information is needed to check the origin of a selected web object? We implement an application-source monitor and a WebView source-reference gate to examine these questions separately. The latter uses a modified browser and simulated approval; its implementation status is specified in § 6.1 . Consider a host application displaying two embedded documents. A sharing policy permits a selected object from origin P but not an otherwise identical object from Q . The host package and selected bytes alone do not express that distinction. This illustrative case motivates our selected-object tests. The application-source monitor asks a different question—which applications the agent recently observed—so it is evaluated under a separate threat model and workload. Contributions. We make three contributions: (1) We measure an origin-attribution gap in the inspected WebView accessibility metadata, compare it with browser-side origin information, and reproduce the finding on a limited unmodified configuration (§ 4.1 ). (2) We implement and separately evaluate two authorization prototypes (§ 5 , § 6 ). One shows how application history can restrict benign tasks. The other tests origin checks on selected objects, but still lacks authenticated delivery and atomic capture of the object–origin binding. (3) We provide supporting measurements of argument matching and planner behavior that motivate checking actions independently of model-selected instructions (§ 4.2 , § 4.3 ). Argument matches are textual rather than causal, and the planner trials are exploratory rather than a controlled model ranking. The study concerns observation interfaces and execution checks. We do not pool the prototypes’ outcomes into one defense rate. Table 1 maps the measurements to the two prototypes. The WebView measurement motivates the selected-object case. The benchmark and planner measurements motivate checking individual actions independently of the planner. We present the application-level case first, then the selected-object case. Together, they illustrate why a check must identify the application or document required by its policy and link that identity to the object it executes on.
