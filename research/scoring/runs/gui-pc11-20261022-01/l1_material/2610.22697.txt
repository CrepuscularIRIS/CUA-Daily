title: What It Is, Not What It Says: Securing Agentic Browsing Interactions with Web Semantics
source: https://arxiv.org/abs/2610.22697

§Abstract
AI agents increasingly browse the web on users' behalf, yet they consume webpages as screenshots or text, exposing their LLMs to unvetted third-party content. Browsers enforce semantics under which what an element can do depends on what it is and where it comes from, not on what it says. Agents flatten these semantics, so injected text can persuade the LLM to exercise the user's authority for content that has none. As LLMs remain easy to persuade, the agent's interface to the web must itself ensure the integrity of what the agent reads, interprets, and does. We propose Intact, which runs on an unmodified browser. Intact builds GenTree, a bespoke representation that captures provenance and web semantics. Intact passes the page via GenTree to the LLM one element at a time, so the LLM decides on each element without any other element's text. Its harness executes each step only within the capabilities of the step's element and asks the user before acting on third-party content. On 1,270 real webpages, GenTree attributes 2.3x as many elements to third parties as the browser, which misattributes 58.7% of them to the first party. On 1,091 of these webpages with injected attacks, only 12.8% of attacks get through Intact's planner, each at most as a consent request, against 73.1% for a conventional planner. Isolation disrupts functionality on only 3.7% of tasks, and a parallel schedule could remove most of its added latency.

§Introduction (from cached fulltext; cut at ~9000 chars)
AI agents increasingly act on users’ behalf, and the web gives them an API to nearly every online service. Agentic browsers (e.g., Comet [ 1 ] , Claude in Chrome [ 2 ] , and Gemini in Chrome [ 3 ] ) and frameworks (e.g., Browser Use [ 4 ] ) read pages, click, fill forms, and navigate across sites, often within the user’s authenticated sessions. This reach carries a fundamental risk, as web content is unvetted. Pages are assembled at runtime by parties their operators neither control nor always know. Third parties appear on 92% of pages, and the median site among the top thousand includes 66 of them [ 5 ] . As third parties load further third parties, about half of websites render content they did not load themselves [ 6 ] . The web is accordingly among the largest attack surfaces in computing. Cross-site scripting has ranked among MITRE’s two most dangerous software weaknesses every year since 2020, and in 2025 SQL injection joined it at the top [ 7 ] . One would thus expect agents to interface with the web through carefully designed mechanisms. Instead, they simply consume a page as a screenshot or as text derived from its markup [ 8 , 4 ] , exposing the underlying LLM directly to unvetted content. LLMs are known to follow instructions embedded in such content, i.e., prompt injection [ 9 ] , and to fall for scams [ 10 ] . Model-level defenses reduce but do not eliminate either [ 11 , 12 , 13 ] , and OpenAI concedes that prompt injection, “much like scams and social engineering on the web, is unlikely to ever be fully ‘solved’ ” [ 14 ] . Such attacks are already manifesting in practice. Hidden instructions in Reddit posts and comments have led deployed agents to leak users’ one-time login codes and credit card numbers [ 15 , 16 ] , crafted links have made them exfiltrate email and calendar data [ 17 ] , injected page elements and pop-ups divert web agents at high rates [ 18 , 19 ] , and injections aimed at agents appear on live websites [ 20 , 21 ] . The key issue is that web markup was designed for rendering, not for agentic interfacing. Browsers invest considerable effort in enforcing its semantics. Each element has well-defined capabilities, and origins and frames bound what code from one party can do to another [ 22 , 23 , 24 ] . In the browser, what content can do thus depends on what it is and where it comes from, not on what it says. Screenshots and text serializations flatten these semantics, leaving natural-language text that affords the LLM neither meaning nor control. A <p> element cannot issue a network request, yet its text can cause one by persuading the agent, which then acts as a confused deputy [ 25 ] , exercising the user’s authority for content that has none. Considering the well-known limitations of LLMs, we argue that security cannot rest on the model’s judgment; the interface between the web and the agent must itself ensure integrity [ 26 , 27 ] . Input integrity requires knowing who created or modified each piece of content the agent reads. Processing integrity requires that no element lead the agent beyond what the element itself affords. Output integrity requires that every action, and the data flow it causes, be warranted by the user’s request and permitted by the web’s security boundaries. All three must hold with little loss of functionality. In this paper, we address this problem with Intact . Our key idea is to reuse the semantics that browsers already enforce and extend them with the provenance, capturing both in GenTree , a per-element representation of the page through which Intact mediates what the agent reads, interprets, and does. For input integrity, Intact attributes every DOM creation and modification to the responsible script [ 28 , 29 ] and taints what third parties create or modify. The browser does not make this distinction out of the box, because it attributes everything a third-party script creates in a page to the first-party context. For processing integrity, Intact introduces virtual isolation , which extends the browser’s enforcement of markup semantics to the agent without any change to the browser’s architecture. Intact passes content to the LLM one element at a time, so an element’s text never reaches the decision on another element, and each action the agent derives stays tied to the element it came from, whose properties Intact can then enforce. The <p> above thus cannot cause a request, whatever its text says. For output integrity, Intact controls each action based on the provenance, capabilities, effects, and security boundaries of the elements involved. These checks depend only on the page, so Intact can enforce them reliably. The user’s intent, however, is not encoded in the page, so Intact defers to the user for decisions that the page cannot settle, e.g., using a third-party booking widget that the task requires. ## III Threat Model
System Model. We consider an agent that autonomously interfaces with the web. The agent consists of an LLM and a harness, i.e., the code around the LLM. The harness gives the LLM a view of the page, e.g., its markup, and executes the LLM’s decisions, such as clicking elements, filling in forms, and navigating. Webpages combine first-party content with third-party scripts, advertisements, and embedded services, which may appear directly in the first-party document or in cross-origin frames. Third-party content may originate from arbitrary sources and is not known to the user or the first-party operator in advance. Attacker Capabilities and Goals. We assume a third-party attacker who controls some content on a page that the agent visits, but has no special access to the user, the agent, or the first-party origin. The attacker may control only content, e.g., a promotional note that an honest third party’s script relays into the first-party document. It may run code in its own cross-origin frame, e.g., an embedded payment form. The attacker’s content may be hidden from view and still reach the agent. The attacker may target an element of the first party or of another third party ( outbound attacks) or present its own elements as bait ( inbound attacks). We consider attacks that require the agent, i.e., attacks that the attacker cannot carry out with its own capabilities. A <p> element cannot carry out such an attack; a script can, unless it runs inside a cross-origin frame. We impose this condition because an attacker who can achieve its goal through its own scripts or content does not need the agent. Trust Relationships. We assume that the user, browser, and the agent harness are trustworthy and uncompromised. The LLM has no intent of its own to harm the user, but we do not trust its judgment. We assume that the attacker can persuade it to follow any instruction in the content that it reads, since model-level defenses reduce but do not eliminate prompt injection [ 11 , 12 , 13 ] . The LLM may also err without an attacker [ 41 , 47 ] . We assume an honest first party and trust what its own responses and scripts deliver. We treat as untrusted all content in third-party frames, every element that a third party’s script creates or modifies, and every write whose script cannot be identified. Our instrumentation runs in the page’s JavaScript environment, so we also assume that page scripts do not evade or tamper with it; moving the instrumentation into the browser would remove this assumption (§ VI ). Scope. Our goal is to prevent the attacker’s content from leading the agent to act beyond the user’s request, whether the content sits in the first-party document or in a cross-origin frame. Concretely, the attacker’s text may reach the decisions on its own elements but no decision on another element. Every step must stay within its element’s capabilities, and no step on a third-party element may execute without the user’s consent. We consider the webpage on which the agent plans, not attacks that span several pages. Out of scope. We do not seek to detect or eliminate prompt injection; we aim to constrain its effects when the agent encounters untrusted content. We also exclude attackers who control the first-party origin itself. We do not address availability: an attacker can make the agent fail a task, e.g., with a decoy that draws the planner away from the part of the page that the task needs (§ VI ).

## IV Intact: System Architecture
We propose Intact , an execution architecture for secure agentic web interfacing. Intact ’s main thesis is that the agent’s integrity depends on oversight of the LLM’s input, processing, and output, as the LLM itself remains unreliable. Intact bases this oversight on web semantics, i.e., on what each element is and where it comes from, not on what the element says. To oversee the input, Intact builds GenTree , a bespoke representation of the page that records, for each element, which party created or modified it and what it can do (§ IV-A ). To oversee the processing, Intact plans under virtual isolation (§ IV-B ). It shows the LLM one element of GenTree at a time instead of the whole page, so the LLM decides on each element without any other element’s text. The resulting plan carries little information beyond what the user asked for, yet it is directly actionable. To oversee the output, the harness (not the LLM) turns the plan into browser actions. It permits each step only within the capabilities of the element that the step names, and it asks the user before it acts on any third-party element. Figure 1 describes the execution flow in Intact . We implement Intact in Python on stock Chromium, which we drive through Playwright [ 35 ] and the Chrome DevTools Protocol (CDP) [ 36 ] . We release our source code at https://github.com/llm-platform-security/intact. IV-A GenTree Construction To control what the LLM reads and what its decisions can cause, Intact needs a representation of the page in which this control can be expressed. Agents currently reuse representations built for other consumers, namely screenshots, the DOM, and the accessibility tree, which lend no such control (§ II-B ). We create GenTree , which extends these generic representations with the semantics that Intact needs, so that each element carries what the harness requires to decide what that element’s content may cause. GenTree combines the DOM of every frame, the accessibility tree, and provenance into one record per element, which makes it a much richer representation than any of the three alone (Figure 2 ). Each record holds the element’s tag, attributes, direct text, and parent; the document it belongs to and whether that document is first- or third-party; its accessibility role and name, when the element is in the accessibility tree; its provenance, i.e., the script that created it, if any, and the parties that modified its attributes, text, or event listeners; and its capabilities. GenTree also keeps the elements that the accessibility tree omits, such as scripts, hidden inputs, and hidden subtrees, because their content can still reach an agent. As each record already carries the element’s provenance and capabilities, GenTree also provides extensibility for fine-grained access control that may encode user preferences over them. IV-A 1 Web Semantics Representation Provenance tells Intact who created or modified an element, but not what that element can do. GenTree thus also records each element’s capabilities under the web’s semantics, so that the harness can oversee the output. To that end, we create a taxonomy of capabilities along two axes, following the semantics that the HTML specification [ 22 ] and ARIA define for each element: (i) the interactions that the element affords an agent, e.g., click , type , and upload (ten in total), and (ii) the effects that these interactions can have in the browser, e.g., navigate , send-request , and dom-mutate (thirteen in total). Effects are limited to observable browser consequences; whether a request amounts to, say, a purchase is a judgment that we leave to a separate layer. We statically assign these labels from each element’s tag and attributes with 76 rules, grouped by element family such as links, forms, media, embedded content, and dialogs, and 14 composition rules then adjust them for the element’s ancestors, ARIA attributes, and computed style. For example, text inside a link inherits the link’s click , and a disabled button loses all its interactions. GenTree also records the channels through which an element’s content reaches the agent, e.g., its text, accessible name, or placeholder. The taxonomy further records whether each effect can be undone. A local change , such as dom-mutate , can be reverted; an external effect , such as send-request , cannot be recalled once it occurs; and an undetermined effect, such as submit or navigate , has consequences that the label alone does not settle (Appendix D lists the category of each effect). Typing into a field of the first-party document is a local change, or undetermined when the field sits in a form, since typing can submit the form. Typing into a field of a third party’s frame is an external effect, because that third party can read the value. Custom elements, whose behavior is defined by script rather than by the specification, cannot be labeled statically. GenTree exposes their text but grants them no interactions unless an ARIA role declares one, e.g., role="button" confers click ; the harness therefore does not act on them otherwise, which favors safety over functionality. IV-A 2 Browser Instrumentation GenTree ’s provenance requires knowing which script, if any, created each element and which scripts modified its attributes, text, or event listeners, but the DOM records neither. The browser attributes everything that a script writes into a document to that document’s origin, so content that a third-party script injects into the first-party page is indistinguishable from the site’s own, as with the button in Figure 2 . We therefore instrument the browser to attribute every DOM creation and modification to the responsible script, which lets GenTree separate what the site wrote from what a third party injected into it. Before the page loads, we use CDP to register a script that runs in every frame before the page’s own scripts, wraps the DOM interfaces through which scripts create, insert, and modify elements, and attributes each call to the running script, which it reads from the JavaScript call stack. Script Identity. We identify a script by its party, its URL, and the hash of its content, which CDP reports for every script that the JavaScript engine compiles, so that different scripts served from the same URL remain distinct. Code that has no URL of its own, i.e., code passed to eval or Function and inline scripts that another script inserts, would hide its origin from the call stack, so we give it a synthetic source URL that maps back to the script that created it; the functions it defines, including callbacks that run later, such as timers, thus stay attributed through any chain of such indirections. We strip the source URLs that page code declares so that one script cannot pose as another. A write whose script cannot be identified is marked as unattributed and treated as untrusted rather than as first-party. Coverage. For each element, the wrappers record the script that created it, the script that inserted it, and the parties that set its attributes or text or attached event listeners to it. Interfaces that build elements from HTML strings, such as innerHTML and document.write , do not return the elements that they create, so we collect these elements with a mutation observer that we read synchronously around the call. CDP’s network events attribute each third-party request to the script that initiated it.
