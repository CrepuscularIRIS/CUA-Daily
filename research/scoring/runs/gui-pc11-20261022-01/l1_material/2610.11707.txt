title: DeltaReplay: Task-Relative Memory Reuse for Mobile GUI Agents
source: https://arxiv.org/abs/2610.11707

§Abstract
Memory-augmented mobile GUI agents store successful execution trajectories and reuse them in later tasks, but a stored trajectory rarely matches a new task exactly. The new task may use different parameters, share only some of its steps with a stored trajectory, or have no relevant record in memory. Forcing the agent to use irrelevant memory can mislead it, whereas discarding memory that may still be useful deprives it of guidance from past experience. To address this dilemma, we propose DeltaReplay, a step-level memory reuse framework that decides how to use existing memory without modifying it. We observe that the reusable part of a stored record is determined not by the record itself but by its relation to the new task, mainly through two factors: page-level consistency and action-level generality. We therefore store execution trajectories as paths in a transition graph, whose nodes (pages) and edges (actions between pages) capture these two factors. At reuse time, the action on each edge is split into a task-independent operation and task-specific parameters. DeltaReplay then compares each recorded step with the new task and the current screen, and decides whether to follow it, execute it after replacing its parameters, or leave it to the base agent. On AndroidWorld and SPA-Bench, DeltaReplay improves the task success rate over a base agent with the same backbone by up to 10.3 and 25.0 percentage points, respectively. These results indicate that deciding at each step how to use retrieved memory lets agents benefit even from partially matching trajectories.

§Introduction (from cached fulltext; cut at ~9000 chars)
Mobile GUI agents built on multimodal large language models (MLLMs) read screens, follow natural-language instructions, and act through taps, text entry, and swipes ( Zhang et al., 2025 ; Wang et al., 2024 ; Hong et al., 2024 ; Qin et al., 2025 ) . Many of the tasks they receive recur: users file the same kind of expense, message the same contacts, and toggle the same settings. An agent that stores its successful runs can reuse them instead of reasoning from scratch, and a growing line of work equips GUI agents with trajectory, workflow, and graph memories for this purpose ( Wen et al., 2024 ; Lee et al., 2024 ; Wang et al., 2025b ; Chen et al., 2025b ; Xie et al., 2025 ; Zhong et al., 2026 ) . However, a stored trajectory rarely fits a new task exactly. The new task may use different parameters, such as another contact or amount, or share only some of its steps with the stored task, and frequent app updates can change the screens on which recorded actions were taken ( 42matters, 2026 ; McIlroy et al., 2016 ; Lu et al., 2025 ) . A retrieved step may therefore be executable as recorded, useful only after being re-grounded on the current screen, or not applicable at all, and each case calls for a different use: replay, re-ground, or discard. Retrieving the right memory is thus only the beginning of using it: the agent must still decide, at each step, which of these cases applies. Most memory-augmented GUI agents support only some of these uses, and fix them in advance (Table 1 ): some always add retrieved memory to the prompt ( Xie et al., 2025 ; Chen et al., 2025b ; Guan et al., 2025 ; Sun et al., 2026 ) , some choose only between executing a stored step and discarding it ( Jiang et al., 2025 ; Mi et al., 2026 ; Liu et al., 2025 ) , and some choose only between re-grounding and discarding ( Chai et al., 2026 ) . Each missing use causes a kind of loss. (i) Slow reuse: replayable steps are still reasoned through. Reasoning through a step is slow; GUI-explorer, for example, reports 66 s per step with GPT-4o ( Xie et al., 2025 ) . Yet agents that add memory to the prompt, or re-ground every step, do so even for steps that could be replayed as recorded. Replaying them saves this time: on AndroidWorld tasks whose exact goal is already in memory, our method replays about half of the steps and takes 9.3 s per step, against 19.0–32.2 s for prompting-based memory baselines (Section 5.3 ). (ii) Over-discarding: partly usable memory is dropped as a whole. Execute-or-discard agents check whether a record can be used before reusing it, for example by asking an LLM whether a shortcut’s preconditions hold ( Wang et al., 2025a ) or whether the record applies ( Jiang et al., 2025 ) , or by matching elements in the UI hierarchy ( Liu et al., 2025 ) ; a record that passes is executed as a whole, and one that fails is discarded as a whole. Yet a record often differs from the new task in only a few steps, for example in one typed value or one target label. For such a record, deciding on the whole record is wrong either way: accepting it executes the old parameters as recorded, and rejecting it also throws away the steps that could still be followed. In our experiments, records of the same template that differ from the task only in parameters solve 9.1% of the tasks when replayed verbatim, and ignoring them leaves the base agent at 63.6%, whereas following their matching steps and replacing only their parameters reaches 86.4% (Section 5.5 ). (iii) Misuse: inapplicable memory is still applied. LLM agents may reproduce retrieved experience even when it does not correspond to the current task ( Xiong et al., 2026 ) ; in an ablation of Darwinian Memory, searching memory with subtasks keyed by the task goal alone lowers AndroidWorld success to 29.7%, 11.3 percentage points below the 41.0% obtained without memory ( Mi et al., 2026 ) . In our experiments, when memory holds only other, weakly related tasks of the same app, adding retrieved records to the prompt lowers success from 39.6% to 25.0% (Section 5.3 ). These failures mostly share one cause: existing methods treat a memory as a whole, using or discarding it together, whereas reusability varies across the steps of the same memory. A record’s reusable steps depend on the new task and the current screen, so they can only be decided step by step at use time. We therefore present DeltaReplay, which makes the most of existing memory without modifying it and chooses among the three uses at every step (Figure 2 ). Route A (replay) executes the recorded step once a structural check confirms that the screen matches, the recorded target maps to a current element, and the step carries no parameters of the old task. Route B (re-ground) handles a step that applies but cannot be executed as recorded: it replaces the parameters the step carries from the old task with those of the current task (Figure 1 ).
