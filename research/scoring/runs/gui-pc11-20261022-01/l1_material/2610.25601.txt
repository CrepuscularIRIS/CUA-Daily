title: Step-Aligned Script Generation with Verification and Recovery for Web Automation Testing
source: https://arxiv.org/abs/2610.25601

§Abstract
Automated generation of end-to-end web tests remains costly: developers must identify stable selectors, encode multi-step workflows, attach assertions, and maintain scripts as interfaces evolve. Recent LLM-based web agents can complete natural-language tasks in a live browser session, but task completion is not the same as producing a test-ware artifact - code that is executable, replay-able from a reset state, inspectable by developers, and tied to an oracle. We present TESSARA, an adaptive test-script generation framework that converts natural-language test intent into Playwright scripts consisting of executable interaction code, goal-state assertions, and step-level provenance linking each step to its generated code fragment, selector evidence, execution outcome, and repair history. TESSARA grounds each planned step via Step-Aligned Scripting (SAS), enabling fine-grained failure localization, selective regeneration of failing suffixes, and reversibility-aware backtracking that avoids undoing likely commit points (e.g., form submissions). A three-level verification pipeline (syntactic, execution, and semantic/oracle), detects and repairs malformed code, interaction failures, and incorrect landing states. We evaluate TESSARA on three public web benchmarks, measuring script executability, oracle satisfaction, replay stability, and repair efficiency, and show substantial improvements over baselines and underlying VLMs used directly as script generators.

§Introduction (from cached fulltext; cut at ~9000 chars)
Web applications are central to modern software systems, and end-to-end (E2E) testing is a standard part of their quality-assurance pipeline. E2E tests encode user-visible requirements as executable browser interactions (logging in, searching, filling forms, navigating workflows) and are routinely run in CI/CD pipelines to catch regressions before release. Writing such tests, however, remains expensive and brittle: developers must manually identify stable UI elements, encode the interaction sequence, attach assertions that check the test actually validates the intended behavior, and revise scripts whenever dynamic interface behavior breaks them failures [ 1 ] . These costs are amplified in modern web applications, where dynamic DOMs, asynchronous loading, and non-standard widgets routinely invalidate scripts written against a snapshot of the UI. Frameworks such as Playwright [ 2 ] or Selenium [ 3 ] provide the execution substrate, but authoring and maintaining the scripts that run on them is still largely manual. A second challenge is handling failures in test scripts. In a testing environment, a failure when executing test scripts is diagnostic information about where a script is fragile and what needs to be repaired. Existing approaches to web interaction largely treat failures uniformly [ 4 ] . Retrying a step or regenerating an entire trajectory without attributing the failure to a specific action, selector, or assumption about the page state. For a testing tool, this is a missed opportunity. To elaborate, if a step in the script breaks because a selector changed, a developer (or an automated program repair tool) should be able to localize the fix to that step, inspect why it failed, and regenerate only the affected code fragment — preserving the rest of the script as a still-valid regression test. Treating the whole script as atomic discards exactly the information a maintainable test suite needs. We present Tessara , an adaptive test-script synthesis framework that converts natural-language testing intent into executable, replayable, and repairable Playwright tests. Given a testing goal, Tessara first decomposes it into a sequence of high-level interaction steps, then grounds each step into an executable code fragment via Step-Aligned Scripting (SAS), maintaining an explicit, persistent alignment between each semantic step and the code that implements it. This alignment is what makes the output a testing artifact rather than a transcript. It supports step-level failure localization, selective regeneration of only the failing suffix of a script (preserving validated prefix steps as reusable test fragments), and reversibility-aware backtracking that avoids undoing actions with likely durable side effects (e.g., form submissions, payments). To assess the correctness of a generated test script, Tessara applies a three-level verification pipeline. At the syntactic level, generated fragments are checked and repaired against compiler/runtime feedback before they are executed on the browser. At the execution level, each fragment is run, monitored and logged, so failures are attributed to the step that caused them rather than the script as a whole. At the semantic level, an oracle check evaluates whether the resulting page state is actually consistent with the testing intent. This addresses a failure specific to testing tools, where a script can execute without crashing yet land on the wrong page, producing a script that always ”passes” without succeeding. In summary, this paper makes the following contributions: (1) Tessara , a framework for generating executable web automation scripts from natural-language task descriptions via planning, step-aligned scripting, verification, and recovery. (2) Step-Aligned Scripting (SAS) , which aligns high-level action steps with executable code fragments, enabling stepwise verification, failure localization, and effective backtracking. (3) A structured verification and recovery, combining a 3-level stack (syntactic, semantic, and execution) with reversibility-aware backtracking to support targeted repair during script generation. (4) Empirical evaluation : to show Tessara ’s effectiveness in generating accurate and executable web test scripts.

## II Motivation
II-A Motivating Example In this section, we present a real-world example to motivate our solution. The testing intent is to use the Google Maps website (https://www.google.com/maps/) to answer the query: ”Find the difference in travel time by walking versus cycling from the Empire State Building to Central Park.” The goal is to generate a reproducible artifact in the form of a Playwright test script. This scenario exposes two fundamental challenges in automated test script generation. First , generating a stable, replayable test script requires a canonical, selector-grounded interaction sequence (one such sequence shown in Fig. 4 ). Existing approaches [ 5 , 6 ] are optimized for reaching a correct landing page by any viable path rather than producing a fixed, reproducible script. The action sequences these approaches produce compound the problem: natural-language descriptions (e.g., ”Click the Search button”) cannot be executed directly by Playwright or Selenium without an error-prone conversion step [ 6 ] . Pixel-coordinate representations [ 7 , 8 , 9 , 10 ] execute in a single session but break silently when the UI is updated or rendered across environments, with no indication of which step failed or what needs repair. Second , test scripts must not only be executable, but also satisfy the oracle. They must verify that the expected behavior occurred, rather than merely confirming that execution completed without crashing. Existing agents lack an explicit mechanism to verify that the final GUI state matches the expected behavior, and instead treat successful execution as a proxy for test correctness. Observation 1 . Automated test script generation requires selector-grounded, step-traceable, replayable interaction sequences. Action representations that are ambiguous or coordinate-dependent are insufficient for stable regression testing because they break silently under UI changes and provide no basis for localized repair. Motivation. To motivate our solution, we evaluated SeeAct [ 6 ] on the Google Maps testing task above. SeeAct uses GPT-4V with ReAct-style reasoning [ 11 ] to generate browser actions and executes them through Playwright, interleaving visual observation, reasoning, and UI interaction. On the first attempt, GPT-4V completed Steps 1 and 2 but fails at Step 3, as it doesn’t locate the ‘Directions’ button using only the DOM tree. After adding the screenshot (Fig. 2 ), it successfully completes Step 3. However, after entering ‘Central Park, New York,’ SeeAct misclicks the ‘Walking’ icon instead of the search icon, triggering alternative routes and making Step 6 (‘Note walking time…’) ambiguous. It then repeatedly fails to extract the walking time and eventually selects an incorrect button. Thus, SeeAct produces an artifact that would fail the oracle on every subsequent replay, with no way to identify which step introduced the error or repair only that suffix. Observation 2 . When an incorrect interaction corrupts the UI state mid-script, existing approaches have no mechanism for step-level failure localization or selective suffix repair. The entire script must be regenerated, discarding validated prefix steps and producing no diagnostic information about where the test is fragile. II-B Key Ideas Key Idea 1. [Step-Aligned Scripting for failure localization and adaptive script generation] Tessara supports failure localization and adaptive script generation through Chain-of-Thought (CoT) planning and Step-Aligned Scripting ( SAS ) with verification and backtracking. Step-level failure localization involves the ability to localize failures to specific reasoning steps. Tessara achieves this through stepwise verification, where each step in the generated plan is individually grounded and evaluated during execution. To enable this, Tessara first uses CoT prompting to generate a high-level sequence of interaction steps. It then applies SAS to translate the plan into a complete Playwright script while preserving an explicit alignment between each reasoning step and its corresponding code fragment. This alignment allows execution outcomes to be traced back to specific steps. During execution, Playwright interacts with the target application (e.g., Google Maps), and failures are localized to the corresponding step (e.g., Step 6 in Fig. 3). Stepwise verification further enables adaptive recovery. When a step repeatedly fails, Tessara backtracks to the most recent successful step and replans from that point using the task description, updated page state, and current URL. It regenerates only the remaining suffix of the plan and incrementally updates the script, preserving prior successful steps. Backtracking is invoked only for actions deemed reversible; otherwise, it falls back to full replanning. Key Idea 2. [3-tier verification and recovery to reduce full replanning] Tessara combines syntactic, execution-level, and semantic verification with reversibility-aware backtracking. This allows it to detect (and recover from) malformed code, failed interactions, and incorrect landing states. Key Idea 3. [Automated Test Script Generation] Tessara represents an action on a Web page as a 3-tuple of (l,e,a) (l: label, e: Web GUI element, a: operation) that can be automatically transformed into test scripts to support automated test script generation.
