title: From Seeing to Reporting: A Theory of Reliable Visual Set Generation in Vision-Language Models
source: https://arxiv.org/abs/2610.25503

§Abstract
Vision-language models (VLMs) are asked to report what they see: to count objects, box them, parse a screen or pick a click target (GUI grounding). We argue that reporting is part of the visual task, not merely its formatting. In a dense scene with 173 shapes, GPT-6.1 lists 173 records that match every shape, yet the counts it states in the same response sum to 188. From Seeing to Reporting (FSR) is a theory of visual reporting and a set of inference-time procedures that improve the reports of frozen VLMs. It models reporting as a chain from responses to decoded records, constructed sets and task answers, linked by task-compatible matching. The chain gives exact relations for deleting records, averaging their coordinates and switching readouts, and it splits the error of one answer chosen among several calls into missing candidates, lost representatives and wrong choices. These relations guide procedures for counting, detection, document layout, screen parsing and GUI grounding that use the task specification and a shipped configuration, without requiring labels from the target task. On 50 dense synthetic scenes, a one-call reporting-and-decoding protocol cuts per-type count error by 85.2% for GPT-6.1 and 98.8% for Claude Sonnet 5.5. On 600 ScreenSpot-Pro items, a GUI-grounding tier that combines three models lowers the miss rate from 13.67% for GPT-6.1's two-stage zoom to 9.33%, against 12.67% for three such zooms combined by a cluster vote at about the same cost. A plain vote over the same three models misses 12.33%: the other models supply the candidates, and selecting among them turns those candidates into fewer misses. We release the protocols, the stored responses and the analysis code.

§Introduction (from cached fulltext; cut at ~9000 chars)
Vision-language models are now asked to report a set of objects in an image: to count them, to box them, to parse every element of a screen, or to pick the one element a user means (GUI grounding: given a screenshot and an instruction, return the point to click). A typical answer has two parts. The first is a list : one entry per object, each giving a class name and a location (a point or a box). We call each entry a record . The second, when it is requested, is a stated count : the numbers the model writes for how many objects of each class it found. Code can also count the records in the list; we call that the list count . The two counts should agree. Often they do not. Figure 1 a shows one response of GPT-6.1 to a dense synthetic scene with 173 shapes of five classes. Its list has 173 records, and each record matches a different shape of the same class within 20 pixels, so the list is exact. In the same response, the model states counts that add up to 188. Across 50 such scenes, GPT-6.1 wrote an exact list in 20 scenes, and in 19 of them its stated counts were wrong. Sonnet 5.5 wrote an exact list in 39 scenes (after mapping its word “diamond” to the class “square”), and its stated counts were wrong in all 39. The response contains a correct enumeration; the model’s own summary of that enumeration is not faithful to it. Visual set reports are becoming the interface between perception models and the systems that use them: inventory counts, document layout, screen parsing for computer-use agents, click targets. Practitioners compensate with folklore: ask again, ask the model to check itself, overlay a grid, tell it not to miss anything, vote across models. Some of these help, some do nothing, and some make things worse. Without a model of where reporting errors come from, it is hard to predict which. Our thesis is that reporting is part of the visual task, not merely its formatting : what a model delivers depends on how it is asked to report, how the report is decoded and read, and how several reports are combined, and each of these steps can be analysed and improved. What we do. We describe reporting as a chain with four objects (Figure 2 ): a response , the raw text of one call to a model; the records decoded from it; a set of records built from one or more responses, for example by keeping only records that two calls agree on; and the task answer read from that set, such as a count per class or a click point. Three quantities connect the chain to every loss we study: the maximum number of records that can be paired one-to-one with true objects under the task’s matching rule, the number of records that are scored, and the rule that reads the answer. They give exact relations for what each operation does. Deleting unconfirmed records lowers the error exactly when the deletion loses fewer than one match per two scored records removed (with equal costs of the two error types), whichever model or view supplied the confirmation. Averaging the coordinates of agreeing records is a separate effect that can help or hurt. The chain takes reports as they come: from one call on the whole image, or from several views produced by an existing view planner such as tiling or zoom, whose merging and cross-view confirmation are constructions like any other. Alongside these relations we state a behavioural model, kept separate from them: each object has a persistent tendency to be reported or missed, partly shared across models. This analysis of what a model reports complements analyses of what a single call can see ( Shi et al., 2026 ) . Seeing and reporting. The title names the two things the chain separates. What a set of calls has seen is its coverage : the correct records or candidates present anywhere in the responses, in any field, view or model. What is reported is a selection from that coverage: which field is read, which records are kept, which point is output. The repairs in this paper add coverage, improve the selection, or, by averaging coordinates, move the records that are kept; on a fixed set of calls an operation helps exactly when, on what it changes, the errors it repairs outweigh the correct outputs it breaks, at the exchange rate the loss sets (Section 4 ). Reading the list instead of the stated count, and deleting unconfirmed records, change only the selection. A smaller view or a second model adds coverage, and a selection must then use it: on 600 click items, three models’ points with a plain vote have a miss rate not significantly different from that of three calls of one model, and choosing among the same points with a scorer and a comparison removes 18 more misses. Detecting and judging ask what the outputs alone reveal about a selection. Three problems, kept apart. Practice often treats three problems as one.
