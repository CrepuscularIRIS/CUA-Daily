title: Who Verifies the Agent's Success Claim? Self-Report Leakage in GUI-Agent Completion Judging
source: https://arxiv.org/abs/2610.29609

§Abstract
In automation pipelines, a GUI agent's confident success report can let downstream stages proceed even when the recorded execution trace does not show that the agent produced the requested outcome. We call this case a dangerous misreport: an unhedged success claim that the trace does not support as causal accomplishment during the run. We study report--trace auditing, which checks an agent's completion claim against an independently recorded trace. A controlled aware/blind intervention reveals self-report leakage: the agent's own self-report changes how completion is judged. The same judge reads the same task and trace; only that self-report is included or withheld. Withholding it improves trace-only dangerous-misreport recall by 43.4 percentage points with Qwen3.5-35B-A3B and 13.3 percentage points with DeepSeek-284B-A13B, with the same trend on held-out Batch 2. This motivates report isolation. The report records what the agent claims, but it must not influence the trace-state judgment. We implement this separation with a structured auditor that separates claim interpretation from claim-blind trace analysis and applies deterministic rules to extracted evidence. Because evidence extraction is separated from the policy that consumes it, the same audit record can be replayed under alternative policies without new model calls. The auditor achieves F1 0.75--0.78 on the 465-record audit-target set and 0.77--0.81 on held-out Batch 2, outperforming claim-aware and prompt-blind controls in recall and F1. Under audit-stage gating, where flag and review both block automatic pass, it blocks 74--90% of dangerous misreports at 45--56% inspection load, or 16--19% of the full in-scope stream after coarse status triage.

§Introduction (from cached fulltext; cut at ~9000 chars)
LLM-driven GUI agents are increasingly used inside mobile testing and regression workflows [ 1 , 2 , 3 , 4 ] , where task outcomes may be consumed by downstream harnesses or review pipelines. Consider a run that ends with “Done—the duplicates were removed.” The harness records the task as pass , downstream stages proceed, and the resulting device state enters the pipeline as if the requested operation had succeeded. But the trace may show a different execution: the agent inspected an empty list, acted on the wrong screen, or failed to save the requested change. No exception is thrown. The failure remains silent because the agent under audit supplies its own success report. We study report–trace auditing. Given a completed run, the agent reports completion and the audit checks whether the independently recorded trace supports that report. A dangerous misreport occurs when the report claims success but the trace does not show causal accomplishment, meaning that it does not show the agent itself producing the task-relevant outcome during the run. Final-screen compatibility alone is insufficient, because pre-existing goal states, empty target lists, proxy screens, and unsaved edits can all make a failed run appear successful [ 5 , 6 ] . Such cases are dangerous because they can be recorded as silent false pass outcomes. Claim-aware completion judging creates a circular evaluation path in GUI-agent evaluation. Because task-specific success checks are costly to author across heterogeneous GUI tasks and human trajectory review is costly, recent agent-evaluation work increasingly uses LLM or agent judges for trajectory success [ 7 , 8 , 9 , 10 ] . A common pattern is to ask the judge to read the task, the execution trace, and the agent’s final report in a single prompt, then decide whether the task was completed [ 11 , 12 , 13 , 10 , 14 ] . The report thereby ceases to be merely a claim to be verified and instead becomes part of the evidence for its own truth, making the evaluation path circular. We quantify this circularity with an aware / blind intervention. The same completion judge reads the same task and trace; only the agent’s self-report is included or withheld. If the self-report were harmless context, the trace-state judgment would remain stable. It does not. Withholding it raises trace-only dangerous-misreport recall by 43.4 percentage points with Qwen3.5-35B-A3B and 13.3 percentage points with DeepSeek-284B-A13B on the combined audit-target set, and the held-out Batch 2 split shows the same trend. Exposing the self-report shifts trace judging toward completion and suppresses dangerous-misreport recall. These results make report isolation a design requirement: the report records what the agent claims, but it must not shape the judgment of the trace. Report isolation alone is not sufficient. We therefore build a report-isolated evidence–policy auditor. A prompt-blind judge withholds the report, but it still returns an opaque verdict that is difficult to inspect or reuse under a different completion policy. Our auditor instead separates the problem into evidence extraction and policy enforcement. One component reads the report to identify the claim; a second reads only the task and trace to extract typed evidence of accomplishment. Neither decides completion directly. Deterministic rules consume the extracted evidence and assign each run to pass , flag , or review . This evidence–policy boundary also makes the audit replayable: cached evidence can be evaluated under alternative policies without another model call [ 15 , 16 ] . The output is not a prompt-level verdict but a software audit record whose evidence fields and policy decisions can be inspected, regression-tested, and replayed. We evaluate this auditor on 465 audit-stage records drawn from 1,384 in-scope GUI-agent execution attempts, including 180 dangerous misreports. On the full audit-target set, the auditor achieves F1 0.75–0.78, and on held-out Batch 2 it reaches 0.77–0.81, outperforming claim-aware and prompt-blind controls in recall and F1. Under audit-stage gating, where both flag and review block automatic pass, it blocks 74–90% of dangerous misreports from automatic pass at 45–56% inspection load within this audit-target set. This paper makes three contributions: 1. We quantify self-report leakage in GUI-agent completion judging. Holding the task, trace, model, serialization, and scoring rule fixed, exposing the agent’s self-report shifts trace-state judgments toward completion and suppresses dangerous-misreport recall. The result makes report isolation an empirical design constraint rather than an optional prompt choice. 2. We define dangerous misreporting by separating the report from trace evidence. The formulation separates what the agent claims from what the trace supports. Claim intent is labeled from the report alone, while causal accomplishment is labeled from the task and trace alone. ## II Problem Formulation
This section formalizes report–trace auditing for a completed GUI-agent run. The formulation separates three questions that one-shot claim-aware judging often conflates: what the agent claims, what the trace supports, and whether the claim is consistent with the trace. II-A Audit-Target Runs and Completion Construct We study post-hoc auditing of a GUI-agent run u=(x,\tau,m), where x is the natural-language task, \tau is the recorded execution trace, and m is the agent’s final report. In this section, m denotes only the final report. More broadly, we use self-report for the agent’s own assertions about its progress, which occur at two granularities: the final report m , a single end-of-run completion assertion, and per-step self-reports , one short completion or progress claim the agent emits after each recorded step (e.g., “deleted recipe X”). Per-step self-reports are agent-authored claims—not chain-of-thought reasoning, and not part of the recorded GUI states in \tau —stating what the agent asserts it did, not why it acted. The final report m is the sole source of the claim-intent label c^{*} introduced below; per-step self-reports never assign c^{*} and enter the analysis only as additional agent-authored context in the aware condition (Section V-A ). The final report is the claim source, while the trace is the independent evidence source. Since the report is produced by the same agent whose execution is under audit, it conveys what the agent claims. The trace, by contrast, supplies independent evidence of whether the claimed accomplishment occurred. We model the trace as \tau=\langle s_{0},s_{1},\ldots,s_{n}\rangle, where s_{i} denotes the observable GUI state after the i -th recorded step. Each state contains GUI information such as visible text, content descriptions, resource identifiers, and bounds. The auditor operates offline from a completed trace, without access to a live device or an executable task-specific oracle, unlike benchmarks that provide environment checkers [ 17 , 18 , 19 , 20 ] . A GUI task can be judged complete under different semantics, including final-state satisfaction, causal accomplishment, and report faithfulness. We use causal accomplishment as an audit construct: the trace must show evidence that the agent performed a task-relevant action and reached the requested post-condition during the run, rather than merely ending in a compatible state. A goal state already present at s_{0} , an empty target list, or a typed but unsaved value is therefore not by itself evidence that the agent accomplished the task. Let y^{*}(x,\tau)\in\{\text{{completed}},\text{{not\_completed}},\text{{unsure}}\} denote the human gold completion judgment under this causal-accomplishment policy. It is assigned based on the task and trace without revealing the final report to annotators. II-B Claim Intent, Trace Support, and Positive Class A report–trace auditor separates claim interpretation from trace-state estimation. The claim-intent function C(m)\in\{\text{{success}},\text{{failure\_or\_incomplete}},\text{{unclear}}\} captures what the agent says, not whether the claim is true; failure_or_incomplete denotes failure or incompletion. The trace-state function T(x,\tau)\in\{\text{{completed}},\text{{not\_completed}},\text{{unknown}}\} returns what the trace supports under the audit policy. A valid auditor must keep this trace-state estimate claim-blind: the input to the trace-state estimator excludes m , so changing the final report may change C(m) , but cannot change T(x,\tau) . This information-flow requirement is the key difference between report–trace auditing and one-shot claim-aware judging. The ground truth is defined over two independently annotated axes. The claim label c^{*}\in\{\text{{success}},\text{{failure\_or\_incomplete}},\text{{unclear}}\} is derived from the final report alone, while the actual-completion label y^{*} is derived from the task and trace alone, under the claim-blind causal-accomplishment policy. A record is a dangerous misreport iff c^{*}=\text{{success}}\quad\wedge\quad y^{*}=\text{{not\_completed}}. This is the positive class for evaluation: a failed execution risks being misclassified as pass because the agent reports success. Self-reported failures, where the report also indicates failure or incompletion, are not dangerous misreports because they do not create a silent false pass. The reverse inconsistency, where the report indicates failure or incompletion but the trace supports completion, may matter operationally as an underclaim, but it is not the positive class studied here. The implemented detector predicts a dangerous misreport iff \displaystyle\widehat{d}(x,\tau,m)=1\;\Longleftrightarrow \displaystyle C(m)=\text{{success}} \displaystyle\wedge\;T(x,\tau)=\text{{not\_completed}}. Labels and predictions are not circularly dependent: gold positives use human labels c^{*} and y^{*} , while predictions use the implemented pipeline. Because prediction depends on C(m) , Section V also reports a gold-claim condition that replaces C(m) with c^{*} to isolate trace-channel behavior. II-C Audit Disposition and Evaluation Views The auditor returns a disposition A(C,T)\in\{\text{{pass}},\text{{flag}},\text{{review}}\}. The overclaim case corresponds to a dangerous misreport: C(m)=\text{{success}}\;\wedge\;T(x,\tau)=\text{{not\_completed}}\;\Rightarrow\;\text{{flag}}. Uncertainty in either channel routes the record to review ; agreement between the claim channel and checked trace state routes it to pass . Here pass is an audit disposition: it means that the report–trace consistency check does not flag the run as a dangerous misreport, not that the underlying GUI task is necessarily completed. We report two evaluation views. In the automatic-detection view, only flag counts as a positive prediction and review counts as a non-detection. In the deployment-gating view— audit-stage gating —both flag and review block automatic pass, because uncertain runs should not be silently accepted by an automation pipeline.
