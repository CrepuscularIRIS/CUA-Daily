title: TeleGen: Improving LLM-Based Web Application Generation via Runtime Telemetry
source: https://arxiv.org/abs/2610.04981

§Abstract
Large language models can generate runnable web applications from natural-language requirements, but many generated applications still fail interactive tasks. Existing generate-execute-repair pipelines execute the generated application and use task outcomes or error messages to guide code revision. However, this feedback often misses the runtime behavior between a browser action and the final task outcome, making interaction-level failures difficult to diagnose. Therefore, we propose TeleGen, an observability-enhanced framework for LLM-based web application generation. TeleGen instruments generated applications, collects runtime telemetry during task execution, and compresses raw telemetry logs into concise briefs for repair. We evaluate TeleGen on WebGen-Bench and Web-Bench. On WebGen-Bench, TeleGen improves task success from 67.7% with repair without telemetry to 76.2%, an increase of 8.5 percentage points. On Web-Bench, it improves cumulative Pass@2 from 21.7% to 29.8%. Ablation results show that runtime telemetry provides a useful diagnostic signal, while telemetry briefs make this signal more effective and less costly to use. Further analysis shows that telemetry is especially helpful for failures involving hidden execution paths, such as navigation, form workflows, and frontend-backend coordination.

§Introduction (from cached fulltext; cut at ~9000 chars)
Large language models (LLMs) have made substantial progress in code generation ( Chen et al., 2021 ; Austin et al., 2021 ; Jiang et al., 2026 ; Hui et al., 2024 ) , moving from standalone programming problems ( Hendrycks et al., 2021 ; Li et al., 2022b ; Jain et al., 2025 ; Liu et al., 2023 ) to repository-level tasks ( Liu et al., 2024b ; Zhang et al., 2023 ; Jimenez et al., 2023 ; Wang et al., 2025 ) . Within web code generation, the task has similarly shifted from producing static webpages to building interactive web applications from requirements expressed in natural language, screenshots, or domain-specific languages ( Lu et al., 2025a ; Xiao et al., 2025 ; Li et al., 2026 ; Yang et al., 2026 ; Wan et al., 2025a ; Dang et al., 2025 ) . Static web page generation asks a model to translate a visual design or screenshot into HTML/CSS that reproduces the intended layout and appearance ( Si et al., 2025 ; Wan et al., 2025b ) . Interactive web application generation goes further: the model must produce runnable website code from a high-level natural-language requirement, implementing user-facing workflows such as search, navigation, and form submission ( Xiao et al., 2025 ) . Correctness therefore depends not only on the rendered appearance or individual code fragments, but also on whether user interactions trigger the right frontend logic, state updates, and backend behavior during execution ( Mesbah et al., 2012a ) . To improve the quality of generated code, recent work adopts a generate-execute-repair workflow ( Lu et al., 2025b ) . After generating an initial application, an execution step exercises its behavior by performing user-oriented tasks, either through browser agents that interact with the application in realistic web environments ( Deng et al., 2023 ; Zhou et al., 2024 ; He et al., 2024 ; Koh et al., 2024 ) or through end-to-end testing frameworks that programmatically verify behavior against expected outcomes Zhang et al. (2025) ; Teoh et al. (2026) ; Chevrot et al. (2025) . This step exposes failures that the source code alone does not reveal, such as a button that does not trigger its handler ( Artzi et al., 2011 ) , or a form submission that does not update the interface ( Mesbah et al., 2012b ) . When execution reveals a task failure, the repair agent ( Pabba et al., 2025 ; Maddila et al., 2025 ; Xia et al., 2023 ) receives the feedback and revises the generated code. While effective, this feedback is often incomplete for interactive web applications: interaction-based execution can reveal that a generated application fails a task, but it can miss critical information that is not captured through the visible UI layer alone ( Alimadadi et al., 2016 ) . As a result, the feedback that reaches the repair agent ( Fan et al., 2023 ; Bouzenia et al., 2025 ) is typically limited to task-level pass/fail outcomes or surface-level error messages. For example, after a browser agent clicks a button, the available feedback may not show if the click reached the intended event handler, sent a request, received the expected backend response, or the application state changed but was not rendered ( Jr. et al., 2017 ) . From the outside, these failures may look similar as the expected result was not reached. For repair, however, they point to different defects and require different code changes ( Jr. et al., 2016 ) . This gap motivates our central question: can making generated applications more observable during execution provide better runtime evidence for repair? To answer it, we add an observability step before repair. Drawing on the use of observability to diagnose complex software systems ( Li et al., 2022a ; Li et al., 2021 ) , we instrument the generated application with lightweight logging mechanisms and record its runtime behavior while the browser agent executes each task. The resulting runtime telemetry ( Barik et al., 2016 ) captures interaction events, runtime errors, state changes, and other task-relevant execution signals. Rather than passing the raw telemetry logs directly to the repair agent, we employ a separate agent to compress them into a telemetry brief. Raw logs often contain duplicated messages ( Li et al., 2019 ; Li et al., 2022c ) , framework noise, and other low-level details that can obscure the evidence relevant to a failed task ( Locke et al., 2022 ) . They are also lengthy, increasing the context size and cost of each repair attempt ( Liu et al., 2024a ) . The telemetry brief is designed to preserve concise diagnostic evidence while avoiding the noise and cost of long execution logs. We evaluate our approach on two web code-generation benchmarks, WebGen-Bench ( Lu et al., 2025b ) and Web-Bench Xu et al. (2025) , covering both full web application generation and sequential web-development tasks.
