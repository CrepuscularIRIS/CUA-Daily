title: Understanding Tool-Mediated Interaction Failures in Agentic GUI Software: An Empirical Study
source: https://arxiv.org/abs/2610.31698

§Abstract
Large language model (LLM) agents increasingly complete tasks through live graphical user interfaces (GUIs). Because the model cannot directly operate the GUI, these systems often rely on tools to capture screenshots or UI trees, translate model outputs into GUI actions, and report whether the interface changed. We study failures where this tool-mediated interaction makes the agent's view of the task diverge from the live GUI. We construct Malva, a defect library with 335 confirmed real-world failures from 40 open-source applications. These failures fall into 11 defect patterns rooted in state representation, state transition, and synchronization problems. They are widespread: 90% of the studied applications contain more than one defect type. They are also often silent: incorrectness appears in 86.6% of failures, including 119 cases that produce wrong behavior without a fail-stop signal. We operationalize this taxonomy with MalvaGuard, a pre-deployment static contract checker that reaches 57.3% precision and 76.8% recall on an additional 20-application corpus.

I-A Motivation With the rapid advancement of large language models (LLMs), an increasing number of software systems pair an LLM agent with tools that observe and operate existing graphical user interfaces (GUIs), including web browsers [ 1 ] , desktop applications [ 2 , 3 ] , and mobile applications [ 4 ] , without relying solely on programmatic APIs [ 5 , 6 , 7 ] . This paper refers to these systems as agentic GUI software [ 8 , 9 , 10 ] . In the past 12 months, over 3,000 open-source applications have emerged on GitHub, along with around 30 commercial products launched by leading tech companies ( e.g. , Anthropic [ 11 ] ). At runtime, tools in these systems often capture GUI state from screenshots or UI trees, and the LLM plans the next step. Tools then execute actions such as clicks or typing and report the resulting environment feedback back to the agent [ 12 ] . While promising, this tool-mediated process introduces a reliability problem: the agent’s view of the task can silently diverge from the live GUI [ 6 ] . Such divergence matters because these agents are moving into real digital workflows, including enterprise dashboards, customer-support portals, office productivity tools, online transactions, and mobile services [ 1 , 2 , 11 ] . In these settings, a tool misrouting a click can submit the wrong form, a stale screenshot can trigger redundant transactions, and premature success feedback can leave critical tasks silently incomplete [ 6 ] , resulting in financial loss, data corruption, or irreversible errors that are hard to detect and recover from. To illustrate such defects, consider a real scenario where the vision-language desktop application UI-TARS-desktop [ 13 ] sends messages via WhatsApp [ 14 ] . As shown in Figure 1 , when a user instructs the agent to send a greeting, the agent minimizes its main interface and keeps a small transparent status window on top of the desktop. The type tool succeeds because the text field remains unobstructed. The next click tool, however, is issued for the send button at the perceived coordinates, while the OS routes the event to the agent’s own overlay instead, and the message is never sent. The failure exposes a missing check: the tool exposes visual coordinates without verifying which window holds focus. This failure is not isolated, developers of agentic GUI software face three reliability challenges: Challenge-1: Partial GUI observations. Developers often need agents to operate applications without programmable interfaces, relying instead on tools that read screenshots or UI trees [ 15 , 8 ] . These tools expose only a slice of the live interface: elements may be obscured, off-screen, omitted from the UI tree, or visually present but not actionable. As a result, the agent may plan from an incomplete view of the target state. Challenge-2: Weak action boundaries. Developers expose large action spaces so agents can handle diverse tasks, but they rarely specify each tool’s operational boundary, including accepted parameters, required GUI preconditions, expected return format, or when to stop, retry, or escalate [ 16 ] . This leaves the tool loop unable to determine whether the next step is valid, leading to malformed calls, non-progressing retries, context overflow, or actions that target the wrong element. Challenge-3: Delayed tool feedback. LLM inference, GUI rendering, and tool execution run at different speeds [ 17 ] . After an action is executed, transient GUI changes, backend timeouts, or expired resource handles can cause reported tool status to diverge from the actual live interface state before the next observation begins. Despite extensive work on GUI automation and LLM agents, the tools that connect agents to live GUI environments have received little attention. Empirical work studied defects in traditional software [ 18 , 19 ] , ML-enabled systems [ 20 , 21 , 22 , 23 ] , and LLM integrations [ 24 , 25 ] . Traditional GUI automation treats automation code as test infrastructure, through scripted, model-based, and AI-assisted approaches [ 26 , 27 , 28 ] , while GUI-agent studies evaluate task completion across web [ 5 , 29 ] , OS [ 6 ] , and mobile [ 30 ] settings, and frameworks such as OpenClaw [ 3 ] propose architectural designs. Across all these lines, prior work either treats the tool layer as invisible infrastructure or focuses on model and agent behavior, overlooking the tools that mediate between the agent and the environment. This paper fills this gap by systematically studying how such tools introduce failures in agentic GUI software. ## III Study Methodology
Since no prior work has systematically studied failures at the tool-mediated boundary in agentic GUI software, we construct Malva , a defect library of confirmed failures, from scratch. As summarized in Figure 3 , we follow four procedures, each described in detail below: III-A Application Selection We select 40 open-source agentic GUI applications from GitHub, using their latest versions as of January 1 st , 2026 . We first use the GitHub Search API [ 38 ] to collect about 500 repositories of agentic GUI software using keywords that cover major platforms and agent types, such as “GUI agent”, “web agent”, “desktop agent”, “mobile agent”, and “computer use agent”. After removing duplicates and inactive forks, we keep repositories that meet three criteria: 1. the repository implements an executable agent loop for real-world tasks, not a toy demo or thin API wrapper; 2. the implementation contains concrete observation and action tools for GUI interaction; 3. the repository contains enough implementation and issue evidence to support defect analysis. We further review around 200 repositories from the same GitHub search space, but find no major differences from the existing corpus. We therefore stop the collection. The applications target three environments, as shown in Table I : 40% are web agents that browse and complete online tasks, 43% are desktop agents that use mouse and keyboard simulation to operate software and manage files, and 18% are mobile agents that use swipes and taps to operate phone applications. Most are written in Python (68%) or TypeScript (25%), with the rest using other languages. For reasoning, 60% use cloud APIs, mainly GPT [ 39 ] , 8% use local models, mainly LLaMA [ 40 ] , and 33% support both. For GUI observation, 58% rely only on screenshots, 15% rely only on structural UI representations such as DOM trees, and 27% combine both. Their primary grounding mechanisms also vary: 38% use direct screenshot-to-coordinate VLM grounding [ 41 ] , 15% add detectors, OCR, or grounding modules, 23% rely on accessibility or UI-tree structures, and 25% use DOM/XPath, browser-structural, or task-specific grounding. The applications average 71,687 lines of code, with a median of 24,978 and an interquartile range from 2,910 to 57,146. They have 226 commits on average, a median of 438 stars, and a maximum of 19,330 stars. In addition, 63% are less than one year old, reflecting how quickly the field is changing. Among desktop and mobile agents, 96% support workflows across multiple applications, while 4% focus on a single application. III-C Task Execution To collect evidence for candidate reports, we first inspect the issue status: 104 are closed issues, and 104 are open issues. • Closed issues : we examine discussions, linked pull requests, and commits to identify the failure scenario that developers acknowledged or fixed. • Open issues : we reproduce the failure directly when the required environment and credentials are available. Through this process, we derive 62 executable tasks from the open issue scenarios, since multiple issues often describe the same scenario. For each open issue, we identify the user goal, required environment state, and expected outcome. Each task specifies an initial state, an agent instruction, and a success oracle such as a UI change or system confirmation, instantiated under 14 environment-specific scenarios. The tasks span web, desktop, and mobile agents, with 35, 14, and 13 tasks respectively, and range from simple actions such as clicking or text entry to multi-step planning such as booking flights or configuring a system. To account for non-determinism, we run each of the 62 tasks 20 times with a 3-minute timeout per run [ 5 ] , yielding 1,240 task runs. Each run involves multiple agent-environment interactions, and automated logging records visual evidence including screen recordings and DOM snapshots, agent traces including prompts and action logs, tool invocations and return values, and environment feedback such as page loads and errors. In total, the dataset contains about 3,000 agent interactions. We conduct most experiments on Windows 11 to ensure a consistent graphical environment, using Linux virtual machines for Linux-only applications. III-D Defect Identification Using the evidence collected in the previous procedure, we manually assess each of the 208 candidates to verify whether the reported failure is real and reproducible: • Confirmed when multiple evidence sources converge on the same tool-layer mistake, such as linked fixes or commits for closed issues, and reproduction logs, tool traces, and before/after GUI states for open issues. • Excluded when the failure only appears in a few runs due to unstable environments, missing credentials, or unsupported setups. This yields 99 confirmed defects out of the 208 candidates, including 43 from open issues and 56 from closed issues. As a failure confirmed from one GitHub issue may not be unique to that application, we next perform cross-app expansion. For each of the 99 confirmed tool-layer mistakes, we exhaustively inspect all remaining 39 applications to check whether the same erroneous tool behavior arises at the same type of tool-environment interaction. When a matching case is found, we reproduce the corresponding failure and count each successful reproduction as a separate confirmed failure. This process yields 335 confirmed interaction failures in total. Finally, we label the confirmed failures through a separate iterative process. In each iteration, four authors discuss the identified failures and refine a list of patterns based on workflow phase, root cause, tool-layer mistake, and impact. Three authors independently categorize each failure into one of the defect patterns, label its impact, and cross-check their labels, reaching 95% initial agreement (Fleiss’ \kappa=0.95 ). A fourth author joins when disagreements remain and resolves them by revisiting the original evidence. The iterations stop when no new patterns emerge, and the labeling effort took about 7 person-months.
