title: ResTest: Targeted Coverage of Residual Not-Covered Code Using Large Language Models for Web GUI Testing
source: https://arxiv.org/abs/2506.00520

§Abstract
Automated web GUI testing (AWGT) approaches explore web applications through GUI actions to achieve code coverage. However, existing approaches, whether random-based, model-based, or reinforcement-learning-based, often struggle to generate continuous and semantically meaningful action sequences for testing complex functionalities, limiting their achievable code coverage. Recent LLM-based approaches partially alleviate this problem but still fall short due to limited capability in inferring testable functionalities and low success rates in executing tasks on complex web applications. In this paper, we propose ResTest, a complementary approach that uses coverage-report-guided LLMs to target residual not-covered code left by existing AWGT approaches. ResTest first runs an existing AWGT approach to broadly explore the application while constructing a state transition graph with summarized information. Once coverage plateaus, ResTest employs an LLM to infer not-covered functionalities based on the state transition graph and coverage report, and then utilizes a specialized LLM-driven GUI agent to execute these functionalities in a targeted manner. Our evaluation on ten open-source web applications shows that ResTest improves three categories of AWGT approaches by 17.52\% to 24.36\% in average code coverage. Ablation studies further confirm the sustained coverage improvement capability and the contribution of each component.

§Introduction (from cached fulltext; cut at ~9000 chars)
Web applications play an important role across diverse domains, including online marketing, education, and management. To reduce the labor costs associated with quality assurance of web applications, approaches of automated web GUI testing (AWGT) are proposed, aiming to maximize code coverage within a constrained time budget. These approaches interact with the web application under test (AUT) via GUI actions (e.g., clicks, drags), emulating human behavior. Existing AWGT approaches can be broadly categorized into three main categories. Random-based approaches [ 1 , 2 ] generate GUI actions randomly on web pages to perform testing. Model-based approaches [ 3 , 4 , 5 , 6 , 7 ] dynamically construct a state transition graph using state abstraction techniques [ 8 , 5 , 7 ] during testing and employ traversal algorithms such as depth-first search to systematically explore the AUT. Reinforcement-Learning-based (RL-based) approaches [ 9 , 10 , 11 , 12 , 13 , 14 ] employ RL algorithms such as Q-Learning [ 15 ] to guide the testing process. However, existing approaches suffer from a limited ability to generate continuous and meaningful action sequences to cover complex functionalities in modern web applications [ 16 , 17 , 18 ] , limiting their ability to reach a satisfying code coverage for two main reasons. First, existing approaches lack the ability to comprehend content within the AUT, reducing their capacity to complete a single unique functionality in a concentrated manner. Second, modern web applications are inherently complex, dynamic, and nondeterministic [ 3 , 8 , 18 ] , causing existing approaches to face difficulties in building the state transition graph and exploring these applications. Recently, a number of studies [ 19 , 20 , 16 , 17 , 18 , 21 , 22 , 23 ] attempt to leverage the strong semantic understanding and logical reasoning capabilities of large language models (LLMs) to enhance GUI testing, but still face limitations in reaching high code coverage, for three main reasons. First, testable functionalities are hard to infer. Modern web applications typically exhibit rich, dynamic, and complex content [ 16 ] , making it challenging for LLMs to accurately infer functionalities that should be tested, particularly when prioritizing important functionalities (e.g., functionalities that can underly high code coverage) for testing. Second, the execution context during testing is complex and hard to memorize. A complete testing process can require the generation of hundreds and even thousands of actions, making it challenging for LLMs to recall previously executed actions or already tested functionalities [ 16 , 17 ] . Third, the success rate of task execution is low. Existing work [ 24 , 25 , 26 , 27 , 28 ] shows that even the state-of-the-art GUI agents achieve limited success rate (i.e., below 30%) when applied to modern web applications to execute specific tasks. The low success rate inevitably undermines the effectiveness of applying LLMs for AWGT. To address these limitations, in this paper, we propose ResTest, complementing AWGT with coverage-report-guided LLMs for covering residual not-covered code [ 29 ] in a targeted manner. ResTest consists of four phases. In the exploration phase, ResTest runs an existing AWGT approach to broadly explore the AUT until coverage stagnates, while simultaneously collecting GUI information and coverage reports. In the asynchronous information processing phase, ResTest organizes the collected information into a state transition graph enriched with natural language descriptions and associations between code files and GUI states. In the testing-task inference phase, ResTest employs an LLM to analyze the state transition graph and coverage reports, identifying low-coverage code files and inferring a batch of testing tasks targeting residual not-covered functionalities. In the task execution phase, ResTest employs a specialized LLM-driven GUI agent, guided by key-state information from the state transition graph, to execute the inferred tasks and improve coverage. ResTest addresses the aforementioned limitations in the following four ways. First, to overcome the difficulty of existing AWGT approaches in exercising complex functionalities, ResTest introduces an LLM-driven GUI agent that can execute testing tasks in a targeted manner, enabling focused exploration beyond generic strategies. Second, to mitigate the challenge faced by existing LLM-based AWGT approaches in inferring testable functionalities from complex and information-rich web pages, ResTest incorporates coverage reports and an online-constructed state transition graph, and explicitly associates code files with abstracted GUI states. This design allows the LLM to accurately identify not-covered code and reason about corresponding functionalities using contextual information of abstracted GUI states. ## II Approach
Figure 1 illustrates the architecture of ResTest, which comprises four phases: exploration (Section II-A ), asynchronous information processing (Section II-B ), testing-task inference (Section II-C ), and task execution (Section II-D ). II-A Exploration Because ResTest targets the residual not-covered code left by existing AWGT approaches, it first invokes one such approach until code coverage stagnates, thereby broadly exploring the AUT and collecting essential information for subsequent analysis. After each action step, ResTest records action-level information (e.g., action type and input value), page-level information (e.g., screenshots and HTML), and the corresponding coverage report. The collected information is forwarded to the asynchronous information processing phase, in which ResTest constructs a state transition graph that subsequently guides the LLM in inferring and executing testing tasks targeting residual not-covered code. II-B Asynchronous Information Processing In this phase, ResTest transforms the unstructured, multi-modal information collected during exploration into a concise textual representation stored in a state transition graph, by combining LLM-based analysis with heuristic rules. To avoid blocking the testing process, this phase operates concurrently with the exploration and task execution phases. The state transition graph is represented by three components: (1) a natural-language description of each state, (2) state transitions, and (3) the code files associated with each state. Templates and instantiations of each component are presented in Table I , together with the representation of our coverage report. The resulting textual representation serves as input to the LLM for inferring and executing testing tasks. State transition graphs have been widely adopted in existing AWGT approaches [ 8 , 32 , 5 , 6 , 7 ] , where pages exhibiting equivalent functionalities from a testing perspective are merged into a single state. Such abstraction mitigates state explosion and avoids redundant exploration of functionally equivalent pages. We empirically adopt WebEmbed [ 5 ] as the state-abstraction technique, since it strikes a favorable balance between abstraction effectiveness and the number of constructed states. After each action step, ResTest uses WebEmbed to compare the current page against previously constructed states and either assigns it to an existing state or instantiates a new one. II-B 2 Natural Language Descriptions of Each State (Descriptions) A constructed state transition graph typically contains dozens of states. Directly representing each state by raw HTML or screenshots would yield an information volume that exceeds the input limits of mainstream LLMs [ 33 , 34 ] . Moreover, since modern LLMs follow a generative paradigm based on the Transformer architecture [ 35 ] , excessive and redundant information in the prompt impairs reasoning ability and instruction adherence [ 36 ] . To convey the knowledge encoded in the state transition graph concisely, ResTest generates a natural-language description for each state using a multi-modal LLM (MLLM), referred to as the Describer . When a new state is added to the graph, the Describer takes the corresponding screenshot as input and produces a textual description. Due to space limit, all prompts used in ResTest are presented in our open-source repository [ 31 ] . Because state abstraction is intended to distinguish pages by their testing-relevant functionalities [ 8 , 32 , 5 , 6 , 7 ] , each description focuses on the functionalities offered by the page and the status of its components. Since these descriptions also serve the subsequent inference and execution of testing tasks, they should be sufficiently detailed to disambiguate similar states yet concise enough to avoid confusion and redundancy. The objective is therefore to convert the multi-modal state transition graph into a textual and concise form for use in subsequent phases. We design the prompt with the Chain-of-Thought (CoT) [ 37 ] technique, which guides the LLM to reason step by step before producing the final answer, thereby improving the accuracy and detail of the generated descriptions. We adopt page screenshots, rather than HTML, as the prompt input for two reasons. First, screenshots preserve the spatial layout of the GUI, allowing the MLLM to leverage its visual understanding to capture component positions and effectively express the visual state of the GUI. Second, since screenshots and prompt text reside in different modalities, the prompt is not flooded by lengthy HTML, reducing the risk of confusing the model or degrading its instruction adherence [ 16 ] . II-B 3 State Transitions (Transitions) After producing the description of each state, ResTest also conveys the transitions among states so that the LLM can connect individual states into a coherent view of the entire graph. Because exploration may execute hundreds or even thousands of actions, directly feeding the entire action sequence to the LLM risks both confusion and context-window overflow. To compactly represent state transitions, ResTest first prunes the state transition graph by discarding self-loops (i.e., edges whose source and target are the same state) and retaining a single edge between any pair of states. It then performs a breadth-first traversal over the pruned graph and serializes each transition as a single line of text containing the identifiers of the source and target states, the action type, the action value, and the identifier of the target component. II-B 4 Code Files Associated with Each State (Code Files) States constructed from GUI information and code coverage reports reside at different abstraction levels and in different modalities. Relying solely on the LLM to bridge them is unreliable. We therefore explicitly associate coverage information with states during the construction of the state transition graph. After each action step, ResTest computes the difference between the current and previous coverage reports and applies two heuristic rules. First, code files newly observed in the current report are associated with the state reached after the action, since the loading of a new state typically loads its corresponding code files. Second, code files whose existing coverage changes are associated with the state from which the action was issued, since that action triggered the additional coverage. To bound time overhead, the differencing is performed at file granularity. Consequently, a code file may be associated with multiple states, and a state may be associated with multiple code files. II-B 5 Coverage Report Relying solely on the state transition graph to infer functionalities that remain not-covered after the exploration phase is insufficient, because some relevant states may not have been visited or recorded by the AWGT approach, and many functionalities are not visible from GUI pages (e.g., authentication controllers). To enable effective and targeted generation of testing tasks aimed at residual not-covered code, we augment the LLM context with information extracted from the final coverage report (i.e., the report obtained at the end of the exploration phase or of a previous task execution phase). The coverage report exposes the coverage status of each code file together with the project’s organizational structure, helping the LLM identify residual and untested functionalities. Specifically, ResTest ranks code files in the coverage report by the number of not-covered lines and selects the top 25. For each selected file, ResTest provides the file path, coverage statistics, and the names of not-covered functions as input to testing-task inference. The coverage report is obtained via code instrumentation, while the names of not-covered functions are extracted via static code analysis. Because modern web applications are typically built upon mature frameworks and follow standard naming conventions [ 38 ] , file and function names usually convey their intended functionalities. The coverage report therefore provides the LLM with sufficient and meaningful contextual knowledge to support effective testing-task inference. II-C Testing-Task Inference After the collected information is processed, ResTest feeds the resulting concise representation to an LLM, referred to as the Reviser , to infer testing tasks targeting functionalities that remain not-covered after the exploration phase. We do not employ an MLLM at this stage, as all relevant information has already been transformed into the textual modality. The prompt also follows the CoT pattern, instructing the Reviser to first comprehend and summarize each input component before emitting the testing tasks in the specified format. We require the Reviser to output, for each task, the target code file the task aims to cover. This design encourages the Reviser to focus on tasks that are explicitly aligned with improving file-level code coverage.
