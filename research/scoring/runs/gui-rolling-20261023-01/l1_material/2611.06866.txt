title: GH-AWTrace: A Large-Scale Dataset of GitHub Agentic Workflow Execution Logs
source: https://arxiv.org/abs/2611.06866

§Abstract
Agentic workflows enable AI agents to perform recurring repository tasks on schedules or in response to repository events. Existing studies examine workflow definitions and outputs, but provide limited evidence of what happens during execution. We present GH-AWTrace, a dataset linking 25,014 verified GitHub Agentic Workflows across 5,051 repositories to 4,112,526 run records and 562,877 nonempty execution log archives. The dataset preserves execution evidence subject to GitHub's log-retention limits and links it to repository metadata and generated workflow configurations. Illustrative cases show how the logs expose tool denials, provider failures, changes in an agent's approach, and delegation among agents. These observations enable research on execution failures, tool use, and the relationship between reported run outcomes and visible task progress. Coverage varies across workflows, and the logs provide partial observations rather than complete agent trajectories. Video: https://youtu.be/KIlfmZhHxtA

§Introduction (from cached fulltext; cut at ~9000 chars)
Agentic AI can inspect repositories, edit code, run tests, and resolve software issues through development tools [ 1 ] . In common coding-agent use, a developer starts each task by assigning an issue or writing a prompt, then reviews the proposed change [ 2 ] . Agentic workflows let developers specify recurring tasks once and run them on schedules or repository events, without a person starting each execution [ 3 ] . GitHub Agentic Workflows (gh-aw) implements this model in Markdown: a file combines the agent’s task with its trigger, permissions, and allowed outputs [ 3 ] . gh-aw compiles the file into a GitHub Actions YAML workflow that starts a coding agent and can produce reviewable issues, comments, or pull requests [ 3 ] . In Azure/azure-dev , a weekly workflow reads feedback on merged pull requests and turns recurring reviewer requests into proposed updates to the repository’s Copilot instructions [ 4 ] . In August 2026, it examined 49 pull requests and proposed rules to reject ignored command-line flags and redact credentials from URLs before printing them in logs [ 5 ] . Repository settings prevented the workflow from opening a pull request, so it saved a branch and an issue with the patch; a maintainer refined and merged the changes through pull request #9731 [ 5 , 6 ] . Khelifi et al. [ 7 ] studied how developers specify and maintain gh-aw workflows. Valenzuela-Toledo et al. [ 8 ] released histories that link Markdown definitions to generated YAML. Sun et al. [ 9 ] measured whether comments from AI code-review Actions led to code changes. Wang et al. [ 10 ] used static analysis to find prompt-injection paths in agentic GitHub Actions workflows. Isbarov et al. [ 11 ] tested prompt-injection attacks in live AI-powered CI/CD workflows. These studies provide complementary perspectives on workflow specifications, outputs, and security. However, workflow definitions describe intended behavior, while run-level outcomes summarize execution without explaining the intervening actions. Execution logs provide additional evidence of tool interactions, access restrictions, infrastructure failures, and recovery attempts. Preserving and linking this evidence is particularly important because GitHub’s retention limits make it unavailable over time. To support research on agentic workflow execution, we release GH-AWTrace, linking 25,014 verified gh-aw workflows from 5,051 repositories to 4,112,526 run records and 562,877 nonempty execution log archives. Its contributions are threefold: (1) an archive of execution logs that may otherwise become unavailable under GitHub’s retention policies; (2) linked workflow, repository, run, and log metadata that support traceable analyses; and (3) illustrative use cases showing how the data can support studies of failures, tool interactions, and within-run agent coordination.

## II Dataset Collection and Curation
We construct GH-AWTrace in three stages: 1) identifying generated gh-aw workflows, 2) collecting their run metadata, and 3) archiving available execution logs. Figure 1 summarizes coverage across these stages. II-A GitHub Agentic Workflow Identification First, we search for gh-aw generated workflows through the GitHub REST API code search [ 12 ] using the following search query on both .yml and .yaml files separately: "This file was automatically generated by gh-aw" path:.github/workflows extension:yml fork:true size:0..393216 GitHub returns at most 1,000 code-search results per query [ 12 ] . To reach files beyond this limit, we search non-overlapping file-size ranges in bytes. When a range reported the maximum allowed 1,000 matches, we split it in half and searched both smaller ranges. We retrieve every page from the final ranges and remove duplicate files using the repository ID and exact file path. Upon further investigation, we notice that the target phrase could appear as a quoted text rather than a generator comment. We fetched each file at the blob revision returned by search and accepted it only when the generator phrase appeared in an opening YAML comment before any configuration key. Of 25,227 candidate files in 5,059 repositories, 63 lacked the required header, and 150 indexed blobs could not be retrieved. This process yielded 25,014 verified gh-aw workflow files across 5,051 repositories. II-B GitHub Agentic Workflow Runs Collection We use the GitHub REST API to collect runs for each gh-aw workflow, querying by workflow ID and saving all data fields returned by the run listing API [ 13 ] . We link runs to the YAML revision indexed during discovery by repository ID and exact path. This revision may differ from the one used by a run if the workflow changed. The run metadata retains its head_sha . This phase yields 4,112,526 run records dated August 14, 2025, through September 21, 2026, since GitHub retention policy deletes runs after 400 days [ 14 ] . II-C Log Collection Finally, GitHub automatically deletes public workflow execution logs after at most 90 days [ 14 ] . We therefore select 2,453,263 run records created from June 23 through September 21, 2026, the 90 days before our run cutoff. For these runs, we download and save 1,633,215 execution log archives (56.1 GB), one ZIP per downloaded attempt [ 13 ] . A run has one GitHub run ID. Each rerun keeps that ID and receives a new attempt number, so we identify an archive by run ID and attempt number. We check each ZIP’s integrity and record its SHA-256 hash and file list. Of the selected runs, 821,672 have no downloaded archive, which may reflect retention, deletion, access restrictions, or an unfinished run. Among the downloaded ZIPs, 1,070,338 contain no files and 562,877 contain log files. The 562,877 archives with files belong to 561,367 runs, and 18,337 archives come from attempts after the first. In an early audit of 2,900 empty ZIPs with saved job metadata, 2,699 show only skipped jobs in the available pages and 195 list no jobs. We cannot determine the cause of every empty ZIP. ## III Dataset Characteristics
III-A Schema and Stored Files Figure 2 shows how repositories, gh-aw workflows, runs, and log archives are linked. A repository can contain one or more gh-aw workflows, linked through repo_id . When a workflow executes, it has one or more runs, linked through repo_id and its exact YAML path . A run may have no downloaded log archive or an archive linked through run_id . If a run is rerun, each downloaded attempt archive is distinguished by its attempt number. III-B Available Content The JSON fields retain additional GitHub metadata, including each run’s event, actors, branch, commit SHA, and timestamps. CSV indexes support direct joins, while the raw YAML, API responses, and ZIPs preserve the underlying content. A download row records whether an archive was saved or unavailable; a saved ZIP can still contain zero files. Its receipt lists each member and checksum. Runs skipped because of age have no downloaded archive. III-C Execution Distributions Figure 3 shows the distribution for the 6,040 workflows with logs. The median is 16 logs per workflow (interquartile range: 6–60). Each downloaded execution attempt contributes one log archive. Table I groups nonempty log archives by their run’s recorded event. The workflow column counts verified workflows with at least one log under that event. A workflow can appear under multiple events, so workflow counts are not additive.
