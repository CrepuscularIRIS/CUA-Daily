title: OS-Bench: Evaluating SWE Agents on Cross-OS Code Migration
source: https://arxiv.org/abs/2610.19368

§Abstract
Language-model (LM) agents are increasingly evaluated on repository-level software engineering (SWE) benchmarks derived from GitHub issues and pull requests. Although these benchmarks cover a broad range of development tasks, they provide limited insight into a common yet technically distinct challenge: migrating an existing implementation from one operating system (OS) to another while preserving behavior on both. We introduce OS-Bench, an executable benchmark for cross-OS code migration between Linux and Windows. Motivated by case studies showing that cross-platform features are frequently implemented on one OS before support is added for another, OS-Bench identifies migration opportunities by comparing execution coverage collected from the same repository on both systems. Platform-specific regions are then verified, organized into five migration scenarios, and transformed into repository-level tasks with target-platform tests and source-platform regression tests. The resulting benchmark contains 140 validated tasks from 111 repositories across C, C++, C#, Go, and Rust, comprising 91 Windows-to-Linux and 49 Linux-to-Windows migrations. We evaluate six models with SWE-agent, Claude Code, OpenHands, and Win-agent. The best configurations achieve only 26.4% success on Linux-target tasks and 20.4% on Windows-target tasks while preserving correctness across both systems. These results indicate that cross-OS migration is a challenging and underexplored capability, and OS-Bench is a testbed for improving platform-aware SWE agents.

§Introduction (from cached fulltext; cut at ~9000 chars)
Cross-platform support is essential for software libraries, developer tools, and applications that need to run across different computing environments. Supporting a new operating system (OS), however, requires more than recompiling the same source code. Developers often need to handle differences in system APIs, filesystem and path conventions, process and signal behavior, networking interfaces, text encodings, build toolchains, and command-line environments. A migration patch must therefore implement the required behavior on the target platform while preserving existing functionality on the source platform. LM-based software engineering agents can explore repositories, execute tests, and modify multiple files in response to natural-language instructions. Their progress is typically evaluated on benchmarks built from real GitHub issues or pull requests [ 1 , 2 , 3 , 4 ] . While these benchmarks capture realistic repository-level development tasks, they usually evaluate each task in only one execution environment. As a result, they do not directly test whether an agent can identify an OS-specific implementation gap, adapt behavior across incompatible platform abstractions, work effectively in the target operating system, and preserve existing functionality on the original OS. Our preliminary case studies illustrate how this challenge arises in real multi-platform repositories. In these cases, functionality is implemented for one platform first, such as Linux, and later ported to another, such as Windows, using a separate platform-specific implementation. Figure 1 shows an example from the asynchronous I/O library libuv/libuv . Support for configuring UDP sockets for multicast and broadcast was first introduced in the Unix backend and was later added to the Windows backend in a separate commit. The two implementations expose the same user-facing behavior, but they live in different code paths and rely on different operating-system interfaces. Although such histories reveal migration work, migration tasks cannot be reliably extracted directly from individual commits. A single migration may span multiple commits, and each commit may mix migration changes with unrelated bug fixes, refactoring, or feature development. Using a commit as a task can therefore omit changes needed to complete the migration or include edits unrelated to it. Constructing a coherent task from commit history therefore requires substantial manual effort to trace the migration across multiple commits and disentangle relevant edits from unrelated changes. We address this challenge requiring heavy manual workload and automate the task-construction process by using differences in execution coverage to identify platform-specific implementations. When a repository’s tests are run on Linux and Windows, code associated with one backend is exercised on one OS but not the other. We build OS-Bench around this observation using a differential-coverage pipeline. We first build and test candidate repositories in native Linux and Windows environments, compare their coverage traces, and verify which differences reflect platform-specific behavior. We then remove verified target-platform implementations to construct migration tasks, retaining tests that fail when the implementations are missing and regression tests that check unrelated behaviors are preserved. This procedure creates controlled restoration tasks without requiring migration changes to align with historical commit boundaries. OS-Bench contains 140 executable tasks from 111 open-source repositories spanning C, C++, C#, Go, and Rust. It includes both migration directions: 91 tasks migrate functionality supported on Windows to Linux, while 49 migrate Linux-supported functionality to Windows. Each task provides a repository at a reproducible base commit, a natural-language migration objective, an executable environment, fail-to-pass tests for the target functionality, and pass-to-pass tests for regression checking. We evaluate each patch on both the target and source platforms to check that it restores the missing functionality while preserving existing behavior under the test suites. We evaluate six models using three Linux agent harnesses—SWE-agent, Claude Code, and OpenHands—as well as the Windows-native Win-agent harness. The strongest configuration solves only 26.4% of Linux-target tasks, while the best Windows configuration reaches 20.4% on Windows-target tasks when success requires the patch to work correctly on both systems. Performance also varies substantially across languages, migration directions, and agent harnesses. In particular, changing the harness can noticeably change the performance of the same underlying model. These results show that reliable migration remains difficult and that performance depends on both the model and the tools it uses to interact with the operating system. ## OS-Bench
An OS-Bench task starts from a repository with part of its implementation for one operating system removed. The agent restores support for that target system, and evaluation checks the submitted patch on both the target and source platforms. Figure 2 summarizes the full OS-Bench construction and evaluation pipeline. Task Formulation Let R^{+} denote the complete repository at a fixed revision, with executable test workloads on a source platform s and a target platform t . Let C_{s}(R) and C_{t}(R) be the sets of source lines executed by the repository’s test workload on the two platforms. We identify target-specific candidate code as D_{t}=C_{t}(R^{+})\setminus C_{s}(R^{+}). (1) An LM-based verifier V examines the source code and filters out coverage differences unrelated to platform-specific behavior. A masking transformation M then removes or replaces the verified target implementation: R^{-}_{t}=M(R^{+},V(D_{t})). (2) The agent receives (R^{-}_{t},I,E_{t},B) : the incomplete repository, a natural-language migration instruction, the target execution environment, and a fixed interaction budget. It returns a patch \Delta . Let T_{t}^{\mathrm{fix}} denote target tests that do not pass in R^{-}_{t} but pass in R^{+} , T_{t}^{\mathrm{keep}} denote target tests that pass in both states, and T_{s}^{+} denote tests that pass in the complete source environment. A patch solves the task only if it satisfies both \displaystyle\operatorname{pass}_{t}(R^{-}_{t}\oplus\Delta,T_{t}^{\mathrm{fix}}\cup T_{t}^{\mathrm{keep}}) \displaystyle=1, (3) \displaystyle\operatorname{pass}_{s}(R^{-}_{t}\oplus\Delta,T_{s}^{+}) \displaystyle=1. (4) The first condition checks target repair and regression tests; the second checks source-platform preservation. We also require the source reference set T_{s}^{+} to be nonempty. The same patch is evaluated in both native environments. Why test both platforms? A target test suite cannot directly exercise code compiled only on the source OS. A patch can therefore pass the target suite while breaking a source-only branch or removing a guard needed by the source build. Running the patch on both systems checks behavior that would otherwise go unobserved. As with any test-based evaluation, passing these checks establishes correctness only for the behaviors they cover. Repository and Environment Selection We start from popular open-source repositories written in C, C++, C#, Go, and Rust whose continuous-integration configurations indicate support for both Linux and Windows. For each repository, RepoLaunch [ 9 ] checks out a fixed revision, resolves dependencies, builds the project in a native environment, identifies a stable test command, and constructs a parser that converts raw test output into test names and statuses. A repository is retained only when usable environments can be built on both operating systems. The complete repository provides the reference behavior for task construction and evaluation. The environments retain platform-native shells and toolchains, since path handling, command execution, and system APIs are part of the migration problem. Differential Coverage and Verification We run each repository’s tests with language-appropriate line-coverage instrumentation on both Linux and Windows. Coverage paths are normalized to the repository root while accounting for differences such as platform-specific separators, generated build prefixes, Go module paths, and Rust registry paths. For each file, we identify lines executed only on Linux or only on Windows and merge neighboring lines into candidate regions. Coverage asymmetry alone does not establish that code is platform-specific. A line may execute on only one system because of differences in test selection, nondeterminism, dependency versions, or unrelated feature flags. We therefore use an LM-based verifier that receives the complete source file with Linux-only and Windows-only regions annotated and assigns each region one of six labels: • Platform-Conditional : compile-time guards, build tags, platform-specific filenames, or runtime OS checks; • Platform-API : system calls, headers, commands, libraries, constants, or other facilities specific to one OS family; • Platform-Path : differences in separators, roots, drive prefixes, case sensitivity, or path-list semantics; • Platform-Encoding : line endings, locales, console code pages, Unicode conversion, or other platform-specific text representations; • Other-Migration-Feature : portability shims, dependency substitutions, capability probes, build adaptations, and related compatibility logic; • False-Positive : asymmetric execution with no inherent platform-specific semantics. Regions assigned to the first five categories were retained while those labeled False-Positive were discarded. The LM-retained lines were further filtered by human. For each migration direction, the retained regions in a repository form one task. A task may therefore involve several categories and require changes across multiple files. Constructing the Incomplete State For each retained repository, we first rebuild and test the complete version on the target platform and record its reference test status G_{t} . An LM-based masker is prompted to substitute every verified target-only region with a placeholder which would be silently bypassed during execution, while avoiding inserting obvious exceptions or a replacement implementation to maintain a sufficiently high level of task difficulty. Test files are excluded by default. The LM-masked fields are manually verified to ensure that: (1) It masked all verified target-specific regions selected for the task with no exceptions or re-implementations inserted; and (2) It did not touch source-platform codes and source-platform test suite T_{s}^{+} remains passed. The violations are manually fixed. We then rebuild the incomplete repository and run the same target test suite to obtain status B_{t} . The task labels are then derived directly from the difference between the complete and incomplete states: \displaystyle T_{t}^{\mathrm{fix}} \displaystyle=\{x\mid G_{t}(x)=\mathrm{pass}\land B_{t}(x)\neq\mathrm{pass}\}, (5) \displaystyle T_{t}^{\mathrm{keep}} \displaystyle=\{x\mid G_{t}(x)=\mathrm{pass}\land B_{t}(x)=\mathrm{pass}\}. (6) A candidate is kept only when T_{t}^{\mathrm{fix}} is nonempty. Thus every retained task has at least one previously passing test that fails, is skipped, or is absent after masking. The reverse of the masking diff provides the reference (gold) repair patch. To prevent recovery of the removed implementation from Git history, the original .git data including the Git remote URL were removed and the repo is re-initialized with a root commit. We assign each task a construction-time difficulty label based on the size of the verified migration region. A task is hard if the region exceeds 100 estimated lines or spans more than five files, medium if it exceeds 30 lines or two files, and easy otherwise.
