title: OpenGameEval: Benchmarking Agentic Programming and Exploration in a Stateful Game Engine
source: https://arxiv.org/abs/2610.02563

§Abstract
We present OpenGameEval, a benchmark and evaluation framework for agentic game development inside Roblox Studio. It runs language models as agents in reproducible, stateful game-engine sessions and scores each run with executable checks, both on the edited scene and in a simulated play session. Most agentic coding benchmarks require exploration but score only final task success. OpenGameEval separates observation tools from editing tools in its eight-tool action space, so exploration can be measured directly. We measure the pass rates and exploration behavior of 13 frontier models on 84 human-curated core tasks, with 16 attempts per task. The tasks are hard for current models. The best model solves 51.7% of tasks on a single attempt and 39.4% five times out of five, and no tested model solves six of the tasks. Models at the frontier reach similar pass rates by solving different tasks: splitting tasks by the kind of work they require spreads the top five by 5.0pp on script-authoring tasks and 12.5pp on scene-change tasks. Exploration behavior predicts whether a run succeeds. Holding task and model fixed, a run that inspects every object a reference solution touches before acting on it passes 13.4pp more often than a run that inspects none of them on scene-only tasks, and 9.8pp more often on script-only tasks. We release the task suite, its place files, the per-task annotations, a plugin that runs the tasks inside Roblox Studio, and an updated leaderboard under the MIT license at https://github.com/Roblox/open-game-eval.

§Introduction (from cached fulltext; cut at ~9000 chars)
Code-generating language models are mostly evaluated on outcomes: a model receives a problem, and a fixed oracle checks its output. HumanEval and MBPP score function bodies against unit tests ( Chen et al., 2021 ; Austin et al., 2021 ) , and SWE-bench and its verified subset score patches against a repository’s own test suite ( Jimenez et al., 2024 ; Chowdhury et al., 2024 ) . This approach has driven substantial progress, but it assumes that the final outcome is the only quantity worth measuring. The same passing result can come from an agent that understood the system or from one that guessed, and the outcome alone cannot tell them apart ( Zhu et al., 2025 ; Bean et al., 2025 ) . We study a domain where that assumption breaks down, and we focus on exploration: what a model finds out about the world it is working in. Consider an AI coding assistant inside a game engine that is asked to “implement health regeneration that begins two seconds after damage and restores ten health per second” in an existing game. The prompt does not say which scripts manage health, whether damage is server-authoritative, or where in the object hierarchy the player rig lives. The agent has to find these facts itself, by searching the object hierarchy, reading the scripts already in the game, and inspecting the properties of the objects it finds. Correctness is also a play-time property. It can only be observed once the game runs, the damage event fires, and the client sees health climb on the right schedule. We introduce OpenGameEval , a benchmark and evaluation framework for agentic game development that runs an LLM agent inside a reproducible editor session. Four design properties together let us measure exploration, not just outcomes: (i) a stateful world with hidden structure that the agent must discover through tools (Figure 1 ), (ii) an instrumented eight-tool action space that separates observation from action, (iii) play-time verification with real physics, networking, and client–server dynamics, and (iv) human-written reference solutions annotated with the objects and scripts a correct run should consult. We evaluate 13 models on the 84-task core suite, with 16 attempts per task, and report three main results. First, the tasks are hard for current models. The strongest model solves 51.7\% of core tasks on a single attempt and only 39.4\% five times out of five. No model solves six of the core tasks in any of their 16 attempts, although each task’s human-written reference solution passes its checks. Second, the models at the frontier do not fall into a simple order. Five models finish within 1.1 pp of one another at about 51\% , but they get there by solving different tasks. All five solve only 27 of the 84 core tasks, while at least one of them solves 58 (§ 6 ). Scoring each kind of work separately shows where they differ: the spread among the same five models grows from 1.1 pp to 5.0 pp on script-authoring tasks and to 12.5 pp on scene-change tasks (Figure 2 ). A single average pass rate hides how different these models are. Third, how a run explores predicts whether it succeeds. The first two results concern which tasks a model solves, and this one concerns the trajectory. Motivated by the failure modes we observe in game development tasks, we ask whether an agent’s exploration predicts the outcome, and find that it does on both kinds of work. On tasks whose solutions have annotated dependencies, and holding task and model fixed, inspecting the expected objects before acting on them is associated with a 13.4 pp higher chance of passing on scene-only tasks ( 95\% CI [+1.2,+25.7] ) and a 9.8 pp higher chance ( [+3.6,+16.0] ) on script-only tasks, whose work is only to author script text (§ 7 ). The measurement scheme is not specific to game development. Any evaluation of tool-using agents that labels its tools as observation or action can compute the label-based features, and one that also annotates each task’s dependencies can compute the coverage signal. We release all task definitions, the place files they run against, the per-task annotations used in § 7 , a plugin that runs the tasks in Roblox Studio, and the leaderboard under the MIT license at https://github.com/Roblox/open-game-eval .
