title: BT-Agent: Deploying Onboard Robot Agents with Behavior Trees and Multi-Fidelity Evaluation
source: https://arxiv.org/abs/2610.13862

§Abstract
Deploying language-model agents onboard mobile robots requires task reasoning and responsive execution within limited compute and memory. We propose BT-Agent, an onboard architecture combining LLM-driven task decisions with predefined behavior-tree (BT) skills. These skills enforce execution conditions and return structured failure feedback. We demonstrate fully onboard operation with a 9B model on a quadruped across five task categories. Intervention tests show that local checks stop ongoing navigation without waiting for another model decision, while the agent remains active to retry or report constraints. To compare agent designs efficiently, we introduce a 161-task multi-fidelity benchmark, evaluated in text on all tasks and in Habitat on 39. Text supports 10.9$\times$ higher evaluation throughput, while simulation reveals how perception and motion failures change task outcomes. BT-Agent's largest success gains over the strongest Act/ReAct baseline occur at 4B and 9B: approximately 10 and 5 percentage points. Ablations identify structured tool calls and informative failure feedback as the most useful components.

§Introduction (from cached fulltext; cut at ~9000 chars)
Mobile robots increasingly receive high-level goals that require sequences of physical actions. During search, inspection, and manipulation, they need to track partial information and adapt when an action fails [ 1 ] . For operation independent of remote compute, this reasoning must run onboard, sharing finite memory and compute with perception and control. Deploying an agent on an embedded platform therefore involves both task-level decision making and responsive physical execution. Language-model robot agents interleave task-level reasoning with action through skill selection, execution feedback, and programs over robot APIs [ 2 , 3 , 4 , 5 ] . These methods primarily address what the agent should do next. There is, however, no shared interface across these approaches for how selected robot skills expose execution state, enforce conditions, and support interruption. Behavior trees (BTs) provide a modular, robotics-native basis for such an interface [ 6 ] . To this end, we propose BT-Agent, a deployment-oriented architecture that separates task-level model reasoning from reactive robot execution through predefined BT skills (Fig. ). An onboard Actor selects skills and arguments using the task, state, and previous observations. A supervisor BT starts each skill and returns structured feedback, forming a reasoning-and-acting (ReAct) loop [ 7 ] . Within each skill, guards recheck conditions on every tick and can interrupt a running action without another model decision. The Actor cannot modify skill implementations or guards, so their logic can be reviewed and tested independently of the task-level policy. This combines established BT execution mechanisms with flexible, feedback-driven task reasoning: the model adapts its decisions, while the BT enforces the conditions under which each skill can run. Evaluating this architecture means checking both the agent’s decisions and how its skills perform. We need controlled comparisons across models and harnesses, alongside trials where perception and motion can fail. We therefore construct a multi-fidelity benchmark with 161 text tasks derived from Habitat and Isaac scenes, sharing task goals and skill interfaces with simulator execution. Text trials support inexpensive comparisons of task performance, inference cost, and responses to injected faults such as navigation timeouts and observation failures. Paired trials on 39 primary Habitat tasks examine where perception and motion change the outcome. Robosuite experiments [ 8 ] additionally examine task-level orchestration in manipulation. Finally, real-robot trials demonstrate fully onboard task completion with a 9B model, while intervention tests validate the architecture’s reactive skill execution. In summary, our contributions are: i. An agentic robot architecture, BT-Agent, for onboard deployment, combining model-driven task decisions with predefined BT skills, reactive execution checks, and structured feedback. ii. A multi-fidelity evaluation methodology connecting a 161-task text benchmark, simulation-informed fault injection, and physical execution through shared task goals and skill contracts. iii. An empirical evaluation across model sizes and execution backends, characterizing task success and inference cost, demonstrating fully onboard deployment with a 9B model, and achieving 10.9 \times higher evaluation throughput in text than in Habitat at eight concurrent workers. We will release the BT-Agent implementation and benchmark code under the Apache-2.0 license.

## III BT-AGENT
An LLM-driven robot should enforce execution conditions even when the model proposes an unsuitable action. BT-Agent therefore separates task-level choice from execution: the agent selects actions, while predefined BT skills determine whether and how they execute (Fig. ). III-A Agent The LLM Actor reasons about the next step, selects a skill, and uses the returned observation to inform its next decision. This reasoning-and-acting loop follows ReAct [ 7 ] . Using the task, history, and stored results, it selects skill arguments or claims completion. A supervisor BT executes one skill at a time, returning status and results before the next Actor call. The supervisor converts the Actor’s completion claim into a terminal submission. The Actor receives text and structured data; perception skills process images. We summarize history to limit context and retain skill results in a typed object store for reuse. Failure feedback lets the Actor retry, change actions, or report why it cannot continue. Cancelling the task interrupts its running skill. III-B BT Skills We implement each robot skill as a predefined behavior tree and expose it as a named tool. Developers can review its fixed execution logic independently of model choices. Consider a request to photograph a pair of glasses. The Actor queries scene memory, navigates to a returned viewpoint, surveys the cameras, and captures the glasses. Query and survey provide context; navigation and capture perform task actions. We keep context skills available so the Actor can gather information and report constraints even when physical actions are blocked. We check preconditions before allowing a physical skill to start. Navigation requires a known target location. The framework validates arguments, resolves object references, and checks required prior observations. These conditions filter available physical skills and reject ineligible calls before execution. Guards determine whether execution may continue: localization can fail after navigation starts. Each physical skill’s reactive sequence rechecks cancellation, elapsed time, and skill-specific guards on every tick, a periodic tree update. By construction, the skill body advances only if all guards pass on that tick. A failed guard interrupts the branch and requests that the controller stop. Checks run without further Actor calls, and the Actor cannot disable them through skill arguments. We also check cancellation in context skills. Failed guards or leaves supply diagnostic feedback when available, without another model call. Physical response depends on the specified checks, state feedback, and controller stopping behavior. BT-Agent does not prescribe a fixed skill library. For our inspection benchmark, we use the skills described in Section IV .

## IV SIMULATION FRAMEWORK
Physics simulation makes repeated tests of agent decisions and skill execution costly. We extend externally supplied Habitat and Isaac environments with text counterparts for inexpensive evaluation. Shared tasks, skill interfaces, and explicit goal checks align the backends, while text also supports controlled fault injection. Figure 2 outlines construction; Fig. 3 illustrates the shared task requirements. IV-A Scene Coverage The framework covers four scene configurations: two indoor Habitat configurations of the same home, an outdoor Isaac scene, and an additional HSSD home [ 24 ] . An independent evaluation team supplied 32 tasks for the first three configurations to test object search, inspection, and interaction: 21 indoor and 11 outdoor. We add 18 indoor tasks varying reference ambiguity, target count, interaction dependencies, and infeasibility. Together these form the 50-task primary suite (39 Habitat-derived, 11 Isaac-derived). This suite supports prompt and harness development. We author 111 transfer tasks in the additional home to test the resulting configurations, with model weights unchanged. IV-B Aligned Execution For each scene, the framework provides a scene memory with object descriptions and locations, a navigation graph, and viewpoints from which objects can be observed. These are derived from simulator geometry and rendered images. Collision checks validate graph connections, and object masks record visibility. Additional records describe changes after scripted interactions. Scene memory provides prior knowledge about the environment. The agent’s own object store and history accumulate results and observations during the current task. Text execution uses these records to update robot position, visibility, and interaction state. Physics simulation executes motion and renders current camera images. In Habitat, surround_survey and capture use VLM perception, while CMU’s depth-based local planning stack [ 25 ] executes navigation along the supplied graph. Unlike stored text observations, VLM outputs can miss or misidentify objects. Perception and simulated motion can therefore change the feedback and task outcome despite shared instructions and completion requirements. Table II lists the skill interface. IV-D Fault Injection Nominal task success alone does not show how an agent handles failure. The text backend applies repeatable faults to eligible skill calls (Table IV ), changing execution state, returned observations, or both. Some explicitly report failure; others report success despite incomplete execution, testing whether agents check outcomes beyond the returned status. Cases are informed by simulation failures and supplemented with targeted stress cases.
