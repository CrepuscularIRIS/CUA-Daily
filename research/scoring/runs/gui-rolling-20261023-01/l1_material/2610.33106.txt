title: VibeGame: Prompt-to-Game Development with AI-Native Engine and Self-Evolving Adversarial Agent Team
source: https://arxiv.org/abs/2610.33106

§Abstract
Large language model agents have enabled software development through natural-language interaction, but extending this paradigm to end-to-end game development remains challenging. Building a playable game requires coordinating code, scenes, assets, animations, physics, and configurations, while allowing developers to validate their integrated behavior through interactive testing. We introduce VibeGame, a framework for creating complete 2D game projects from natural-language prompts and optional reference images. Its AI-native game engine represents project state as schema-validated structured text and provides frame-synchronous runtime control, enabling agents to inspect game states, execute actions, and verify behavior at their own pace. Built upon this interface, we design an Adversarial Agent Team of eight specialized agents to separate implementation from review, so that problems are found and fixed through multi-round loops. For each conducted and accepted project, we further introduce a training-free self-evolution mechanism to distill it into reusable skeletons, modules, and collaboration contracts for future development. We evaluate prompt-assets-to-game (PA2G), where agents are given an asset library, and prompt-to-game (P2G), where agents generate their own art. On a GameCraft-Bench subset, VibeGame in P2G consistently outperforms a range of agent harnesses in either P2G or PA2G with the same underlying model, including GPT-6.1-Sol.

§Introduction (from cached fulltext; cut at ~9000 chars)
Games are among the most demanding types of software to develop: they must sustain interactive worlds in real time, maintain a coherent visual identity, and enforce consistent, balanced rules. Meeting these requirements has traditionally required months of collaboration among designers, programmers, and artists using game engines such as Unity [ 1 ] , Unreal Engine [ 2 ] , and Godot [ 3 ] . The required time and resources put game development out of reach for many creators. Artificial intelligence (AI) has begun to lower this barrier from two directions, yet neither fully supports practical game creation. World models such as Genie [ 4 ] generate interactive experiences directly from video but produce no editable source code, while large language models (LLMs) integrated into commercial engines, as in DreamGarden [ 5 ] for Unreal, face project state scattered across graphical interfaces and binary assets that agents cannot consistently inspect or modify. Neither produces a complete game project that can be built, played, inspected, versioned, and iteratively revised. Meanwhile, LLM-based coding agents [ 6 , 7 ] have made “vibe coding” increasingly accessible, allowing non-programmers to describe software in natural language and refine it through iterative feedback. Games are the natural next step, and we formulate this challenge as Prompt-to-Game (P2G) Development : given only a natural language description and optional reference images, the system must produce a complete playable game project, discovering and fixing its problems along the way. Recent systems and benchmarks have made progress toward this goal. AutoUE [ 8 ] and OpenGame [ 9 ] build games end to end with agents, and GameDevBench [ 10 ] and GameCraft-Bench [ 11 ] evaluate such abilities, the latter also with a provided asset library, a setting we call Prompt-Assets-to-Game (PA2G). However, most of these efforts reserve runtime checks for final evaluation or limit them to verifying that a game builds and runs. Yet many game issues emerge only during play, making interactive testing and refinement essential to playability. Additionally, fixing one project artifact can introduce inconsistencies across interdependent code, scenes, assets, animations, physics, and configurations. Addressing these challenges reliably and carrying validated solutions forward to future projects requires three tightly coupled capabilities. First, an agent-operable project state must expose the structure and dependencies among scripts, scenes, assets, animations, physics, and configurations, because direct file access alone cannot prevent a seemingly local edit from violating hidden relationships elsewhere. Second, interaction-grounded verification is needed because a structurally valid project can still fail at runtime when player input, physics, animation, and game logic interact; since execution unfolds faster than an agent can reason about it, verification requires controllable execution that can be paused, advanced, and examined. Third, the system must preserve validated development experience : so that reusable project structures, features, and coordination procedures can guide subsequent work, while unverified or project-specific content must remain isolated. To address these requirements together, we introduce VibeGame , a unified framework that connects project construction, runtime verification, and experience reuse within a development loop, as illustrated in Figure 3 . (1) An AI-native game engine exposes scenes, nodes, assets, scripts, and configurations as structured text with explicit references and schema validation, and its frame-synchronous runtime control lets agents inspect game states, inject actions, and observe their consequences. (2) Built upon this interface, an Adversarial Agent Team (AAT) separates implementation roles from auditor, player, and reviewer roles, which challenge the game from structural, behavioral, and project-level perspectives; the team iterates review and revision until the project satisfies the intended design and functionality. (3) Once the project is accepted, a training-free self-evolution mechanism distills its reusable experience into project skeletons, verified modules, and collaboration contracts (Section 3.3 ), which subsequent projects adapt and revalidate rather than reuse blindly. Ablation studies further show that removing either the AI-native engine or the adversarial review roles substantially lowers the overall score, and that the experience distilled through self-evolution with a stronger model can be transferred to improve a weaker one.
