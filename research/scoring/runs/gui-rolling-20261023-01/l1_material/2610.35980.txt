title: UnityBench-Mini3D: Evaluating LLM Agents for 3D Game Development in Unity
source: https://arxiv.org/abs/2610.35980

§Abstract
Game development stresses coding agents in ways general software engineering does not: correctness depends on how engine APIs, serialized scene state, and runtime behavior interact, not on source code alone. Existing benchmarks mainly target platforms such as Godot and heavily rely on LLM judges or coarse task-level outcomes. We present UnityBench-Mini3D, a benchmark of 77 project-level Unity tasks organized around seven expert-defined skill categories rather than tutorials or genres, with three difficulty tiers. Each task pairs a complete Unity project with natural-language requirements and is evaluated using 1,178 held-out, human-authored milestone tests covering scene structure, component configuration, and runtime behavior. This in-engine evaluation provides deterministic partial credit, localizes failures, and distinguishes partial implementations from complete solutions without relying on subjective judges. Across 21 models and 9 coding harnesses, the average pass rate reaches 80.9% on easy tasks but falls to 35.2% on hard tasks, with just 57.7% overall. UnityBench-Mini3D provides a reproducible, diagnostic testbed distinguishing systems across difficulty levels.

§Introduction (from cached fulltext; cut at ~9000 chars)
Motivation. Game development is a systems-engineering discipline rather than a single programming activity. Even a small 3D game requires developers to organize scenes, implement gameplay logic, configure physical interactions, coordinate animation state machines, build responsive user interfaces, author particles and shaders, and often extend the editor with custom tools. These activities draw on distinct skills yet interact through shared project state: a small change to a collider, serialized reference, scene hierarchy, or animation transition can affect systems far from the edited asset. Consequently, correctness cannot be established from source code or compilation alone. It depends on the structure and configuration of the project as well as its runtime behavior: a project may compile and launch while containing a miswired reference, a character that clips through the floor, or an interface that never updates ( La et al., 2026 ) . Most game-development work takes place inside a game engine. Engines such as Godot, Unity, and Unreal maintain asset databases, serialization systems, and editor environments in which much of a project’s state is created and persisted. Game development therefore means operating within a stateful software environment rather than editing a collection of source files. In parallel, large language models have become capable of software-development tasks ( Chen et al., 2021 ; Jimenez et al., 2024 ) , and a growing body of work shows that they can support parts of the game-development workflow while demonstrating competence with engine APIs and conventions ( Chen et al., 2023 ; Yin et al., 2026 ; Jiang et al., 2026 ) . These capabilities are now reaching production tooling ( Unity, 2026 ; Epic, 2026 ) . Alongside them, benchmarks have emerged to evaluate agents on tasks grounded in real engines, using engine execution, automated tests, or judgments over runnable artifacts ( Chi et al., 2026 ; La et al., 2026 ; Luo et al., 2026 ; Sun et al., 2026 ) . Despite this progress, existing benchmarks leave three important gaps. First, engine coverage is narrow: most benchmarks use Godot ( Chi et al., 2026 ; Luo et al., 2026 ; Sun et al., 2026 ) , few target Unreal ( La et al., 2026 ) , and Unity coverage remains limited despite its widespread commercial use; MAGE covers only single-file C# generation for 26 hand-crafted 2D mini-games rather than editing complete Unity projects ( Liu and Tatar, 2026 ) . Second, tasks are rarely organized around how game development is actually practiced. Many are adapted from tutorials ( Chi et al., 2026 ) , creating a risk that reference implementations already appear in pretraining data, while others group tasks by game genre or by topic clusters derived from public repositories ( Luo et al., 2026 ; Zhang et al., 2026a ) , categories that describe what a game is rather than the development skill required to build it. Third, and most importantly, evaluation remains coarse. Many benchmarks rely on LLM judges, introducing subjectivity and limiting reproducibility ( Jiang et al., 2026 ; Luo et al., 2026 ; Zhang et al., 2026a ) , while deterministic alternatives reduce an entire task to a single pass/fail outcome or an aggregate similarity score ( Chi et al., 2026 ; Sun et al., 2026 ) . An agent that implements a jump but never lands the character may then score the same as one whose scene does not load at all, and a solution that hard-codes an expected value or modifies the test itself may still be counted as successful. Together, these limitations motivate a Unity-based benchmark whose tasks reflect the structure of real development work and whose outcomes are verified finely enough to explain not only whether an agent succeeds, but what it builds correctly and where it fails. Contribution. To address these gaps, we present UnityBench-Mini3D, a manually curated benchmark for evaluating LLM agents on 3D game development in Unity. Its taxonomy is grounded in expert-defined development skills rather than tutorial content or ad hoc topic groupings, and it comprises 77 project-level tasks spanning seven common development skills and three difficulty tiers. Each task is provided as a complete Unity project with a written specification and is evaluated by 1,178 held-out, human-authored milestone tests executed within Unity. By decomposing each task into independently verifiable checkpoints, these milestones provide deterministic requirement-level partial credit, identify which requirements are satisfied or missed, and distinguish partial implementations from complete solutions. Our contributions are threefold: (1) We introduce UnityBench-Mini3D, an open-access benchmark along with an evaluation framework. Evaluation is performed in a containerized environment with the engine version, project dependencies, and testing infrastructure fully pinned, ensuring that results remain reproducible, comparable across research groups, and stable over time.
