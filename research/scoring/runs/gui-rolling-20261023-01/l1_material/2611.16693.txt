title: MobileProbe: Adaptive Security Evaluation of Mobile Agents via Trajectory-Aware Injection

§Abstract
Mobile GUI agents read the screen of a phone and operate apps on a user's behalf to complete multi-step tasks such as online shopping or messaging. Because the agent acts on whatever the screen shows, an attacker can embed malicious instructions into ordinary UI content and redirect its actions. We refer to this threat as environmental injection attack (EIA). Existing benchmarks measure this risk by pinning hand-crafted payloads to a fixed step of a fixed task. This approach faces two limitations. First, each payload is bound to one task in one app and does not transfer without manual redesign. Second, agents given the same task may follow different routes, so an agent that never reaches the injected page is recorded as safe without being tested. This insufficient test coverage can cause fixed-point benchmarks to underestimate the security risk of deployed mobile agents. In this work, we propose MobileProbe, a trajectory-aware red-teaming framework that evaluates mobile agents adaptively. MobileProbe discovers attacker-controllable content surfaces through automated pentesting, localizes vulnerable decision points along the agent's trajectory, and iteratively refines context-aware payloads through a surrogate-filtered evolutionary loop. We construct a benchmark of 83 long-horizon attack instances spanning 12 mobile applications. Each is annotated with a Confidentiality, Integrity, or Availability (CIA) attack goal to cover the principal categories of security threats facing mobile agents. On three representative agent architectures, MobileProbe attains higher attack success rates than human-written, zero-shot LLM, and prior automated red-teaming baselines adapted to the mobile domain. MobileProbe can serve as a pre-deployment auditing tool to systematically uncover vulnerabilities and inform security hardening of mobile agents.

§Introduction (from cached fulltext; cut at ~9000 chars)
Mobile GUI agents accept natural-language instructions from users and autonomously operate multiple applications on a phone screen to complete long-horizon, cross-app tasks such as online shopping, schedule management, and messaging [ 1 , 2 , 3 , 4 , 5 , 6 ] . Within a single execution chain, an agent may traverse several applications, handle sensitive user data, and take irreversible actions. Because the agent’s decisions rely entirely on perceiving on-screen content, its observation space is inherently exposed to externally controllable material [ 7 , 8 ] . Environmental Injection Attacks (EIA) exploit this exposure: it enables attackers to embed malicious instructions into UI content perceived by the agent, allowing the attack to be mounted solely by controlling app-visible interfaces without access to user inputs or agent internals. Existing EIA security benchmarks for mobile agents [ 9 , 10 , 11 ] follow a static evaluation paradigm: attack payloads are manually authored by security experts and pre-positioned at a fixed step of a fixed task. This paradigm faces two fundamental limitations when applied to long-horizon, cross-app settings. ➠ Instance Specificity: Creating a single attack instance requires a security expert to understand the target task workflow, manually identify a suitable injection page, and craft a payload tailored to the specific app context. The resulting artifact is a one-off product bound to one task within its host app. Transferring it to new scenarios demands substantial redesign, making systematic coverage across multi-step tasks impractical. ➠ Insufficient Test Coverage: As task complexity grows, different agents given the same task follow different execution paths. An agent whose path never reaches the pre-positioned injection point is recorded as “safe”: not because it resisted the attack, but because it was never exposed to it. Fixed injection points do not reliably provide comparable attack exposure across agents with divergent trajectories. Fig. 1 illustrates this path-dependent coverage gap. To overcome these limitations, security evaluation should adopt an adaptive paradigm: both the injection point and the payload should be selected based on each agent’s actual execution trajectory, rather than being statically pre-positioned before evaluation begins. Such adaptivity is essential to simultaneously achieve scalable construction, contextual fidelity, and unified attack exposure across divergent agent behaviors. Implementing adaptive attack generation in the mobile environment faces specific technical constraints. Unlike the web-agent scenario, where DOM manipulation and invisible elements provide flexible injection channels, Android’s application sandboxing makes these techniques unavailable to unprivileged third parties. The attacker’s intervention surface is confined to content rendered by legitimate applications, such as text within emails, messages, or UI components rendered within an attacker-controlled app’s Activity window. Within this constrained surface, automatically generated payloads need to satisfy three conditions for the attack to be feasible. First, the payload should be semantically consistent with the application context; anomalous content is likely to be ignored or rejected by the agent regardless of its underlying instructions. Second, injection should target a step where the agent is about to make a consequential decision , rather than enumerating every step in the trajectory. Most intermediate steps involve routine navigation, where injection is unlikely to induce behavioral deviation. Third, the visual presentation of injected content should be indistinguishable from the host app’s UI components. Based on the foregoing analysis, we propose MobileProbe , a trajectory-aware red-teaming system that enables adaptive security evaluation of mobile GUI agents. MobileProbe overcomes both limitations above through a dual-layer architecture. The Probing & Evaluation Platform handles the infrastructure concerns that are specific to the mobile setting: before evaluation begins, it conducts an automated pentesting pass over each injectable app and normal task to discover potential attacker-controllable content surfaces and encode them as reusable injection templates; During evaluation, the platform hosts the task environment within an Android Virtual Device (AVD) for the target agent to interact with. It injects attack content through a template-driven mechanism that triggers only when the mobile agent reaches a matched page and verifies attack outcomes through task-specific programmatic verification programs. The Red Team Agentic System handles the adversarial reasoning, executing a three-phase attack optimization process on the agent’s realized execution trajectory. ## III Problem Formulation
III-A Threat Model Mobile GUI agents operate in environments where screen content may originate from untrusted sources. Prior work has demonstrated attack vectors against mobile GUI agents: malicious instructions embedded in emails and messages [ 11 ] , deceptive dialog components rendered by repackaged third-party apps [ 10 ] , and adversarial notifications delivered through system channels [ 34 ] . These are all achievable by unprivileged third parties within the default Android permission boundary. Our evaluation targets this class of threats, restricting scope to unprivileged, already-documented attack surfaces. The threat model involves two principal roles: \bullet Target Agent. The target agent is a mobile GUI agent that observes the current screen state at each step and produces GUI actions to advance toward the user’s goal. During execution, the agent uses on-screen content as part of its task context, but lacks a reliable built-in mechanism to distinguish legitimate interface content from adversarially injected material. Attacker-controlled content rendered in the visual interface can therefore affect the agent’s subsequent decisions. \bullet Threat Source. The threat source is modeled as an unprivileged third-party app developer or content publisher: no root or privileged system access, no visibility into the agent’s internals, and no ability to alter user prompts or intercept OS-level communications. The threat source’s intervention surface is confined to attacker-controllable content fields. Locations within the Android environment where third-party content can legitimately appear and be rendered by the agent’s visual perception layer. As a red-teaming framework, MobileProbe is granted two additional privileges at design time: (1) the ability to execute the target agent on a user task and observe its full execution trajectory; (2) root access to the Android emulator for attack content injection and outcome verification. These privileges are used exclusively during attack construction and evaluation, and do not extend to the deployed attack artifact. To identify attack vectors suitable for systematic evaluation, we assess candidate visual injection modalities along three dimensions: (1) Attacker Privilege , whether the attack remains within unprivileged third-party boundaries; (2) Trigger Reliability , whether the payload persists long enough to be captured by the agent’s screenshots; (3) Content capacity , whether the payload can convey complex adversarial instructions. Table I summarizes the assessment. Three candidates are excluded. (1) Overlay Window displays floating UI elements above another app’s interface, but requires the SYSTEM_ALERT_WINDOW permission, which is not granted by default, placing it outside the unprivileged boundary. (2) System Notification delivers content through transient banners that are short-lived and whose preview area is constrained by Android system display limits. (3) UI Identity Spoof forges an app’s icon or name to mislead the agent about which app it is interacting with, but its influence is limited to the app-selection and launch stage. This vector embeds adversarial instructions into ordinary user-visible content such as emails, messages, or social posts, without modifying the hosting application. It represents the lowest intrusive attack setting, where the adversary acts only as a legitimate content publisher. ➠ In-App Fake Dialog. This vector is rendered by a repackaged third-party app within its own Activity window, exploiting the inherent freedom of Android apps to display arbitrary UI elements without additional permissions. By presenting fabricated prompts that mimic legitimate system or application requests, the adversary misleads the agent into executing unauthorized actions. Malicious Text corresponds to content-layer manipulation by a legitimate publisher, whereas In-App Fake Dialog captures UI-level deception within the presentation layer of a potentially compromised application. The two vectors cover complementary unprivileged surfaces: the untrusted semantic environment of external content and the potentially compromised UI environment of third-party applications. III-B Formal Definitions We formalize a Mobile GUI Agent as a sequential decision-making process. Given a user task instance g\in\mathcal{G} , the agent at time step t observes the current screen state s_{t}\in\mathcal{S} and produces an action a_{t}\in\mathcal{A} (e.g., tap, swipe, type) according to its policy \pi:S\to A . The agent’s full execution trajectory is defined as: \tau_{g}=\langle s_{0},a_{0},s_{1},a_{1},\dots,s_{T}\rangle (1) where s_{0} is the initial state, s_{T} is the terminal state, and T is the trajectory length. When the agent navigates to a screen containing content pre-positioned by the attacker, it encounters a corrupted state. We denote the step at which this occurs as k , and define the corrupted state as: \tilde{s}_{k}=s_{k}\oplus\delta (2) where \oplus denotes the rendering operation that superimposes the payload onto the current screen state. Following the encounter, the agent observes \tilde{s}_{k} as the current screen state and produces a deviated action \tilde{a}_{k}=\pi(\tilde{s}_{k}); ; subsequent state transitions arise naturally from \tilde{a}_{k} under the environment dynamics, without further adversarial intervention. The full adversarial trajectory is defined as: \tilde{\tau}_{g}=\langle s_{0},a_{0},\dots,s_{k-1},a_{k-1},\tilde{s}_{k},\tilde{a}_{k},s^{\prime}_{k+1},a^{\prime}_{k+1},\dots,s^{\prime}_{T}\rangle (3) where s^{\prime}_{k+1},\dots,s^{\prime}_{T} are the subsequent states induced by the deviated action \tilde{a}_{k} . The payload \delta is categorized into two types according to the injection vector: Malicious Text ( \delta_{\text{Text}} ) and In-App Fake Dialog ( \delta_{\text{Dialog}} ). Each payload has internal structure along two dimensions. The attack strategy space \Sigma governs the logical mechanism by which the payload attempts to redirect the agent (e.g., operational suggestion, manufactured urgency, or false contextual premises). The stylistic presentation space \Omega governs the surface form, including tone, formatting, and visual arrangement (e.g., plain declarative statements, system-notification formats, or conversational style). The function content(\sigma,\omega) denotes the textual payload generated under attack strategy \sigma and stylistic presentation \omega . Each payload is parameterized as: \begin{gathered}\delta=\text{Render}\left(\text{content}(\sigma,\omega),\;v\right),\\ \sigma\in\Sigma,\;\omega\in\Omega,\;v\in\{\text{text},\text{dialog}\}\end{gathered} (4) where v denotes the injection vector and \text{Render}(\cdot) produces the final rendered payload in the target UI modality. The product space \Sigma\times\Omega constitutes the full structured search space over which the automated attack generation procedure operates; in practice, the injection vector and the content type of the host app at the selected injection point determine the compatible subset (§ IV-C2 ). Each attack instance is associated with an attack objective o_{g}\in\mathcal{O} , specifying the malicious outcome the adversary intends to achieve. Following the CIA security model, attack objectives are categorized into three classes: • Confidentiality ( \mathcal{O}_{C} ): inducing the agent to exfiltrate sensitive user information (e.g., account credentials, private messages, personal data) to adversary-accessible channels; • Integrity ( \mathcal{O}_{I} ): inducing the agent to perform unauthorized modifications to user data or system state (e.g., sending unauthorized messages, altering files, submitting false forms); • Availability ( \mathcal{O}_{A} ): disrupting the agent’s ability to complete the legitimate user task (e.g., interrupting task flows, triggering irreversible actions, locking critical functionalities). Classification follows an intent-first principle: the label is determined by the attacker’s intended outcome, not the surface form of the action. For instance, any action that causes the agent to transmit data to an external channel is classified as Confidentiality regardless of its technical implementation. For a given attack objective o_{g} and adversarial trajectory \tilde{\tau}_{g} , we define the attack outcome via an ordinal compliance function that captures the degree to which the agent’s post-injection behavior aligns with the adversarial objective: R(\tilde{\tau}_{g},o_{g})\in\{0,1,2,3\} (5) where the four levels correspond to Ignored (0), Detected & Refused (1), Partially Followed (2), and Fully Followed (3). The binary attack success indicator is defined as: r(\tilde{\tau}_{g},o_{g})=\mathbbm{1}\left[R(\tilde{\tau}_{g},o_{g})=3\right] (6) The ordinal function R provides a dense feedback signal consumed by the red-teaming search procedure, while the binary indicator r underlies the framework-level effectiveness metric. The overall effectiveness of the framework is measured by the Attack Success Rate (ASR): \text{ASR}(\mathcal{F},\pi,\mathcal{G})=\frac{1}{|\mathcal{G}|}\sum_{g\in\mathcal{G}}r(\tilde{\tau}_{g},o_{g}) (7) Building on the above, we formalize the core problem addressed by MobileProbe as a bounded search over the structured attack space. Given a target agent policy \pi , a task set \mathcal{G} where each task g is paired with a designated attack objective o_{g} , the agent’s benign execution trajectories \{\tau_{g}\}_{g\in\mathcal{G}} , and and an adversarial experience memory \mathcal{M} , that accumulates successful attack patterns across previously evaluated tasks, we seek an automated attack generation procedure: \mathcal{F}_{T_{\max}}:(g,o_{g},\tau_{g},\mathcal{M})\to(\delta^{*},k^{*},v^{*}) (8) where T_{\max} bounds the number of environment-grounded evaluations, and \mathcal{F} jointly produces an injection step k^{*}\in\{1,\dots,T-1\}, , a structured payload \delta^{*}=\text{Render}(\text{content}(\sigma^{*},\omega^{*}),v^{*}) with (\sigma^{*},\omega^{*})\in\Sigma\times\Omega , and an injection vector v^{*}\in\{\text{text},\text{dialog}\} , such that the induced adversarial trajectory \tilde{\tau}_{g} satisfies r(\tilde{\tau}_{g},o_{g})=1 . This formulation maintains a strict separation between design-time and deployment-time operations.
