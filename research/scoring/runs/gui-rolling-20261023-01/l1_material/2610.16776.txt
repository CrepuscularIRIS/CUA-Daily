title: Game-Creation-Agents: Autonomous Game Production

§Abstract
Game-Creation-Agents (GCA) turns a natural-language request into a runnable Phaser 4 browser game. The pipeline first builds a multimodal game design document that couples mechanics and scene contracts to grounded visual references. It then projects that document into a runtime scaffold, machine-readable contracts, and deterministic tests. Eight specialized agents next carry out production: scenes are implemented serially, assets are produced in parallel, and one reduced manifest joins the two branches into a single build. Build-linked real-UI checks and a code-blind critic then verify that build and decide whether the game may ship. Each blocker returns to the agent that owns the affected artifact for a bounded repair, and the game is released once all the gates pass. We evaluate finished games separately, through their rendered interfaces alone, over prompt-matched tasks run under a common protocol. GCA achieves stronger requirement satisfaction, core mechanics, content depth, and functional visuals than a comparable open pipeline. In a side-by-side human study, raters also score GCA's games higher on every dimension and prefer them overall.

§Introduction (from cached fulltext; cut at ~9000 chars)
Large language model agents can now write and revise real programs, and recent work organizes them into pipelines where each agent takes on a role ( Qian et al., 2024 ; Hong et al., 2024 ; Wu et al., 2024 ) . Games are a good target for this, and a hard one. A game is not finished when it compiles and renders. It has to take input, follow its own rules, move through levels and end states, and show the player what is going on, using art that was generated along with the code. One request therefore asks for dozens of things that can be checked, spread across the design, the running code, and the assets. The hard part is that nothing outside the pipeline tells it when it is done. Code generation usually runs against a test suite that already exists ( Chen et al., 2021 ; Austin et al., 2021 ; Jimenez et al., 2024 ) , but a game pipeline has to build its own contracts, tests, and runtime evidence before it can judge what it made. This is the test-oracle problem ( Barr et al., 2015 ) . An agent reporting that a scene works is not evidence that it works ( Huang et al., 2024 ) , and a page that renders can still have broken input, collisions, progression, end states, or interface feedback. Running work in parallel makes it worse: design choices constrain scenes and assets, code and art are produced at the same time but have to match at integration, a repair can touch a file another agent owns, and leftovers from an earlier attempt can look like current output. Without a record of which artifact belongs to which agent and to which build, it is easy to mistake work being done for work being finished. GCA takes a game request in plain language and produces a runnable Phaser 4 browser game ( Phaser Studio, 2025 ) , along with its design package, generated assets, executable tests, and verification evidence. Eight agents split the work, each owning one kind of artifact. The design agent writes a design specification paired with grounded scene concepts, detections, and element crops; together these are the multimodal game design document (GDD) , or multimodal GDD , and everything downstream is built from it. Scenes are then implemented one at a time, while independent asset batches run in parallel. Figure 1 gives the whole sequence, and Figure 2 shows six games it produced. Verification then runs on the assembled game, not on what the agents said about it, and every check is bound to the build it ran against. Because each artifact has exactly one writer, every blocker has a responsible owner, and the repair goes back to that agent rather than to whoever noticed it. A typed Model Context Protocol (MCP) control plane ( Anthropic, 2024 ) enforces both of these rather than leaving them to the agents. We evaluate the finished games from outside the pipeline. The evaluator gets only the prompt and one finished game through its rendered interface. It never sees the multimodal GDD, the trace, the reports, or the critic’s verdict, so the internal gates cannot affect the score. Over prompt-matched tasks scored under one protocol, GCA has higher mean Requirement Satisfaction, Core Mechanics, Content Depth, and Functional Visuals than an open-source baseline ( Jiang et al., 2026b ) , and performs comparably on Art & Presentation. A human study of the same pairs gives GCA higher mean ratings on all five dimensions and a clear majority of decisive preferences. The rest of the report is organized as follows. Section 2 places GCA among prior work on complete-game generation, evaluation and testing, and content generation. Section 3 details the pipeline and Section 4 the MCP control plane. Section 5 reports the automated and human evaluations together with the Gold Miner case, and Section 6 summarizes the findings.
