title: Hybrid Computer Use: A Unified Programmatic, Semantic, and Visual Interface for General Agents
source: https://arxiv.org/abs/2610.41432

§Abstract
Computer-use agents increasingly tackle tasks ranging from everyday desktop activities to long-horizon professional workflows. Yet interfaces centered on screenshots and mouse-and-keyboard actions can impose a human-interaction prior, requiring repeated screen interpretation while leaving the computer's semantic and programmatic capabilities underexposed. We argue for exposing these capabilities and letting models choose and combine them. We introduce Hybrid Computer Use (HCU), a unified interface for general agents that combines three complementary channels: programmatic interaction through code and command-line tools, semantic interaction through accessibility (AX), and visual interaction through graphical user interfaces (GUI). Our HCU supports efficient AX interaction and guards against stale-state actions during channel switching. A supplementary HCU skill guides agents in selecting and coordinating channels to use the unified interface effectively. Our designed AX tools return compact observations, execute actions in batches, and report their effects as AX diffs, so the model needs fewer round trips. On OSWorld 2.0, HCU achieves the highest Partial and Binary scores among the compared systems. Analyzing agent trajectories, we find that all evaluated models improve with HCU yet allocate work across the channels differently and consistently outperform compared baselines in terms of both efficiency and task success, highlighting the value of unified computer-use interfaces that allow flexible channel selection and combination.

§Introduction (from cached fulltext; cut at ~9000 chars)
AI agents are increasingly able to carry out user requests by operating software applications on computers directly. Computer-use research has expanded from everyday desktop tasks in OSWorld 1.0 [ 1 ] to long-horizon workflows and specialized professional software in OSWorld 2.0 [ 2 ] . As tasks become more involved, agents must sustain progress across many operations, making interaction efficiency important alongside task performance. Most existing computer-use interfaces mirror how humans operate software: inspect the screen, locate a UI control, and use the mouse or keyboard. While this approach offers broad coverage with human-like perception and action, it also imposes a strong human-interaction prior on the action space of a frontier Large Language Model (LLM), overlooking more efficient channels for interacting directly with the system. An agent with existing computer-use interface may spend substantial effort precisely locating a field by screen coordinates even when the application exposes its identity and value through accessibility data, or manipulate data through repeated click-and-drag actions when code could process it directly. Modern computer systems offer a wide range of interaction tools that fall into three complementary channels: visual interaction through GUIs, structured semantic access through accessibility APIs, and direct programmatic access through code and command-line tools such as Bash. Accessibility (AX), originally developed for assistive technologies and now also used for automation, exposes application UI controls, their properties, and supported operations [ 3 , 4 ] . Code and command-line tools provide direct access to files, data, and software, while GUI interaction supplies visual evidence and control where structured access is insufficient. Prior work [ 5 , 6 ] combines programmatic and visual interaction but makes limited use of the semantic channel provided by AX. UFO2 combines UI Automation with GUI and application-API execution [ 7 ] , while Tactile exposes semantic actions alongside OCR and visual fallbacks [ 8 ] . CUA Driver, an open-source computer-use interface, supports all three channels but favors AX-based interaction in the background to preserve the user’s active desktop [ 9 ] . We build on these efforts to organize reference-addressed AX actions, in-call wait steps, and post-action feedback for efficient, sustained interaction, while exposing all three channels within a general agent for model-directed selection and combination. We introduce Hybrid Computer Use (HCU), a unified interface for general agents that combines three complementary channels: programmatic, semantic, and visual interaction (Figure 1 ). HCU adds AX and GUI tools to the agent’s own programmatic tools via the Model Context Protocol (MCP), with cross-channel action guards to maintain a consistent view of the current desktop state and an HCU skill to guide the model in selecting and combining the exposed channels. Our designed AX channel lets the model read a compact AX view, act on several targets in one call, and see the resulting changes without a separate observation. Because all three channels act on the same desktop, an action in one can invalidate the evidence held by another; action guards therefore re-check targets and layouts against live state before each input. A supplementary HCU skill explains how to use these tools and when each channel is most effective, helping the model follow the execution and feedback contracts and reduce invocation errors. We evaluate HCU on OSWorld 2.0 and OSWorld 1.0, and further evaluate it on WeaveBench, MacAgentBench, and Windows Agent Arena in Appendix A . On OSWorld 2.0, HCU achieves the highest Partial and Binary scores among compared systems, advancing the performance–efficiency frontier (Figure 1 , right). With GPT-6 Astra , it reaches 72.37% Partial, outperforming CUA Driver by 3.55 points. With Claude Opus 5, it improves Partial by 3.75 points and Binary by 3.76 points over the model’s official leaderboard result, reaching 35.19% Binary at 20% lower Cost. On OSWorld 1.0, HCU outperforms CUA Driver across four other backbone models, each in its own harness, averaging 6.48 more points in Score, 17% fewer Steps, and 30% lower Cost, and reaches 70.13% Score with GPT-5.4 while transferring these performance and efficiency gains to WeaveBench, MacAgentBench, and Windows Agent Arena at roughly half the Cost. Component ablations and tool-call analyses reveal distinct channel preferences across models, yet gains consistently concentrate on tasks that use HCU’s desktop tools. Within tasks, we observe that channels often play complementary roles, with screenshots supporting observation and AX enabling execution. ## Hybrid Computer Use Interface
HCU combines three interaction channels in one agent’s task context: programmatic, semantic, and visual (Figure 2 , top). The programmatic channel uses the agent’s own code, shell, and file tools. HCU adds the semantic and visual channels through two desktop tools exposed via the Model Context Protocol (MCP) [ 23 ] : the AX channel reads application accessibility trees and executes reference-addressed actions, while the GUI channel takes screenshots and sends mouse and keyboard input (Appendix Table 13 ). All three channels act on the same computer. Action guards check AX targets and GUI layouts against live state before input. A supplementary skill explains how to use the interface. The agent uses HCU within its existing observation–action loop. Given the task and available observations, the model chooses a channel to inspect state or act; the selected tool executes the request and returns its result to the same context, from which the model decides whether to continue, inspect further, or change channels. Observation and execution need not use the same channel: a screenshot can supply visual context for a subsequent AX action. Channel selection remains model-directed. HCU adds no planner, subagents, or loop of its own, so the same interface attaches to different agent harnesses (Appendix E.5 ). The following subsections describe the AX channel’s observation, execution, and feedback design (Section 3.1 ), the action guards that support switching between channels (Section 3.2 ), and the skill that explains how to use the interface (Section 3.3 ). Accessibility for Computer Control AX exposes a structured representation that applications or UI frameworks supply for assistive technologies: a tree of elements with roles, names, values, states, and supported operations. It lets an agent identify and operate controls without locating every target in pixels, but using it to control a computer presents three challenges. 1. Coverage depends on what applications expose. Applications choose which properties and operations to expose through AX. Custom-drawn content may have no accessible elements, accessible objects need not map one-to-one to widgets, and virtualized items may be absent until rendered [ 3 , 24 ] . AX therefore provides incomplete coverage of visible content and available interactions. CUA Driver addresses this by returning the tree and a screenshot together by default, so the model can use pixels when AX omits or misrepresents a target [ 25 ] . HCU retains the acquired AX records, marks unavailable information, and lets the model request a screenshot when semantic evidence is insufficient. 2. Changing targets. Controls can share names, move, disappear, or be recreated; AT-SPI explicitly marks defunct objects [ 26 ] . A label or tree position therefore cannot establish identity across actions. CUA Driver instructs the agent to refresh element indices before acting and rejects ambiguous window targets [ 27 , 28 ] . HCU binds target references independently of the displayed view and resolves them against live elements before each action, including actions within a batch. 3. Verifying action effects. AT-SPI reports invocation, which does not establish that the intended state change occurred [ 29 ] . CUA Driver verifies caller-defined postconditions through a separate operation [ 27 ] . HCU lets the agent compose actions and optional AX wait steps in one batch, such as selecting a checkbox and waiting for its checked state before continuing, without a separate verification call. CUA Driver prioritizes best-effort background input to preserve the user’s active desktop, with foreground input available on request [ 9 ] . In contrast, HCU prioritizes completing the requested action, using native AX operations or focused input as needed. Its efficiency-oriented design also gives the agent more control over how work is composed: compact views reduce observation size, while batched actions, optional wait steps, and AX diffs let the agent combine execution, verification, and state feedback within a single call. Composable Semantic Interaction These properties motivate an AX interface that lets the agent compose actions while HCU validates targets, runs requested wait steps, and returns evidence for continuation. Figure 2 (bottom) illustrates this interaction: a compact AX view supplies target references, a batch combines actions with optional wait steps, and post-action feedback supports the next decision. Compact AX views and target references. HCU separates the AX records it retains from the compact AX view shown to the model. It removes structural wrappers and condenses repeated content in the view while retaining the acquired records for target identification and state comparison. Target references are bound to elements before this compression, so shortening the view does not change which element a reference identifies. The retained records also support AX diffs after an action, while find and scoped observations let the model retrieve targets omitted from the compact AX view. Appendix E.2 gives same-capture examples and measures the reduction in tokens. Batched actions and wait steps. HCU lets the agent compose known actions and optional AX wait steps in a single call. The act mode executes the steps in order within one application window, checking each target with the AX target guard before input (Section 3.2 ). A wait step sends no input and holds until an expected state appears, such as a checkbox becoming checked or a dialog opening, before later steps run; placed last, it verifies the final state. This combines batching, also used for GUI interaction [ 6 ] , with state verification akin to Playwright assertions [ 30 ] . If an action fails, a wait times out, or window continuity is lost, HCU stops the batch and reports the stopping point and execution evidence. This lets the agent decide how to continue without blindly repeating earlier actions. Post-action feedback. HCU returns per-target effect summaries and an AX diff by default after an action call, showing changed values, window changes, and target references relative to the last eligible observation delivered to the model. The agent can instead request a screenshot or execution evidence only, according to what it needs for its next decision. Returning this feedback with the action lets the agent continue without a separate observation when the information suffices (traces and samples in Appendix Figure 16 and E.3 ). HCU reports only what the available evidence supports, so the agent is not led to treat input delivery as a verified effect. Like CUA Driver [ 27 ] , it distinguishes known non-delivery from an unknown effect after possible input. The agent uses this distinction and the returned continuation instructions to decide whether to retry, inspect state, or stop. Guarding Actions Across Channels The model observes the desktop through discrete tool outputs rather than a continuous view of its state. After an action, it may not know which earlier observations remain valid, especially when combining channels. An AX action may open a dialog over coordinates from an earlier screenshot, or a GUI action may replace a control addressed by an AX reference. Reusing that evidence can send input to an unintended target without the model noticing. HCU therefore leaves channel choice to the model while using action guards to check the targets and layouts on which its actions depend immediately before input (Algorithm 1 ). The AX target guard resolves each target reference immediately before execution and checks the element’s identity and action-specific requirements. If the target is missing, ambiguous, or replaced, or an action-specific requirement is not met, HCU rejects the action without sending input. It does not redirect the action to a similarly named element. The GUI layout guard checks whether the layout underlying the model’s chosen coordinates still matches the last screenshot. Before coordinate input, it compares the current desktop bounds, visible top-level windows, stacking order, active window, and target-point window layout with those associated with that screenshot. If the layout has changed, HCU blocks the affected input and returns a fresh screenshot so the model can choose new coordinates. Both guards inspect current state regardless of which channel changed it, including earlier actions in the same channel. Detected mismatches lead to explicit rejection before input, allowing the model to revise its next action (Appendix E.4 ; recorded rejection in Figure 18 ). Skill for Effective Interface Use HCU provides a supplementary skill that explains how to choose and compose the interface’s capabilities. We distilled its instructions from recurring mistakes in development trajectories, including malformed arguments and misused target references, following the trajectory-informed refinement of usage instructions in SWE-agent [ 15 ] . The skill addresses three aspects of interaction: (1) Channel capabilities. The skill explains what programmatic, semantic, and visual interaction can provide, including their observation scope and limitations, so the model can decide which channels to use and combine for the task. (2) Efficient interaction. It explains how to use target references, batch known actions with wait steps, and continue from returned feedback, requesting additional observations only when needed. (3) Verification and recovery. It distinguishes input delivery, local UI changes, and task outcomes; explains how to verify saved or applied results; and describes how to recover from stale targets, invocation errors, or insufficient evidence. The skill makes these instructions concrete through rules for common invocation and recovery mistakes, while the tool schemas define argument shapes. It contains no task-specific solutions; Appendix F.2 presents its text. The skill ablation in Section 4.3 shows reduced invocation errors and improved interaction efficiency; Appendix B.1 describes instruction integration.
