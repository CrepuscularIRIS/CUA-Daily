title: 3DCodeEdit: Benchmarking Instruction-Guided 3D Program Editing
source: https://arxiv.org/abs/2610.38231

§Abstract
Language models increasingly create 3D content through code, with practical workflows often relying on editing existing programs rather than regenerating them, for speed and precise control. Such edits require understanding what a program builds and foreseeing how a change reshapes it, yet prior benchmarks mostly evaluate generation or simple edits against a reference. In this paper, we introduce 3DCodeEdit, a benchmark of 2,592 instruction-guided editing tasks over 108 Blender programs that construct objects entirely in code. Its edits range from parameter to structural changes, style redesign, and scene composition, and are judged from renders against human-reviewed checklists. Across 17 models, the average success rate is only 37%, and even the strongest models complete fewer than 60% of structural and style edits. As models become more capable, their failures shift to geometric foresight, where the code runs but builds the wrong shape. We therefore study whether multi-turn feedback can compensate for this missing foresight. Feedback from a separate reviewer model that describes how the renders differ from the request helps most, more than maximum reasoning effort or an agent harness, and can let a 27B model surpass the single-shot rate of a 2.8T-parameter model.

In end-to-end code , the program builds the entire object; complex code indicates an average program length exceeding 200 lines (Appendix B ); reference-free evaluation judges edits against the instruction rather than a reference output. Code is becoming a common way to represent 3D assets. Procedural generators define objects as programs ( Raistrick et al., 2023 ) , game engines define reusable assets as parametric classes ( Epic Games, 2026 ) , and frontier models now build objects by writing Blender programs ( Anthropic, 2026a ; OpenAI, 2026b ) . Once written, such a program is revised many times, as users refine the asset, adapt it into variants, or update it to new requirements. A user who has generated an armchair, for example, may later want a taller backrest, or want to turn it into a rocking chair (Figure 1 c). Editing the program is faster than regenerating the chair, and it changes only the requested parts while keeping the rest intact. Such an edit is demanding because the instruction describes how the object should look, while the model can only change the code. The model must work out from the code what shape it builds, foresee how a change will reshape it, and write renderable code that makes exactly this change. The task therefore requires multimodal understanding and foresight that link code to 3D geometry, on top of code editing. Even as code generation improves rapidly ( Chen et al., 2021 ; Jimenez et al., 2024 ; Deng et al., 2026 ; Merrill et al., 2026 ) , frontier models still struggle with instructed code editing ( Cassano et al., 2024 ; Chi et al., 2026 ) and with spatial reasoning ( Fu et al., 2024 ; Yang et al., 2025b ; Yang et al., 2026 ; Liu et al., 2026a ) . For example, a model may break the structure of the existing program so that it no longer runs, or, failing to foresee the result of its change, write code that runs but builds the wrong shape, such as a new part floating in the air, disconnected from the object ( Gao et al., 2026 ) . A benchmark for this kind of editing should meet three requirements. First, the program should build the entire object in code, exposing its parameters and parts to the edit. An object stored in a pre-built scene file or as raw mesh data leaves nothing meaningful to edit. Ideally, the programs are also larger, more complex, and diverse, so that the shape cannot be read off at a glance. Second, the edits should range from local changes to structural and open-ended ones, which capture more edit types in practice and also require foreseeing more of the geometry. Third, each edit should be judged from renders on whether the requested change is made and the rest preserved, without relying on a reference output. An instruction rarely fixes a single outcome. Even “make the backrest taller” can be met at many heights, and open-ended edits, common in real-world editing, admit far more. However, existing benchmarks either evaluate generation from scratch ( Du et al., 2024 ; Gao et al., 2026 ; Liu et al., 2026b ; Noor et al., 2026 ) or edit objects in pre-built scenes against a reference output ( Gu et al., 2025 ; Yin et al., 2026 ) (Table 1 ). To fill this gap, we introduce 3DCodeEdit, a benchmark of 2,592 instruction-guided editing tasks over 108 Blender programs (Figures 1 and 2 ). Each program builds its object entirely in code. Besides procedurally generated objects, the programs include designs of buildings, furniture, and mechanical parts shared by designers online, which we reconstruct as editable Blender programs through an agent loop grounded in renders. Building on these programs, we design six edit types: four geometric types graded by scope, from a single parameter to the structure of the whole object, and two open-ended types, style redesign and scene composition. The editor sees only the program and the instruction. An edit succeeds only if its code runs and renders, and it passes a human-reviewed checklist, with one item per requested change and one for preserving the rest, as judged by a multimodal verifier that compares renders of the original and edited objects. We evaluate 17 models and find that editing remains hard, and gets harder with scope.
