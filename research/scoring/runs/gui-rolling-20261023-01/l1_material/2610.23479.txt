title: HexaShell: A Universal Harness for Robot Coding Agents in Simulation and the Real World
source: https://arxiv.org/abs/2610.23479

§Abstract
Agents built on vision language models (VLMs) now control robots by writing code, but the strongest of them refine task-specific code over many rounds of trial and revision. Such code tends to overfit the benchmark on which it was tuned, can exploit the benchmark's shortcuts, and is costly to carry over to a new benchmark or robot. We present HexaShell, a thin, task-agnostic harness designed to test how far general tools can go instead. We design a simple and complete set of 14 basic tools, 4 for motion, 5 for perception and 5 for state, which the agent calls in one Python cell per turn. Perception pairs SAM 3, which segments an object from a few words or a click, with NumPy and OpenCV geometry that turns its outlines in several cameras, or a depth image, into its position, size and grasp angle. The API, agent loop and sandbox are shared across all tasks; a new simulator or robot needs only an adapter of 350 to 1,450 lines and a prompt describing its world, and the only task-specific input is an optional skill of about a page of guidance. The same code runs on four simulated benchmarks, built on three simulators with two kinds of arm, and on real robots. With GPT-6-Astra and no task-specific input, HexaShell reaches success rates of 69.9% on RoboDojo, 59.3% on RoboCasa365, 78.3% on LIBERO-PRO and 82.2% on RoboTwin 2.0. With task skills, it reaches 85.0% (score 88.8), 85.6%, 96.7% and 96.8%, respectively, above the best published result we are aware of on each benchmark. The RoboCasa365 result is listed first on its leaderboard. On real dual-arm robots, HexaShell succeeds in 76 of 90 episodes across nine tasks.

§Introduction (from cached fulltext; cut at ~9000 chars)
Vision language models (VLMs) that write code can control robots: given a task and camera images, the model writes a program against the robot’s interface, executes it and observes the outcome [ 48 , 70 , 38 ] . Used in this way, frontier models now rival learned policies on manipulation benchmarks without a single demonstration [ 88 , 69 , 21 ] . Their performance, however, depends to a large extent on the harness that connects the model to the robot. With the same model, GPT-6-Astra, the RoboDojo team’s agent reaches a success rate of 22.5% on RoboDojo [ 88 ] , whereas ours reaches 69.9%. Building such a harness poses two challenges. The first is spatial grounding. The model perceives objects as pixels, yet every motion requires a position accurate to about a centimetre, and VLMs judge such distances poorly [ 15 , 22 ] . The second is task knowledge: what counts as completion, how deep a plug must be seated, which arm should move first. Existing approaches place this burden at different levels. Vision-language-action models learn both from demonstrations collected for each task and robot [ 12 , 43 , 9 ] . Code-as-policies systems expose a fixed set of hand-written primitives, which the model composes into a program for each instruction [ 48 , 38 ] . The strongest agent systems instead accumulate tools, programs or memories for the tasks they encounter, often through many rounds of trial and revision [ 35 , 45 , 71 , 53 ] . Such task-specific code is costly to develop and difficult to audit, and it tends to fit the scenes on which it was developed. Our earlier exploration, HexaShell-TaskTools (HexaShell-Preview), illustrates the problem: an optimizer agent wrote about 78,000 lines of task tools for RoboDojo over 769 rounds, yet once frozen, these tools passed only 36% of the development episodes on which they had been built ( Section 3.4 ). In this work we study how far a harness can go when nothing elaborate is written for any individual task. Our approach rests on an observation about where coding agents fail: most of what they lack is not specific to a task. They need to know where objects are, to verify a motion before committing to it, and to receive clear feedback when something goes wrong, and these needs are common to all tasks and robots. The task-specific remainder is small: a success condition that the instruction leaves implicit, a parameter that only contact reveals, an order of steps. This suggests a division of labour in which general capabilities are implemented once, as shared and tested code, while task knowledge is conveyed in a short natural-language skill. We present HexaShell, a harness built on this division ( Fig. 2 ). A single robot API, agent loop and sandbox serve every task in every setting; at each turn the model writes one Python cell against the API and reads its output. Perception is decomposed into segmentation and localization. SAM 3 [ 14 ] determines which pixels belong to an object, and geometry implemented with NumPy and OpenCV determines where those pixels lie in the world, by matching outlines across calibrated cameras or back-projecting a depth image, so that the VLM never has to estimate a distance. The API is designed with a language model as its user: motions can be checked before they are executed, results report problems first, and errors state what to change. Porting to a new simulator or robot requires only an adapter below the API and the text of the prompt. Task-specific input is limited to an optional skill, about a page of guidance that an analysis agent drafts from the records of earlier runs and a person reviews. We evaluate HexaShell on four simulated benchmarks, RoboDojo [ 20 ] , RoboCasa365 [ 59 ] , LIBERO-PRO [ 92 ] and RoboTwin 2.0 [ 19 ] , which together span three simulators, two kinds of arm, fixed and wheeled bases, and cameras with and without depth, as well as on real dual-arm PiPER-X robots. Without any task-specific input, HexaShell reaches a success rate of 69.9% on RoboDojo, above every entry of its leaderboard, and in nine episodes out of ten it writes no vision code of its own. With task skills, it reaches 85.0% on RoboDojo, 85.6% on RoboCasa365, 96.7% on LIBERO-PRO and 96.8% on RoboTwin 2.0, above the best published result we are aware of on each benchmark ( Fig. 1 ). The gains from skills stem from a few facts per task. The remaining failures are dominated by grasps that slip, which originate below the API and lie beyond the reach of any skill. Our main contributions are as follows. • Simple and complete general tools. We design a simple and complete set of general tools, shared by all tasks, through which the model acts by writing Python: goto moves an arm, find segments objects, measure locates them in 3D and state reports the arms and the remaining steps.
