arxiv: 2610.33636 (2610.33636v1)
title: Build or Adopt? Custom-Built vs. General-Purpose LLM Agent Harnesses for Automotive GUI Testing
source: https://arxiv.org/abs/2610.33636

§Abstract
As general-purpose LLM agent harnesses mature, organizations must decide whether to continue developing in-house systems or adopt existing alternatives. We study this decision at Volvo Group for GUI testing of Android-based in-vehicle infotainment (IVI) systems. We compare a production, custom-built harness with two general-purpose harnesses, Claude Code and OpenCode, keeping the tools, accessed through the Model Context Protocol (MCP), and the models the same. We evaluate the harnesses with up to four models on Volvo's IVI test cases and on open-ended tasks in public apps (Google Maps, Booking.com), and interview ten practitioners: developers, the product owner, and testers. On Volvo's stepwise IVI tests, general-purpose harnesses match the custom-built harness in success but vary more across runs. Their inference cost per task is 2.6-10.7 times higher, yet the engineering effort they save outweighs this: for a nightly IVI regression suite, total monthly cost, including engineering effort and inference, is 3-66% lower. On open-ended public-app tasks, they succeed more often, mainly because they recover better from incorrect actions. Interviews suggest that external advances can turn an in-house harness into technical debt even without deterioration. Adopting a general-purpose harness shifts maintenance from the agent loop to tools and instructions, but gives teams less control over what the model receives. Regardless of the harness, testers want to inspect the agent's actions and ensure that it follows the prescribed test scenario.

§Introduction (from cached fulltext; cut at ~9000 chars)
Graphical user interface (GUI) testing of Android-based in-vehicle infotainment (IVI) systems is labor-intensive. These systems are stateful, depend on the state of the vehicle, and change with every software release; scripted tests break whenever the layout changes [ 1 ] , and manual testing does not keep pace. Large language model (LLM) agents address this by executing natural-language test intents directly on the device, interpreting the screen rather than relying on static identifiers. When LLM agents first emerged, no capable general-purpose harness , i.e., the software that turns a foundation model into an agent, existed, forcing organizations like Volvo to build their own, as for automotive software release analytics [ 2 ] . These in-house systems are custom-built , relying on code to strictly define the agent’s control loop, prompt construction, and subagent routing. Research on LLM agents for mobile GUIs has followed the same route. Testing agents such as GPTDroid [ 3 ] and DroidAgent [ 4 ] explore apps or pursue test intents through purpose-built memory and planning, and task-automation agents such as AutoDroid [ 5 ] , AppAgent [ 6 ] , and Mobile-Agent [ 7 ] engineer UI representations, app-specific knowledge, and dedicated planning, decision, and reflection agents. These works evaluate new harness designs on benchmarks; to our knowledge, none compares a custom-built harness with a general-purpose one or examines what maintaining it entails in industrial practice. Building such a harness is an investment in technical credit [ 8 ] , i.e., a design decision that requires higher initial effort in return for long-term benefits, but its value depends on an ecosystem that changes quickly. New model generations alter the agent’s behavior, new requirements, such as operating several devices in one test, go beyond the original design, and both require revising the harness. Meanwhile, general-purpose harnesses, such as Claude Code [ 9 ] and OpenCode [ 10 ] , have matured. They run a generic agent loop maintained by their vendors and can reach domain-specific tools through the Model Context Protocol (MCP) [ 11 ] , which would shift the in-house workload from maintaining an agent loop to maintaining tools and instructions. Thus, technical credit can turn into technical debt without any decay of the system itself. As a result, organizations with in-house agents face a build-versus-adopt decision. However, it is unknown whether a general-purpose harness can replace a custom-built one in industrial testing, what the move costs in operation, and what it changes for the engineers who maintain the agent and the testers who rely on it. We study this decision at Volvo Group. Our key design choice is to vary only the harness: we keep the tools and device access of Volvo’s production agent, use them in both the in-house custom-built harness and vendor-maintained general-purpose ones, such as Claude Code and OpenCode, which access them through an MCP server, and run all harnesses with the same models. As a result, differences between the setups reflect the harness rather than the tools or the model. We evaluate the setups across four models on 66 tasks derived from Volvo’s IVI test cases and on 56 open-ended tasks from the AMEX dataset [ 12 ] , repeat every run to measure flakiness, and interview ten practitioners: four developers, the product owner, and five testers. We address four research questions (RQs): • RQ1 (Effectiveness): How effectively do general-purpose harnesses execute intent-driven Android GUI tests compared with an in-house, custom-built harness using the same models? • RQ2 (Lock-in and robustness to change): How robust is each harness’s effectiveness, without adaptation, to a change of the underlying model or the application under test? • RQ3 (Maintenance and cost): How does transitioning from an in-house, custom-built harness to a general-purpose one change the team’s maintenance responsibilities and technical debt, and at what operational cost? • RQ4 (Stakeholder perspectives): What do the stakeholders of the in-house testing agent value in it, and which of these qualities are preserved or put at risk by moving to a vendor-maintained harness? This paper makes the following contributions: • An industrial comparison that varies only the harness: a production, custom-built harness against two general-purpose harnesses with the same tools and models, on 66 IVI and 56 public-app tasks, covering effectiveness, flakiness, robustness to model and application change, latency, and inference cost (RQ1–RQ3; Sections III and IV ). • An interview study with ten practitioners (developers, the product owner, and testers) that identifies ecosystem-induced technical debt and shows how adopting a general-purpose harness redistributes maintenance and control (RQ3, RQ4; Section V ). • A total-cost estimate combining engineering effort and inference cost, and lessons for practitioners who decide whether to keep or replace [...]

## II Problem Formulation
We model autonomous Android GUI testing as a sequential decision process [ 13 ] in which an agent executes a natural-language test intent G through a sequence of UI actions. At step i , the UI state S^{(i)}=\langle V^{(i)},X^{(i)}\rangle consists of a visual state V^{(i)} , the rendered screen captured as a screenshot, and a structural state X^{(i)} , the XML view hierarchy, whose nodes carry semantic properties such as content-desc , resource-id , and class . The central difficulty is relating the two representations: tool calls target elements of X^{(i)} , whereas the agent interprets the screen through both. A visible element may carry no semantic text in the hierarchy, such as an icon in an empty FrameLayout ; the hierarchy may contain nodes that are off-screen or covered; and the two representations can disagree about an element’s state, e.g., whether a media control is playing. In such cases, neither representation alone suffices, and a mismatch leads the agent to act on the wrong element or misjudge the state of the app. An action a_{i}=\langle\tau,\rho\rangle\in\mathcal{A} combines an action type \tau\in\{\text{TAP},\text{SCROLL},\text{TYPE},\text{PRESS\_BACK},\dots\} with its parameters \rho , e.g., coordinates derived from an element’s bounding box in X^{(i)} . A policy \pi selects the next action from the current state, the intent, and the history H^{(i)}=[(S^{(0)},a_{0}),\dots,(S^{(i-1)},a_{i-1})] , i.e., a_{i}=\pi(S^{(i)},G,H^{(i)}) . Because Android UIs are asynchronous, the transition \mathcal{T}(S^{(i+1)}\mid S^{(i)},a_{i}) is stochastic: if the agent acts before an animation or screen transition has finished, it may reach an unintended state. This stochasticity is one source of the run-to-run variation that we measure as flakiness (Section IV-A ).

## III System Architecture
In this section, we describe the testing system that Volvo has developed and used in production, and the direction we explore for its evolution. We use the term harness for the software around a foundation model that turns it into an agent [ 14 ] : the control loop, the prompts, the context given to the model, and the tools it can use. In a custom-built harness , the harness code defines the workflow: the steps, the routing between agents, and which specialist agent runs when; the model works inside decision slots designed by the developers. In a general-purpose harness , a single generic loop with broad tools lets the model decide what to do next and when to delegate work to subagents; such a harness is adapted to a domain not by changing its loop, but through outer-harness components such as instruction files, MCP servers, and skills. The two kinds differ in where the decisions are made: in the harness code or by the model. Setup A, which we designed and deployed for intent-driven GUI testing at Volvo, is based on a custom-built harness (Section III-A ). Setup B keeps the tools of Setup A but replaces its harness with a general-purpose one, that of Claude Code [ 9 ] or OpenCode [ 10 ] , configured through an instruction template and an MCP [ 11 ] server (Section III-B ). Fig. 1 shows both setups. As the tools are the same, both setups share the state representation S^{(i)} and the action space \mathcal{A} of Section II ; they differ in the policy \pi that selects the next action and in who maintains the code that implements it (Section III-D ). III-A Setup A: Based on a Custom-Built Harness Setup A is in production use at Volvo: testers write their test cases against it, and an internal team of developers maintains it. Its primary agent follows the ReAct pattern [ 15 ] in a loop of four fixed steps (Fig. 1 , left). In each iteration, it takes exactly one action, returns its decision in a typed format that includes an explicit checklist, and reports completion through a dedicated output field. This prescribed loop is what distinguishes the custom-built harness from a general-purpose one. Step 1: Observe. The harness captures a screenshot and dumps the view hierarchy through device tools (Section III-C ). It simplifies the hierarchy by keeping only nodes that are interactive or display text, and only the attributes needed to identify an element and judge its state: text, content description, resource identifier, bounds, and the flags checked , selected , and enabled . The primary agent is instructed to judge an element’s state from these flags rather than from the screenshot, and to verify it with a tool when the two disagree. The harness does not align visual and structural elements explicitly; it provides both to a multimodal model and relies on the model’s reasoning to align them. Step 2: Reason. A single LLM call returns an updated checklist that decomposes the intent into atomic UI steps [ 16 ] , a judgment of whether the intent is fulfilled, and the next tool with its arguments. All LLM calls in the harness use zero-shot chain-of-thought prompting [ 17 , 18 ] . Steps 3–4: Validate and act. The harness checks that the selected tool exists and validates its arguments against a schema derived from the tool’s signature. An invalid call is recorded as a failed step; a valid one is invoked as a local Python function of the shared tool layer, and its outcome is recorded in the step log. Instructions and history. The harness rebuilds the prompt from scratch at every iteration. Besides the intent and the current observation, i.e., the screenshots before and after the last action, the simplified view hierarchy, and the foreground app and screen, the prompt contains instructions and history. The instructions are fixed: the system prompts, the tool descriptions, and a list of domain hints, such as how long to wait for a pop-up dialog. The history consists of the step log, which records the purpose, tool, arguments, and outcome of every previous action and realizes H^{(i)} , and the checklist. Thus, the harness itself decides what the model sees: earlier steps survive only as entries in the step log, and only the screenshots around the last action are included. Run records. For every run, the harness produces a report with the screenshot, reasoning, checklist, and action of each step, a log of every prompt and response, and a trajectory that links the primary agent’s run to those of its subagents. These records are the main means of diagnosing whether a failed run reveals an app defect or an agent mistake. III-B Setup B: Based on a General-Purpose Harness We explore Setup B to reduce Setup A’s maintenance burden. We keep the tool layer and device access of Setup A and replace only its primary agent with one built on the harness of Claude Code or OpenCode. Both were built for software development, but their harness is not specific to coding. Setup B adapts it through two outer-harness components: an instruction template and an MCP server through which the primary agent reaches the shared tool layer (Fig. 1 ). The instruction template is identical for every test and shared by both harnesses. Besides a few general rules about our test environment, such as which device to use and that tasks run in installed apps rather than in a browser, it prescribes a general workflow: observe the screen before acting, take element bounds from the hierarchy rather than guessing coordinates, and perform and verify one action at a time. Primary agent. The primary agent receives the intent, the tools, and the instructions, and decides by itself how to accomplish the task. Its harness imposes no fixed steps or decision format: at each turn, the model calls the tools it chooses, reads their results, and decides whether to continue, including when to observe the screen again and when the task is complete. The history of the run is the conversation context, which accumulates every tool call and its result and which the harness condenses when it grows long. Both the loop and the context management are maintained by the vendor and adapted to new models as they are released. Like Setup A, Setup B is a multi-agent system: the primary agent can delegate work to subagents of its own, and its intent-based tools are executed by the subagents of the shared tool layer. MCP server. An MCP server exposes tools to an agent, each with a name, a natural-language description, and a schema for its arguments. Our server exposes the shared tool layer (Section III-C ). Every action tool returns the simplified hierarchy before and after the action, so the agent can verify its effect without a separate observation call. The server reuses the tools of Setup A but none of its orchestration: which tool to call, when, and when to stop are left to the primary agent. III-C Shared Tool Layer and Device Access The tool layer is the same code in both setups: Setup A invokes its tools as local Python functions, and Setup B through the MCP server. Both access the device through uiautomator2 [ 19 ] , which drives Android’s UI Automator framework over the Android Debug Bridge (ADB). Device tools interact with the device without involving an LLM. Two serve observation: one captures a screenshot, and one dumps the view hierarchy as an XML tree, which is simplified as in Setup A; together, they provide V^{(i)} and X^{(i)} . The others act through a single gesture or key event: tap, swipe, drag, set a slider, and press the home or back key. Tools that target an element take its bounding box from the hierarchy and compute the gesture coordinates themselves, e.g., the center of the box for a tap. Subagents perform subtasks that require several interactions or task-specific reasoning: scrolling to an item in a list, entering or clearing text, setting a number picker, and waiting until a condition holds on screen. The primary agent delegates such a subtask with a natural-language intent, such as “scroll to find Developer options and tap it”. Each subagent has its own specialized prompt and LLM context and returns only the final result, which keeps intermediate screens out of the primary agent’s context. Because subagents call an LLM, their behavior, unlike that of device tools, depends on the underlying model. III-D Maintenance and Ownership Moving from Setup A to Setup B changes who maintains what. In Setup A, Volvo maintains the entire stack, from the primary agent to the device layer. Its control loop, prompts, and construction of the context are designed and tuned together for the models in use. When the backbone model is replaced, the same harness can behave differently [ 20 ] : a new model may decompose an intent differently, declare completion earlier or later, or repeat an action where its predecessor did not. Therefore, keeping the harness effective across model updates requires revising these components, and this effort recurs with every model generation the team adopts. The same holds for new requirements: supporting a new feature or test concept requires the team to develop and extend the harness itself, i.e., its prompts, domain hints, and often its tool set or the routing between its agents.
