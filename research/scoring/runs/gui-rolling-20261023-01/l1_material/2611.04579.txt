title: FreeForm Harness: A Mobile-Native Agent Harness for Open and Composable Extensions
source: https://arxiv.org/abs/2611.04579

§Abstract
Mobile phones support many everyday agent tasks, but current mobile agents bundle capabilities into monolithic pipelines with no open recombination point. Users and third parties cannot publish, install, and compose new behaviors, leaving personalized daily-life requests underserved. We argue that the missing piece is a substrate: although phones are the Web's dominant access point, open publication and composition under decentralized authorship stop at the agent harness. We present FreeForm Harness (FFH), a mobile-native agent harness for open, composable extensions. A frozen base and a permanence-aware required layer handle mobile constraints, including location, proactive triggering, and scarce channels. A uniform plugin contract makes independently authored extensions composable, checkable, and replaceable over a frozen socket set. FFH also supports end-user authorship through a tiered commissioned-authoring path. When no existing extension matches a user's intent, a Web coding agent generates a candidate artifact, which is validated and admitted on device under the same contract as other extensions. An Android prototype spans device, market, and cloud. Evaluation shows that architectural boundaries are enforced at runtime; realistic daily-life requests fit the declared composition space without widening it; and user intent reaches on-device execution through retrieval or commissioned authoring, with final trust decisions remaining device-local. FFH advances the agentic Web from "everything is a plugin" toward "everyone is a developer" on mobile.

§Introduction (from cached fulltext; cut at ~9000 chars)
“Remind me to pick up my package when I’m almost home.” A phone already has the needed pieces. It can track location, receive delivery notifications, keep state for hours or days, and show a reminder through a banner, widget, or badge without interrupting the foreground app. What is missing is not capability but an open recombination point . Today’s mobile agents expose these capabilities only through fused pipelines. Users cannot install a new behavior that combines them differently, and third parties cannot publish an extension that others can install. This gap reflects a broader long tail of everyday requests: remind me to buy milk when I pass a supermarket; if rain is forecast and I am still outside, tell me to head home; fill my walk to work with financial news interleaved with navigation prompts. These requests reuse many of the same building blocks, but combine them differently for different users. No vendor can pre-build this long tail, because it is precisely the space of user-specific combinations. The problem is therefore architectural. More and more value now reaches the user through Web services, but it is finally combined and acted on at the device edge. The phone is the Web’s dominant access point, yet the Web’s defining property, open publication and composition under decentralized authorship, stops at the agent harness. Current mobile agent systems provide no open point at which a third party can publish an extension, have it discovered, verified, admitted, and executed on another user’s device without vendor permission. The missing piece is not simply a better mobile assistant. It is a mobile harness that carries Web openness all the way to on-device agent execution. Two requirements follow. First, the extension surface must be open : parties other than the vendor, in principle including the user, must be able to author new behaviors. Second, composition must remain general : because the long tail comes from recombining shared capability pieces in user-specific ways, the architecture cannot hardwire only a small set of favored combinations. Mobile agents therefore need open and composable extensions . Current systems still fall short of both. End-to-end mobile GUI agents such as AppAgent ( Zhang et al., 2025c ) , Mobile-Agent-v3.5 ( Xu et al., 2026 ) , and MobiAgent ( Zhang et al., 2025b ) package capability inside fused pipelines. Some are modular internally, but their parts are not externally installable or replaceable at runtime. Siri and Google Assistant do expose selected mobile behaviors, including location-based reminders, but only as built-in features. More registry-oriented systems move closer to modularity, but authorship remains developer-centered and admission remains tied to a managed registry rather than an open extension surface. On the desktop, DeepSeek Harness and Cordis ( Shi et al., 2026 ) show an important alternative: an agent can be organized as a plugin substrate rather than as a monolithic assistant. But the mobile case is harder. The long tail here is personal, context-sensitive, and shaped by user-specific choices of trigger, data source, output modality, and threshold. On mobile, the plugin-substrate line should extend from everything is a plugin toward everyone is a developer : users should be able to state intent, have the system commission the missing extension on their behalf, and still admit the result under the same on-device contract discipline as any other plugin. The difficulty is that mobile openness cannot come from making everything optional. Three constraints become central once the authoring surface opens: location and mobility , proactive triggering , and scarce channels and exclusive resources . Location is a changing execution context; trigger commitments must survive process death; and independently authored extensions may compete for the same presentation slot or platform-level exclusive resource. If each extension handles these constraints itself, the result is duplication, interference, and lost continuity. Mobile openness therefore requires always-present infrastructure that absorbs these constraints once so that behaviors above it can remain open. We present FreeForm Harness (FFH) , a mobile-native agent harness for open and composable extensions . FFH separates what must always be present from what should remain freely replaceable through three layers: a frozen base L_{0} , a replaceable-but-permanent required layer L_{1} , and an open extension layer L_{2} for independently authored plugins. A uniform plugin contract spans L_{1} and L_{2} , keeping extensions composable, checkable, and replaceable, while L_{1} absorbs location, proactive triggering, and scarce-resource contention through always-present authorities. FFH also extends openness from third-party publication to end-user commissioning. Users can install, compose, and replace extensions directly.
