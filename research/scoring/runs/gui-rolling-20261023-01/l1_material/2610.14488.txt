title: Names Are Not Objects: Object-Bound Confinement for Compromised AI Coding Agents
source: https://arxiv.org/abs/2610.14488

§Abstract
Coding agents read repositories and web pages that anyone can write, and then act with their user's authority. Prompt-injection defenses make it less likely that the model is steered but do not prevent it, so the system around the model must contain an agent that is already compromised. Many exploits against deployed coding agents share one cause: a check approves a name, such as a path, an argument vector, or a directory, and a later step maps that name to a different object: the file behind a symlink, the behavior an option selects, or a repository that git discovers on its own. We present Zero-Trust Agent Cells (ZTAC). A cell runs the agent in a kernel sandbox whose only route to files, programs, and the network is a socket to a broker. The broker resolves each request to the object it will act on, decides on that object, and checks at use that it is acting on the object it authorized. Programs that the broker starts run in a sandbox compiled from the same policy, and approvals are bound to the resolved object and can be used once. Our macOS prototype has 3.2k lines of trusted Rust code, excluding dependencies. We evaluate it against 74 attacks with ground-truth oracles, including replays of 10 publicly disclosed incidents. A tool allowlist loses 66 of them, and an allowlist combined with the kind of command sandbox that deployed agents use loses 56. ZTAC loses 2, both of which encode a secret into traffic to an allowed endpoint, and holds 14 for review. It completes 43 of 46 benign operations, with 8 approval prompts, and 4 of 7 workflows. A no-op brokered request has a median latency of 4.0 ms, and the spawned programs we measured take 8.5 ms to 18.4 ms longer than without ZTAC.

§Introduction (from cached fulltext; cut at ~9000 chars)
Coding agents such as SWE-agent [ 66 ] and the agents shipped with commercial assistants read issues, documentation, and repositories that anyone can write, and then call tools that act on the developer’s machine. A prompt injection in any of that content can direct the agent to read credentials, modify files that later run with more privilege, or send data away [ 28 , 17 , 69 ] . Model-level defenses such as structured queries [ 8 ] , instruction hierarchies [ 57 ] , and input marking [ 30 ] reduce attack success, but adaptive attackers continue to bypass them [ 68 , 38 ] . A system that runs an agent must therefore limit what the agent can do after it has been compromised. This is the setting of classic confinement [ 1 , 47 ] , applied to a principal that may follow instructions from any text it reads. Deployed agents confine tools with command allowlists, permission prompts, and operating-system sandboxes for the commands they run [ 21 , 40 ] . The exploits disclosed against them in 2025 and 2026 show where these mechanisms fail. A read-only command allowlist admitted options that run code or write files [ 46 ] ; in one case an allowlisted git show wrote a crafted format string over .git/config with --output , and the next routine git diff ran the external diff driver it defined [ 22 ] . Agents ran git inside a nested directory that git accepted as a bare repository, whose configuration then executed attacker commands [ 26 , 53 , 10 ] . Six assistants wrote through a project file that was a symlink to a file in the user’s home directory, and their approval dialogs showed the name of the link [ 20 ] . Most escapes in a series of seven did not break the sandbox at all: they planted a file in the workspace that a tool outside the sandbox later executed, such as an editor task, a hook, or the interpreter of a virtual environment [ 13 ] . In each case a check inspected a name : a command string, a path, a directory’s name. The effect depended on an object that a different parser selected later: the behavior that the full argument vector requested, the configuration file that git discovered, the file a symlink pointed to, or the program that an editor found by looking inside a directory. File-system security has known this gap for decades as the time-of-check to time-of-use and name-resolution problem [ 5 , 7 , 56 ] . Agents bring it back at every layer of the tool stack, and they can be steered into constructing the aliases themselves. Zero-Trust Agent Cells (ZTAC) is a confinement architecture for coding agents built on one rule: authorize the object that will be used, and use only the object that was authorized. ZTAC has three parts. • A cell runs the agent in a kernel sandbox that lets it load its runtime, read its key, and connect to one Unix socket. It cannot read workspace contents, open network connections, or create processes; it can read file metadata. • A broker receives signed requests on that socket and handles each in six stages: authenticate, resolve, decide, gate, execute, and record. Resolution maps the request to a concrete object (a file identified by its workspace path and inode, a program and argument vector, an endpoint), and the later stages act only on that object. • One policy, two enforcement points. The path rules that the broker evaluates are compiled, in the same order, into the Seatbelt profile under which every spawned program runs. Where the profile differs from the broker, it is stricter by design. Requests that need a human are held in an approval queue. An approval is bound to the cell, the parameters, and the resolved object, expires, and can be used once. Authorization and outcome records form a hash chain signed by the broker. We implemented ZTAC on macOS in Rust and evaluated it against 74 attacks in 7 categories. Each attack has an oracle that checks the attacker’s goal against ground truth (file contents, service logs, repository history, or the effect of a tool run after the session) instead of the broker’s reply. The adversary controls everything inside the cell, including the agent runtime and any code it runs, and may plant files in the workspace. Our contributions are: 1. An analysis of agent exploits as name/object gaps at five layers: paths, argument vectors, repository configuration, files handed to other tools, and approvals. For each layer we give a design that resolves the name before deciding. 2. A broker and cell implementation with 3,164 lines of trusted Rust code, excluding tests and dependencies, in which one policy drives both the broker and the sandbox of every spawned program. 3. An evaluation with ground-truth oracles against five configurations, among them a command sandbox of the kind deployed agents use, and 14 ablations. ZTAC lets 2 of 74 attacks succeed, contains all 10 replayed incidents, and completes 43 of 46 operations and 4 of 7 workflows. 4.
