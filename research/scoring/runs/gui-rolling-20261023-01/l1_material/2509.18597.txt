title: Robotic Ultra-Long-Horizon Manipulation Skills via Human-guided Lifelong Code Generation
source: https://arxiv.org/abs/2509.18597

§Abstract
Large language models (LLMs) can translate natural-language instructions for robotic manipulation into executable code, but ambiguity, noisy generations, and limited context windows make ultra-long-horizon tasks unreliable. Closed-loop approaches that rely only on LLM feedback also struggle because LLMs have limited robotic reasoning, even when task errors are obvious to humans. Feedback is often stored in representations that generalize poorly to unseen tasks and can cause catastrophic forgetting as new corrections accumulate. We propose LYRA, a human-guided lifelong skill learning and code generation framework that distills human feedback into modular, reusable skills and incrementally extends their functionality across successive interactions while preserving previously learned behavior. External memory stores learned skills and execution examples; retrieval-augmented generation selects relevant knowledge, while user hints guide reuse when retrieval is insufficient, supporting ultra-long-horizon execution. Experiments on Ravens, Franka Kitchen, LIBERO-long, MetaWorld, and real-world tasks show a 0.93 success rate, up to 27\% higher than baselines, and a 42\% improvement in correction efficiency. LYRA also robustly solves ``build a house'', which requires planning over 20 primitives.

§Introduction (from cached fulltext; cut at ~9000 chars)
Large language models (LLMs) and vision-language models (VLMs) bring commonsense knowledge and reasoning to robotic manipulation. Early approaches [ 1 , 2 , 3 ] used language embeddings in reinforcement or imitation learning to align robot actions with human commands, but had limited data efficiency and generalization. Later systems use LLMs such as GPT for task decomposition and language grounding [ 4 , 5 ] : an LLM splits a complex task into sub-tasks and calls a pre-trained language-conditioned policy for low-level primitives. This separates high-level planning from control, but assumes that the policy can execute every requested motion precisely despite environmental perturbations and imperfect policy design. Another direction uses LLM or VLM backbones to pretrain end-to-end Vision–Language–Action (VLA) models on robotic data [ 6 ] . Robotic data are much scarcer than data for computer vision or natural language, making large-scale pretraining difficult. These models often have at least 7B parameters, require substantial compute, and are difficult to deploy on edge devices. These constraints have slowed progress. Well-pretrained LLMs can instead follow instructions and directly generate code for robot control. LLM-generated code for robotic manipulation [ 7 ] offers another route: code itself represents the robot’s actions and can draw on an LLM’s instruction-following ability. Code-as-Policies (CaP) [ 8 , 9 ] , for example, translates human instructions into executable Python code using fixed perception and control primitives, allowing rapid deployment of new behaviors. Generated code can then be tested and revised during interaction. Yet three limitations remain: (1) LLM outputs are noisy and error-prone in long-horizon planning; (2) ambiguous language can obscure the user’s intent; (3) pre-defined primitives and handcrafted prompts restrict the agent, while limited context windows constrain the number of examples. Together, these limitations hinder complex long-horizon tasks: errors compound as plans lengthen, while a fixed primitive set and a finite prompt limit adaptation. Feedback-based approaches [ 10 , 11 , 12 ] improve robustness, but verifiers must repeat the same corrections even for previously seen tasks, so the system has not retained what it learned. Dynamic prompt adjustment can support LLM in-context adaptation, but useful corrections must first be represented and retrieved. This raises two questions. First, how should feedback knowledge be stored and reused? A correction should remain useful on related tasks without asking a verifier to repeat it. Direct prompt updates [ 13 ] can cause catastrophic forgetting, sharply reducing performance on earlier tasks as new instructions are added. Cross-task insights [ 14 , 15 ] often remain ambiguous and task-specific, limiting generalization to unseen tasks. Flat code is easy to modify, but repeated edits introduce noise and errors that destabilize long-horizon generation. Encapsulating temporally extended behaviors as skill functions offers a more stable representation: parameters can be adjusted for new tasks without repeatedly rewriting the behavior, providing flexibility and generalization while preserving stability. Second, which feedback is most efficient during interaction? Language is a convenient interface, but feedback generated solely by LLMs [ 13 , 16 , 12 ] is often unreliable: it may diverge from human preferences or fail on ultra-long-horizon reasoning [ 16 ] . Humans can usually identify, evaluate, and correct robotic task errors that an LLM may miss. In robotic code generation, those corrections can be tested and verified within seconds, whereas training conventional deep learning models often takes hours or days. This short feedback cycle makes human-guided robotic skill learning both reliable and efficient. We therefore propose a human-guided framework that turns user feedback into reusable skills and extends their functionality through a user-designed curriculum, enabling preference-aligned lifelong learning (Fig. 1 ). Across interactions, the curriculum expands what a skill can do while preserving the functionality already learned. External memory stores learned skills and execution examples to prevent catastrophic forgetting and support reuse across tasks. Retrieval-Augmented Generation (RAG) selects relevant skills and examples for dynamic in-context learning during long-horizon planning, without placing the entire accumulated experience in a limited prompt. When retrieval is insufficient, user hints steer the agent toward the skills needed for the current task, improving efficiency and reducing interference from irrelevant data. Our system-level contribution is to show, theoretically and empirically, that human feedback in robot control code generation can become persistent, generalizable, and compositional skill knowledge rather than repeated local corrections. ## II METHOD
II-A Preliminaries Code generation for robotic manipulation can be modelled as using an LLM f to map a natural language instruction l to a robot control code c , i.e., f(l)=c , where f is termed a Language Model Program (LMP) in prior work [ 8 ] . Each code c is achieved by multiple behaviours b ; thus, f can also be viewed as a mapping from l to b . A behaviour b\in\mathcal{B} denotes an evaluable semantic motion or outcome produced during robot execution, such as picking up an object. In our work, we argue that behaviours b requiring no variation can be encapsulated as skills that reliably elicit these behaviours. We denote the skill space as \mathcal{Z} and state parameters as s . Importantly, a skill z\in\mathcal{Z} may also build on other skills: Definition 1 : A skill z\in\mathcal{Z} is an executable parameterized function. Given state-dependent parameters s , its execution realizes a target behaviour b\in\mathcal{B} , denoted as b=\mathrm{Exec}(z,s) . It is worth noting that although the task code c generated by the agent represents a sequence of behaviours to accomplish a task, it is not equivalent to a skill. We define a task (l,s_{0}) by a natural language instruction l and an initial environment state s_{0} , which together form the main interface between the user and the agent. When a task is successfully completed with user feedback, we extend this tuple to (l,s_{0},c,s_{T}) , where c is the task-specific code (often flat, process-oriented) and s_{T} is the achieved final state. In practice, c may call skills z to complete the task, and its execution should produce an evaluable task result. To align the skill output with the user’s desired behaviour b , the agent adjusts the function details under user guidance. We call this process learning the skill . Importantly, “learning” does not refer to deep learning, instead follows a broader concept in computer science [ 17 ] : Definition 2 : An agent is said to learn if it produces better behavioural responses b to an instruction l , as evaluated by a human. Based on these definitions, the learning pipeline should answer: (1) How to encode human-provided feedback into skills that align with user preferences? (2) How to extend skills through lifelong learning while enabling dynamic in-context adaptation? (3) How to reuse and transfer learned skills to unseen long-horizon tasks? II-B Preference-aligned Skill Acquisition Based on the above questions, we design a three-phase pipeline to preserve and utilize human-guided feedback for preference-aligned lifelong skill learning in long-horizon manipulation (Fig. 2 ). The phases are: (1) preference-aligned skill acquisition, (2) lifelong capability extension, and (3) task-specific retrieval and planning. To learn a new skill, three elements must be clarified: (1) what skill to learn, (2) the initial task environment, and (3) the expected functionality or behavior. Asking an LLM to infer all of this at once is impractical due to language ambiguity, so we adopt multi-turn interaction. The agent is initiated with a fixed set of skills z\in\mathcal{Z}_{0} , along with examples e=(l,c)\in\mathcal{E}_{0} that demonstrate their use, enabling basic environment interaction. The user first describes the skill in natural language, and the LLM invokes the “skill_parse” API to generate a Python function header with suggested parameters (e.g., “def stack_blocks(blocks, start_pose):”). The user can accept or refine this skill definition. Once accepted, the LLM requests a base environment setup, and generates a corresponding task scenario. The complexity of the task is user-controlled, but overly complex tasks (over 6–8 steps) hinder skill acquisition when the agent’s ability is still limited. We therefore recommend two principles: (1) tasks should be simple, ideally completed within 1–4 primitives, and (2) tasks should allow flexibility so that one skill can adapt to diverse requirements. After the setup, the user and the LLM agent will work together to “learn” the skill. The agent generates candidate code, deploys it in simulation, and displays results in real time. The user then accepts, rejects, or provides free-form feedback to refine the skill. User tests multiple requirements within the same scenario to check if the skill and its parameters generalize. For example, in Fig. 2 Phase I, the user guides the agent to stack blocks under different conditions such as edge alignment, tower positioning, or rotation. During this phase, the agent can freely modify implementation details under the reserved skill name , with the objective of producing a functional, preference-aligned skill. This forms the foundation for later phases of lifelong skill learning and capability extension. II-C Lifelong Learning-oriented Capability Extension Learning skills from a single task scenario is insufficient for complex ultra-long-horizon tasks, for two main reasons: (1) Simple skills cannot handle variations beyond their learning distribution. For example, a skill like “stack_blocks”, which stacks four blocks at a fixed pose, cannot generalize to tasks such as building a \{i\times j\times k\} structure or stacking multiple towers by color or size. (2) Directly inserting learned skills into prompts risks hallucination, where LLMs may rewrite or fabricate code during long-horizon interactions, leading to catastrophic forgetting of existing skills. Inspired by lifelong learning, we extend the pipeline with a user-designed curriculum that enables bottom-up skill functionality expansion (Fig. 2 Phase II). In this phase, the agent must: (1) solve more complex user-defined task variations, (2) preserve and extend skill functionality to unseen cases, and (3) store skills permanently for reuse. The learning process mirrors Phase I, with an added meta-prompt that explicitly asks the agent to preserve prior functionality while adapting to new tasks . Users should design tasks outside the original distribution and aligned with long-term goals, guiding the agent to acquire foundational skills for future complex tasks. The agent can either (1) create a new named skill that calls existing ones as nested functions, or (2) extend the current skill using modularized code (e.g., if-else or match-case) to avoid overwriting. After adapting to new tasks, the agent is re-evaluated on prior tasks; if performance is preserved, we can say that lifelong learning is achieved. To further prevent forgetting and hallucination, both learned skills z and explored successful examples (including task instruction and task plan) (l,c)\in\mathcal{E} are stored in external memory and retrieved during planning. II-D Task-specific-oriented Retrieval and Planning In Fig. 2 Phase III, we enable long-horizon planning through in-context learning, adapting general-purpose LLMs to specific tasks using two main prompt inputs: (1) few-shot task-specific examples \mathcal{E}=\{(l_{1},c_{1}),...,(l_{M},c_{M})\} that show mappings from instructions to task-specific code plan, and (2) a set of task-agnostic skills \mathcal{Z}=\{z_{1},...,z_{N}\} that the agent can call to compose the plan c . Due to context window limits, both |\mathcal{E}|=M and |\mathcal{Z}|=N are fixed. The goal is that the examples and skills are representative enough for the agent to generalize to unseen pairs (l^{\prime},c^{\prime}) , assuming l^{\prime} reflects the human’s intent and the LLM can produce the correct c^{\prime} from \mathcal{E} and \mathcal{Z} . Key to our approach is dynamically managing the context window . As the number of examples grows, appending all of them to the prompt is infeasible, and many are irrelevant. For example, when solving “press the button”, examples about “open the drawer” add noise and overwhelm the prompt. To address this, we use an external memory module with two vector databases: one for few-shot examples (l,c) indexed by their instructions, and one for skills z indexed by their docstrings. We implement this using ChromaDB and compute embeddings with OpenAI’s text-embeddings-3 [ 18 ] . For a new instruction l^{\prime} , we retrieve the K=10 most similar examples based on cosine similarity and append them to the prompt. We also retrieve the relevant skill headers from memory and include them in the prompt. Additionally, our framework introduces a simple yet efficient mechanism for guiding the agent with a shared free-form language format: hints . Hints allow users to explicitly indicate which previously learned skill may assist with the current task, effectively triggering retrieval from the library of known behaviors. Because our skill library is developed bottom-up, while long-horizon tasks require top-down decomposition, automatic similarity-based retrieval may occasionally overlook a relevant skill, making user-provided hints a simple yet highly effective way to guide the agent toward the correct skills. As the number of skills |\mathcal{Z}| and behaviours |\mathcal{E}| grows, most are irrelevant, and hints provide a way for the user to direct the agent toward the correct subset. If a required sub-behaviour has not yet been learned and cannot be resolved with a hint, the failure signals the user to pause the current skill and teach the missing sub-behaviour first. With this pipeline, our framework can tackle challenging ultra-long-horizon tasks such as “build a house” and “stack a jenga tower”, which require more than 20 planning steps (Fig. 2 Phase III left). We further validate our method on widely used benchmarks, including Metaworld and Franka Kitchen, covering over 20 task variations where the framework consistently solves all tasks (Fig. 2 Phase III middle). Finally, we deploy the framework in real-world settings on a franka FR3, successfully completing diverse tasks such as building a house, and generalizing to the novel task “build a temple” (Fig. 2 Phase III right). It is worth noting that although we present the learning pipeline in three phases, the process is not strictly linear . Whenever the agent cannot handle the current task, the user can roll back to the skill learning or extension phase and iterate until the agent meets the requirements.
